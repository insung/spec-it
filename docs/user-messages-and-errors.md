# User messages and error contracts

이 문서는 0.2.0 규칙 [MSG-001](../rules/messages/MSG-001.md), [MSG-002](../rules/messages/MSG-002.md), [ARCH-005](../rules/architecture/ARCH-005.md)의 적용 방법을 설명합니다. 새 의무의 정본은 각 규칙이며, 0.1.0에 고정된 프로젝트에는 자동 적용되지 않습니다.

## 공통 규칙과 프로젝트의 선택

spec-it은 무엇을 정의하고 검증할지를 정합니다. 실제 한도·권한·노출 조건·문구·언어·로그 수준·후속 행동은 프로젝트의 책임입니다. 작은 서비스에서도 규칙마다 프레임워크를 만들 필요는 없습니다. 기존 기능 명세와 계약 파일에서 시작하고 재사용이 실제로 필요할 때만 분리합니다.

| 책임 | 정본과 소비자 |
| --- | --- |
| 업무 판단 | 도메인 코드가 결과와 안전한 값을 반환한다. DB 최적화 예외는 별도 승인한다 |
| 실행과 복구 | 애플리케이션이 트랜잭션·재시도·유실 불가 후속 작업을 조율한다 |
| 공개 결과 | API adapter가 stable code·parameter·transport status로 변환한다 |
| 사용자 안내 | 화면·CLI·메일의 표현 계층이 대상·상태·언어에 맞춰 표시한다 |
| 내부 진단 | 운영 경계에서 원인과 correlation ID를 기록하되 비밀정보를 제거한다 |

DB 예외를 그대로 외부 응답으로 전달하지 않습니다. 공개 결과는 내부 실패 원인 여러 개를 안전한 일반 code 하나로 매핑할 수 있습니다. 내부 원인과 외부 안내는 같은 정보 집합이 아닙니다. 예상된 업무 거절은 사용자에게 오류여도 운영 장애 알림일 필요는 없습니다.

후속 작업을 로그나 메시지 문자열에서 추론하지 않습니다. 결과 미확인을 확정 실패로 안내하지 않고, 성공한 본 작업과 실패한 선택적 알림도 구분합니다. 유실 불가 전달에만 outbox 등 내구성 있는 방식의 필요성을 검토합니다.

## 구현 코드 대신 계약을 공유한다

프론트와 백엔드가 서로의 구현 패키지를 import할 필요는 없습니다. 그러나 code·parameter·상태 의미에 대한 계약 의존성은 남습니다. HTTP는 OpenAPI, 다른 transport는 해당 계약 형식을 선택할 수 있습니다. 특정 도구나 새 공통 저장소를 기본으로 요구하지 않습니다.

프로젝트는 정본 방향을 하나 선택합니다.

- **contract-first:** 언어 중립 계약에서 타입·문서·검사용 자료를 만든다. 생성물을 직접 수정하지 않는다.
- **code-first:** 백엔드의 타입 있는 정의에서 계약을 추출하고, 소비자 타입·검사 자료는 그 계약을 따른다. 추출된 계약을 별도로 손수 유지하지 않는다.

같은 정보가 이미 OpenAPI 등에 있다면 [YAML 템플릿](../templates/project/user-message-contract.yaml)에 또 손으로 복사하지 않습니다. 기존 계약을 정본으로 선택하고 메시지의 조건·번역·수용 사례처럼 부족한 책임만 연결합니다. 템플릿은 독립된 작은 정본으로 시작하는 예이며 통합 엔진이나 OpenAPI 생성기는 포함하지 않습니다.

### HTTP stream의 오류 mapping

SSE 같은 HTTP stream은 response가 열리기 전과 열린 뒤를 구분합니다. 입력·인증·한도처럼 stream 전에 확정한 오류는 의미에 맞는 HTTP status와 일반 오류 body로 반환합니다. stream이 열린 뒤의 실패나 결과 미확인은 이미 시작한 response의 status를 바꾸지 않고 canonical stream contract의 typed event로 전달합니다. 정상 완료 event, transport 단절, 재연결·resume, 중복 처리와 재시도 안전성도 별개 acceptance case로 검증합니다.

`user-message-contract`의 `transport: http-stream`은 각 outcome에 `delivery_phase`를 요구합니다. `before-stream` outcome은 `http_status`를, `after-stream` outcome은 `stream_event`를 기록합니다. OpenAPI 3.2 `itemSchema`, 연결된 schema 또는 실행 가능한 provider-consumer 계약 중 프로젝트 toolchain이 실제로 보존하는 정본을 선택합니다.

새 code나 parameter의 변경은 구버전 소비자를 고려합니다. 타입 생성은 실행 중인 구버전 앱을 바꾸지 않습니다. 소비자는 모르는 code에 안전한 일반 안내를 제공하고 자동 재시도하지 않으며, 운영에서는 진단할 수 있게 합니다. 동시에 배포해야만 작동하는 계약을 기본으로 만들지 않습니다.

## 다국어와 노출 조건

UI 번역은 해당 클라이언트, 서버 메일은 서버 표현 계층이 소유하는 것이 기본입니다. 번역 key와 치환 parameter 타입을 연결하되 번역 문장으로 프로그램을 분기하지 않습니다. 한 언어만 지원할 수도 있습니다. 지원하지 않는 언어는 선언된 기본 언어, 모르는 code는 안전한 일반 key로 처리합니다.

문장 단위 번역과 locale별 숫자·날짜·복수형 처리를 선택합니다. 형식 검사는 누락 key와 parameter 불일치를 잡지만 번역이 자연스럽고 정책 의미가 같은지는 사람이 검토합니다. 법적 약속·권한·환불·재시도 의미가 바뀌는 문구는 단순 교정으로 취급하지 않습니다.

노출 조건은 성공/실패만이 아닙니다. 대상, 비노출, 동시에 참인 조건의 우선순위, 중복 억제, 해제, 이후 가능한 행동을 포함합니다. [fixture](../examples/user-message-contract/README.md)는 내보내기 한도 거절의 한 예만 보여주며 회사나 실제 제품의 정책이 아닙니다.

## 문서와 코드가 다르지 않은지 어떻게 확인하나

규칙을 읽었다는 AI의 말이나 테스트 개수는 준수 증거가 아닙니다. 적용 규칙을 manifest/lock에서 확인한 뒤 실제 파일·실행 결과·승인 기록을 연결합니다. 0.2.0 검토는 0.1.0에 고정된 프로젝트의 정책 검사와 별도로 표시합니다.

| 확인할 질문 | 검증 방법 | 이것만으로 보장하지 못하는 것 |
| --- | --- | --- |
| 도메인이 DB·웹 SDK에 의존하는가 | import/의존성 검사와 경계 코드 검토 | 업무 분기가 올바른 위치와 의미를 갖는지 |
| 트랜잭션과 프로시저가 안전한가 | 목표 DB에서 중간 실패·동시 요청·rollback·migration 검사 | 모든 운영 부하에서의 안전성 |
| 오류 code와 parameter가 일치하는가 | 계약 schema, 실제 응답 검사, 생성물 차이 검사 | 어떤 조건에서 그 code를 내야 하는지 |
| 승인한 상황에서 맞는 안내를 하는가 | Given/When/Then 사례, 노출/비노출·경계·충돌 테스트 | 테스트에 없는 업무 요구 |
| 번역과 구버전이 안전한가 | key/치환 값 검사, 미지원 locale·모르는 code·구버전 소비자 테스트 | 문장의 자연스러움과 정책 의도 |
| 로그와 후속 작업이 분리되는가 | 로그 redaction, 중복/유실/알림 실패 테스트 | 외부 서비스의 모든 실패 형태 |

### 실제 프로젝트에서의 최소 검증 순서

1. **적용 대상 확정:** 정확한 정책 소스·버전, manifest/lock, 예외를 확인합니다. `not-applicable`에도 이유가 필요합니다.
2. **사람이 수용 사례 확인:** 조건·권한·기대 결과를 먼저 정합니다. AI가 구현에서 역으로 만든 기대값만 사용하지 않습니다.
3. **프로젝트 테스트 실행:** 변경 전 실패, 구현 후 통과를 확인하고 [통합 테스트 계획](../templates/testing/integration-test-plan.md)의 해당 경계를 검사합니다.
4. **독립 검토:** [TST-002](../rules/testing/TST-002.md)에 따라 구현과 분리된 관점으로 승인된 사례와 실물을 대조합니다. 다른 AI의 동의만으로 증거를 대체하지 않습니다.
5. **증거와 미확인 사항 보고:** 규칙 ID, 검사한 commit과 미커밋 diff 범위, 계약 버전, 명령·실행 환경·시각·결과, 증거 위치와 확인자를 남깁니다. 증거 유효성은 [RULE-003](../rules/rule-system/RULE-003.md)의 위험·변경 조건을 따릅니다. 보안 로그 원문은 보고서에 복사하지 않습니다.

### 현재 할 수 있는 것과 아직 없는 것

Phase 0의 [spec-it:check](../skills/spec-it-check/SKILL.md)는 **절차 명세**입니다. 검사기를 설치하거나 코드 생성을 수행하는 실행 명령이 아닙니다. 사용 가능한 AI가 해당 지침을 읽고 수동 검토할 수 있지만 CI guard가 생긴 것은 아닙니다.

기존 판정 계약은 [TOOL-001](../rules/tooling/TOOL-001.md), [RULE-002](../rules/rule-system/RULE-002.md)가 정합니다. 실제 위반은 `fail`, 적용되지 않으면 근거와 함께 `not-applicable`, 미구현 자동 검사·누락 증거·미결 판단은 `human-review`입니다. 프로젝트 테스트가 통과했다는 관측은 보고할 수 있어도 미구현 규칙 검사 전체를 `pass`로 바꾸지 않습니다.

향후 검사기에 연결할 때도 필드 형식과 실제 의미를 나눕니다. OpenAPI diff가 없더라도 한도·권한·오류 발생 조건은 바뀔 수 있습니다. schema와 문서 생성만으로 이 차이를 막을 수 없으므로 동작 테스트와 사람 소유 수용 기준이 필요합니다.

새 [계약 schema](../schemas/user-message-contract.schema.json)는 구조만 검사합니다. code/key의 교차 참조, 번역 치환 값, 파라미터별 값, 실제 조건의 실행 여부는 별도 검사 대상입니다. 이번 fixture의 사례는 실행 증거가 아니며, schema 검사 통과도 애플리케이션 준수 인증이 아닙니다.
