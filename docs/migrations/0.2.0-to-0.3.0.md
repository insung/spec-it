# Migrate a project from 0.2.0 to 0.3.0

0.3.0은 DB 변경 배포와 정기 데이터 산출물 운영 의무를 추가한 pre-1.0 minor release입니다. 기존 0.2.0 project manifest와 lock은 그대로 유효하며 자동 업그레이드하지 않습니다.

## 주요 변화

- DB migration을 version·checksum·소유권·application compatibility·single-executor coordination·environment history·recovery class가 있는 release unit으로 관리하는 `DATA-009`
- scheduled pipeline의 terminal output freshness·completeness·integrity·reconciliation과 run ledger·alert·replay를 연결하는 `OBS-003`
- DB 변경 책임과 정기 데이터 생산 책임을 조건부로 선택하는 `capability/db-migration`, `capability/data-pipeline`

## 프로젝트별 절차

1. 현재 manifest와 lock이 0.2.0에 고정되어 있는지 확인합니다.
2. DB schema·routine·reference data·backfill을 작성·요청·실행하면 `capability/db-migration` 후보로 분류합니다. RDS를 읽기만 한다는 이유로 선택하지 않습니다.
3. 정기 또는 외부 trigger로 product·report·model·downstream job용 데이터를 생산하면 `capability/data-pipeline` 후보로 분류합니다.
4. SQL 객체 소유자와 정본 위치, 중앙 release view, 실행 권한과 delegated lane, application compatibility 표현, recovery class를 결정합니다.
5. pipeline별 expected schedule, target partition, terminal outputs, 정상 빈 결과, freshness·completeness·integrity·reconciliation 검사, alert owner와 replay 경계를 결정합니다.
6. 0.3.0 shadow assessment에서 기존 history·monitoring이 없는 항목을 legacy finding으로 분리하고 정책 채택만으로 운영 DB나 과거 migration을 일괄 변경하지 않습니다.
7. 승인된 profile과 parameter를 manifest에 반영하고 정확한 0.3.0 source에서 lock을 다시 해석합니다. Phase 0 generation은 `human-review`입니다.
8. 실제 release와 run evidence를 대조한 `spec-it:check` 결과를 승인합니다. 신규 자동 검증은 `planned`이며 pass로 보고하지 않습니다.

## 롤백

프로젝트가 새 규칙에 따라 운영 흐름이나 DB를 바꾸지 않았다면 manifest와 lock을 0.2.0으로 되돌릴 수 있습니다. 이미 migration history, release manifest, runtime guard, pipeline monitoring 또는 replay 경로를 도입했다면 정책 파일만 낮추지 말고 해당 운영 계약의 소유자와 소비자 영향을 먼저 확인합니다.
