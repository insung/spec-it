# 0.5.0 → 0.6.0 migration guide

상태: **공개 릴리스**. 공개 권위는 annotated tag `v0.6.0`이며 기존 프로젝트를 자동 업그레이드하지 않는다.

## 변경 범위

- `CODE-005`는 설정 parser·loader 내부의 raw string map과 runtime consumer로 전달하는 이름 있는 typed configuration contract를 구분한다.
- `CODE-006`은 외부 정본이 소유하고 코드와 독립적으로 변하는 사실을 주석에 손으로 복제하지 않도록 한다.
- `backend-service`, `serverless-function`, `python` profile이 두 공통 규칙을 연결한다.
- Python 설정 key의 일괄 상수화, 특정 settings framework, validator, Ruff extension과 CI action은 추가하지 않는다.

## 기존 프로젝트의 재수렴

기존 프로젝트는 고정한 버전을 계속 사용할 수 있다. 업그레이드를 선택할 때만 `spec-it:clarify`와 `spec-it:converge`로 manifest와 lock을 새 공개 release source에서 다시 생성한다. lock의 version이나 rule 목록을 손으로 고치지 않는다.

1. 기존 manifest, lock, exception과 실제 선택 profile을 읽는다.
2. raw configuration map이 loader 밖의 composition·runtime consumer 경계를 넘는지 찾고, 해당 경계의 필드·타입·선택 여부·기본값을 결정한다.
3. 주석과 docstring이 외부에서 독립적으로 바뀌는 값이나 불안정한 문서 위치를 복제하는지 검토하고, 안정된 authority와 지속되는 이유로 바꿀 범위를 승인한다.
4. 기존 동작과 호환성, secret 처리, consumer 변경 범위를 확인한 뒤 프로젝트 코드를 별도 변경으로 다룬다.
5. 발행된 exact version과 policy digest를 사용해 lock을 재생성하고, 사람이 두 규칙의 준수 증거를 검토한다.

### 0.2.0 이하에서 바로 오는 프로젝트

0.2.0에 고정된 프로젝트는 이 문서의 두 규칙만 추가해서는 안 된다. [0.2.0 → 0.3.0](0.2.0-to-0.3.0.md), [0.3.0 → 0.4.0](0.3.0-to-0.4.0.md), [0.4.0 → 0.5.0](0.4.0-to-0.5.0.md)의 조건부 profile, lock 형식, 계약과 미구현 경계를 순서대로 평가한다. 적용되지 않는 capability는 근거를 남겨 제외하고, 선택한 모든 profile을 새 공개 source에서 한 번에 다시 resolve한다. 중간 version의 lock을 손으로 합치거나 최종 lock에 rule ID만 덧붙이지 않는다.

## 남은 구현

두 규칙은 `manual/implemented` human review다. Phase 0에는 설정 계약 검사기, comment freshness 검사기, Ruff rule, CLI 또는 CI action이 없다. schema와 profile 구조 검사가 성공해도 애플리케이션 코드 준수를 기계적으로 증명하지 않는다.
