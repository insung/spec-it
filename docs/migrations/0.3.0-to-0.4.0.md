# Migrate a project from 0.3.0 to 0.4.0

0.4.0은 policy source pinning, DB release 책임·증거 경계, HTTP streaming 오류 계약, EC2 runtime과 Docker Compose deployment profile을 추가하거나 정밀화한 pre-1.0 minor release입니다. 기존 0.3.0 project manifest와 lock은 그대로 유지되며 자동 업그레이드하지 않습니다.

## 주요 변화

- lock schema 0.2.0이 `policy_digest`를 필수로 하고 distribution mechanism이 제공하는 immutable `policy.revision`을 선택적으로 기록합니다.
- `capability/db-migration`이 object decision owner, definition authority와 executor를 구분하고 immutable release digest와 그 digest를 참조하는 environment history를 요구합니다.
- baseline이나 current-state definition projection을 두는 프로젝트는 authority와 release chain 대조 방법을 선언하고, 사후 복원 기록을 정상 pre-approved release와 구분합니다.
- `capability/http-api`가 streaming wire contract와 stream open 전·후 오류 mapping 결정을 추가합니다.
- `runtime/aws-ec2`와 `deployment/docker-compose`가 host runtime과 deployment definition을 독립 축으로 평가하며, EC2는 interruptible capacity와 대체 용량 복구를 project threshold 안에서 판단합니다.
- `capability/rds`가 infrastructure trait을 선택해 topology, capacity, failover, backup·PITR, restore, maintenance, heavy DDL와 ownership boundary를 평가합니다. 새 project-owned table·column에는 `lower-snake-case` 기본값을 제공하고 legacy·외부 소유 identifier는 기존 계약을 보존합니다.
- manifest owner에 선택적 `operations-owner`가 추가되고 `spec-it:converge`가 생성 산출물의 `.gitignore` 병합을 확인합니다.

## 프로젝트별 절차

1. 현재 manifest와 lock이 승인된 0.3.0 source를 가리키는지 확인합니다.
2. 공개된 0.4.0 release artifact의 version과 immutable content를 확인합니다. draft worktree의 version label만으로 lock을 만들지 않습니다.
3. manifest의 `policy.source`와 version을 0.4.0으로 갱신하고, 운영 판단의 승인자가 별도이면 `operations-owner`를 기록합니다.
4. SSE 또는 다른 HTTP streaming endpoint가 있으면 wire format, event schema, completion, heartbeat, disconnect, reconnect, resume와 before/after-open 오류 mapping을 결정합니다. 비스트리밍 HTTP만 있으면 해당 결정은 적용하지 않습니다.
5. project-managed EC2 host가 있으면 `runtime/aws-ec2`, Compose가 deploy unit을 정의하면 `deployment/docker-compose`를 각각 평가합니다. 한 축이 다른 축을 암시하지 않습니다. Spot 같은 interruptible capacity를 사용하면 비율을 공통값에서 가져오지 않고 minimum stable capacity, pool diversity, interruption 처리와 replacement-time budget을 프로젝트에서 승인합니다.
6. 관계형 DB를 사용하면 infrastructure·operations·data·schema object·migration execution의 소유 경계, topology와 failover, RPO·RTO, backup·PITR와 restore evidence, connection·storage·IOPS·maintenance threshold를 재수렴합니다. 새 project-owned table·column은 `lower-snake-case` 기본값을 적용하고 필요한 다른 객체 category의 convention도 정합니다. 기존 convention을 유지하려면 project override와 경계를 기록하며, legacy·외부 소유 identifier는 보존합니다. 이름을 바꿔야 한다면 versioned migration, consumer compatibility와 recovery evidence를 승인합니다.
7. `capability/db-migration`을 사용하면 object decision owner, definition authority와 executor 또는 delegated lane을 구분합니다. 승인된 release definition에 digest를 부여하고 환경별 적용 기록이 그 digest를 참조하게 합니다.
8. baseline이나 desired schema를 함께 두면 독립 정본인지 파생 projection인지 선언하고, 이전 기준선과 승인된 release chain을 적용한 결과와의 대조 방법을 정합니다. 과거 변경을 뒤늦게 복원한 기록은 historical 또는 emergency reconciliation으로 분류합니다.
9. 현재 manifest digest와 공개 policy bundle digest를 계산해 lock schema 0.2.0으로 다시 수렴합니다. Git 배포라면 tag가 가리키는 commit을 `policy.revision`에 기록할 수 있습니다.
10. `.gitignore`에 생성 report, local environment, cache가 빠져 있는지 확인하고 기존 사용자 항목을 보존한 채 필요한 항목만 병합합니다.
11. schema·rule reference·link 검사와 실제 프로젝트 증거를 분리해 `spec-it:check` 결과를 승인합니다. Phase 0의 자동 생성·runtime 검사는 여전히 `human-review` 또는 `not-implemented`입니다.

## 롤백

새 policy digest만 기록했고 애플리케이션·DB·인프라 계약을 바꾸지 않았다면 승인된 0.3.0 release source와 lock으로 되돌릴 수 있습니다. DB release identity나 environment history를 분리했거나 streaming protocol, EC2 topology, Compose deployment 또는 운영 소유권을 이미 변경했다면 정책 파일만 낮추지 말고 evidence reference, consumer, availability, data compatibility와 recovery 영향을 먼저 검토합니다.
