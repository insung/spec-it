# Migrate a project from 0.1.0 to 0.2.0

0.2.0은 새 의무를 추가한 pre-1.0 minor release입니다. 정책 저장소의 릴리스가 기존 프로젝트를 자동 업그레이드하지 않습니다. 프로젝트 책임자가 영향을 검토하고 새 정책 버전을 승인한 뒤 `spec-it:clarify`와 `spec-it:converge`를 다시 수행합니다.

## 주요 변화

- transport DTO와 application input의 분리, transaction·후속 작업 소유권과 DB procedure 경계
- HTTP API resource·command·naming·canonical contract·audience와 lifecycle
- 사용자에게 보이는 message·error code·locale과 내부 log의 분리
- production-derived data를 포함한 격리 통합 테스트와 공유 domain library consumer 추적
- 영어 project identifier, 의미 중심 callable·collection 이름, 이름 있는 business result와 lint contract
- 인프라 profile evaluation, 구현 중 bounded re-evaluation, platform 선택 전 availability 판단과 Redis 물리 저장 최적화

## 프로젝트별 절차

1. 현재 project manifest와 lock이 0.1.0에 고정되어 있는지 확인합니다.
2. `spec-it:check`로 0.2.0 shadow assessment를 수행해 새 규칙, 후보 profile, 기존 위반과 필요한 증거를 분리합니다.
3. 사용자 메시지, API, shared domain library, RDS·Redis·Lambda 등 실제 capability만 선택하고 나머지는 `not-applicable` 근거를 남깁니다.
4. 실행 source가 있으면 repository-owned formatter·linter·static analyzer·필요한 type checker, 설정·명령·범위·CI 목표를 결정합니다.
5. infrastructure profile이 있으면 SLO, cost budget, guardrail과 project-owned revisit threshold를 결정합니다. 공통 profile의 관측 항목을 숫자 기본값으로 오해하지 않습니다.
6. brownfield 이름과 boundary 위반은 새 변경과 legacy finding을 구분해 안전한 remediation 경계를 승인합니다. 정책 채택만으로 일괄 수정하지 않습니다.
7. manifest의 `policy.version`을 `0.2.0`으로 변경하고 승인된 profile과 parameter를 반영합니다.
8. 정확한 0.2.0 source에서 lock을 다시 해석합니다. Phase 0에는 실행 generator가 없으므로 deterministic generation은 `human-review`입니다.
9. 적용 규칙별 테스트·benchmark·ADR·예외를 확인하고 `spec-it:check` 결과를 승인합니다.

## 롤백

프로젝트가 아직 0.2.0 변경을 구현·배포하지 않았다면 manifest와 lock을 검토 전 0.1.0 commit으로 되돌릴 수 있습니다. 이미 공개 계약, 데이터, DB routine 또는 library consumer가 바뀌었다면 정책 파일만 낮추지 않고 해당 migration과 운영 rollback을 먼저 수행합니다.
