# 의도에서 관찰 결과까지 연결하기

이 문서는 기존 [GOV-001](../rules/governance/GOV-001.md), [GOV-002](../rules/governance/GOV-002.md), [HITL-002](../rules/hitl/HITL-002.md), [TST-002](../rules/testing/TST-002.md)의 실행을 돕는 선택적 절차다. 새 공통 의무, QA 제품, 자동 통과 기준이 아니다. 스킬과 템플릿이 존재하는 것과 agent가 실제로 실행한 것은 다르다.

## 사용자가 먼저 작성할 최소 입력

한 문장으로 문제와 원하는 결과를 말하고 알고 있는 원본을 제공하는 것으로 시작할 수 있다. AI가 조사 가능한 경로·기술 정보를 먼저 찾고 목적, 대상, 결과, 정상 예시/반례, 유지 조건, 판정자와 미결정을 정리한다. 모르는 항목은 미확정으로 남겨도 된다. 사람에게 모든 서식을 채워오라고 요구하지 않는다.

되읽기는 “이해했습니다”가 아니라 결과를 대조하는 절차다. 예를 들어 제외 목록을 한 작업에만 적용하는지 계정 전체에 적용하는지, 저장 성공 후 시작한 선택에 적용하는지 진행 중인 작업에도 적용하는지는 서로 다른 동작이다. 조사로 알 수 없는 중요한 차이만 예시·추천·영향과 함께 질문하고 결정자의 답변을 관련 시나리오에 반영한다. 답변·위임 범위가 이미 있으면 반복 질문하지 않는다. 의미가 바뀌지 않는 오타 수정에 이 전체 절차를 붙이지 않는다.

## 완료 검토에서 볼 연결

| 출발점 | 확인할 연결 | 끊겼을 때 다음 작업 |
| --- | --- | --- |
| 원본 기획의 목적·조건 | 승인된 해석과 정정 이력 | 원문 재확인, 중요한 차이는 결정자에게 질문 |
| 해석·디자인 상태 | Scenario, 대상 유형·실행 경로·유지 조건 | 파생 명세가 놓친 원문 요구와 별도 경로 조사 |
| Scenario | 구현/화면/계약과 실제 관찰 위치 | 저장 테스트가 실제 선택 결과를 대신하는지 확인 |
| Case revision | 구현·QA revision, 환경·DB, Run ID와 관찰 | 미실행/미접근을 표시하고 필요한 실행 계획 |
| 결함 | 수정 대상·회귀 사례·후속 run·확인자 | 원인 미확정을 유지하고 조사/수정 담당 구분 |

원문에서 파생물로, 파생물에서 원문으로 양방향 검토한다. AI가 만든 표 내부에 빈칸이 없다는 이유만으로 원문 누락이 없다고 하지 않는다. 원문 접근이 없으면 원문 완전성은 `human-review`다. 열 번 검토해도 증거가 없는 경로는 검증되지 않았고, 한 번의 검토라도 명시된 범위의 관찰 근거는 사용할 수 있다. 이는 모든 실수를 막는 보장이 아니다.

## QA를 계획 검사로만 끝내지 않기

- **기획 적합성**: 승인된 조건에서 요구한 결과가 나오는가.
- **고객 목적 확인**: 그 결과가 해결하려던 문제를 실제로 해결하는가. 설정 저장 성공과 실제 제외 성공은 다를 수 있다.
- **탐색 검증**: 승인 시나리오 밖의 우회 경로·경계·혼재 상태에서 무엇이 깨지는가. 발견한 가설을 임의로 새 요구나 확정 원인으로 승격하지 않는다.

업데이트/회귀 범위는 변경 위험으로 선정한다. 서버·클라이언트 혼재가 있으면 지원 조합과 순서, DB 변경이면 이전/이후 데이터·null/default·부분 적용·쓰기 이후 rollback을 살핀다. 비대상 회귀와 권한·계정 경계도 관련될 때 포함한다. 미지원 조합은 근거·결정자를 남기며 조합 전체를 무조건 실행하거나 오타에 대규모 QA를 요구하지 않는다. 격리·fixture·외부 side effect와 비용·중단 조건은 적용되는 [TST-003](../rules/testing/TST-003.md), [TST-006](../rules/testing/TST-006.md), [DATA-009](../rules/data/DATA-009.md)의 경계를 따른다. 계획 작성은 DB 검사나 업그레이드 실행 증거가 아니다.

## 도구가 분산되어 있을 때

원본의 권한은 기획·디자인·코드·QA 각각 유지한다. 기존 상위 변경 기록 한 곳에서 Change ID와 Scenario ID로 상태를 모으고, 하위 PR/이슈는 그 기록을 참조할 수 있다. 원본 링크를 매번 복제하거나 팀 전체를 GitHub로 이동시킬 필요는 없다.

QA 시트는 프로젝트가 이미 쓰는 문서 DB, 스프레드시트, 이슈 또는 별도 QA 저장소에 둘 수 있다. 사례 ID/revision과 실제 실행 이력을 구별할 수 있는 위치를 고른다. 테스트 코드는 QA 저장소에 두고 구현 저장소는 대상 commit/artifact와 결과 참조만 가질 수 있다. 원본 revision이 없으면 허용된 snapshot/digest와 관측 시각을 사용하되, 시각만으로 내용 불변을 주장하지 않는다.

과거 run의 실패→수정→재실행을 보존한다. 기획 변경은 새 case revision과 새 run으로 연결하고 기존 통과를 수정된 기획의 통과로 바꾸지 않는다. 이슈에는 “어떤 버전·조건에서 무엇을 확인했으며 정상/실패/미확인인지”를 남긴다. 최신 상태 요약은 과거 실행 증거를 대신하지 않는다. [분리 저장소 예제](../examples/intent-verification/README.md)를 참고한다.

링크와 ID는 수집기·동기화·통합 UI가 아니다. 이런 연결을 사람이 유지하기 어려워지면 실제 운영 수요에 따라 별도 솔루션을 평가할 수 있지만, 이 후보에는 connector나 QA 운영 제품이 없다.

## 세션을 잊었거나 절차를 늦게 적용했을 때

[impact](../skills/spec-it-impact/SKILL.md)는 현재 소스와 이전 조사 기록을 대조한다. commit뿐 아니라 dirty 상태와 디자인/기획 revision도 확인하고, 바뀐 helper의 미변경 소비자를 살핀다. 조사 시각·관계 근거·미접근·재검토 trigger를 남기면 다음 세션이 메모리 없이도 재조회할 수 있다. 기록이 없으면 현재 확인 가능한 기준부터 시작하고 과거 상태를 꾸미지 않는다.

정책 미채택은 shadow assessment, 구현 뒤 적용은 late-entry로 구별한다. 이미 한 작업과 누락된 사전 증거를 보존하고 사후 재현·회귀를 준비한다. 읽기 전용 조사와 승인된 기록 저장/정책 투영/수정은 다른 권한이다. 상시 watcher가 없으므로 접근하지 못한 원격 변경과 마지막 조사 후 변경은 자동으로 안다고 주장할 수 없다.

## 채택과 검증 한계

선택 템플릿: [change spec](../templates/project/change-spec.md), [impact](../templates/project/change-impact.md), [case](../templates/testing/acceptance-case.md), [run](../templates/testing/verification-run.md). 실제 필드와 저장 위치는 프로젝트의 승인 범위에 맞춰 축약한다. 이 파일들이 없다는 것만으로 정책 위반이 되지 않는다.

되읽기·인계 instruction의 준수 여부는 실제 응답과 결과로 확인한다. 명시적인 검토 요청의 합성 실행은 평소 구현 요청에서 자동으로 스킬이 선택되는지, 실환경에서 모든 경로를 찾는지, 다른 모델에서도 재현되는지를 보장하지 않는다. 독립 검증자는 구현자의 결론만 받지 않고 사람 소유의 원문·수용 기준에서 출발한다.
