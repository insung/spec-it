# 분리된 구현·QA 기록 예제

합성 설명이며 실제 실행 결과가 아니다. 아래 `met/unmet`은 가상 run 상태다. [의도와 검증](../../docs/intent-and-verification.md)의 연결을 보여주며 도구·폴더·ID 형식을 강제하지 않는다.

상위 변경 `CHG-17`의 승인된 `plan@3`은 유형 A/B의 새 선택에서 제외 항목이 나오지 않는 것을 요구한다. 기획의 원본, 디자인 `node-4@8`, 구현 repo-A, QA repo-B는 각각 유지한다.

| 연결 | 합성 기록 |
| --- | --- |
| 의도·시나리오 | S-17: 저장 이후 새 선택에서 제외 항목 미선택; 비제외 항목은 유지 |
| 적용 경로 | A → 설정 → 필터 → 선택: applies; B → 선택: applies이지만 설정/필터 누락 |
| CASE-17@1 | A/B 각각 제외·비제외 결과; plan@3/node-4@8을 기준으로 고정 |
| RUN-1 | repo-A@a1, repo-B@b1/suite@1, 격리 env-E/config@1/fixture@1; DB 변경 N/A(메모리 fixture). 저장은 met, B 선택은 unmet, 결함 D-1 |
| 수정과 RUN-2 | repo-A@a2, 동일 case/QA/환경; B 경로 수정과 비대상 회귀 관찰이 met이라는 가상 기록. RUN-1은 유지 |
| 이후 plan@4 | 계정 공통 적용으로 승인 변경; CASE-17@2에 계정 경계 추가. RUN-2의 당시 met은 유지하되 새 기대에 대해서는 재검증 필요 |
| 미접근 RUN-3 | 링크만 있고 결과를 읽지 못했으므로 unknown. 최신 통과로 표시하지 않음 |

예시 완료 코멘트: “RUN-2에서 a2/b1·suite1·env-E를 기준으로 A/B 제외와 비제외 회귀를 확인했다는 합성 예시다. plan@4의 계정 격리는 미검증이며 RUN-3을 확인해야 한다.” 실제 업무에서는 원본 증거와 확인자가 있는 관찰만 이처럼 보고한다.

## 누락된 관계를 발견하는 예

확인 시각은 합성 `2026-01-02T09:00:00Z`, 조사 기준은 app-c2/dirty-d2라고 하자. shared helper가 바뀌었지만 B caller 파일은 변경되지 않았다. diff 목록만 읽으면 B를 놓치므로 helper의 호출 관계에서 B를 찾아 결과 시나리오에 연결한다. 원격 C는 접근 불가이므로 적용 여부 unknown과 조사 담당을 남긴다.

다음 세션은 app revision/dirty, plan/design revision, 새 caller/config/계약 또는 C 접근 권한이 바뀌면 관련 결론과 run 사용 가능 여부를 재검토한다. 마지막 확인 이후 원격 상태는 모른다. 문서 허브가 없어도 이 조사 결과를 기존 변경 이슈에 기록할 수 있다.

기획/디자인 충돌은 결정자에게, 승인 조건과 다른 로직은 구현 수정으로, 특정 fixture에서만 발생한 실패는 데이터/환경 조사로 인계한다. 사례 하나를 근거로 모든 프로젝트의 자동 강제를 추가하지 않는다.
