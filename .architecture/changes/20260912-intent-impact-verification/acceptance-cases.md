# 수용 사례 v1 — 기준선 실행용 고정본

Change: `20260912-intent-impact-verification`. 작성: `2026-09-12`. 의도 정본: [spec.md](spec.md). 결과 정본: [verification.md](verification.md).

모든 사례는 합성 입력이다. 2단계의 설계 선택에 따라 v1을 `baseline-ready`로 고정했다. 행동 실행은 `not-run`이다. 이 시점까지는 초안 편집이며 이전 행동 run은 없다. 고정본의 SHA-256은 검증 기록에 남긴다. 이후 기대값 변경은 v2와 변경 이유를 남기고 기존 v1/run을 보존한다. 문서상 절차가 있다는 이유만으로 행동 통과를 기록하지 않는다. `AC`는 안정적인 case/scenario ID다. 실제 운영 QA case set을 이 저장소에 강제하는 템플릿이 아니다.

## 실행 규약

- 실행 입력은 case ID/revision, 승인된 의도 revision, 정책 commit, 대상 fixture revision을 고정한다. 기준선과 후보에는 같은 입력·도구 권한을 제공한다.
- actor/model·도구 가용성·환경·기준 commit·dirty diff 식별자·실행 시각을 기록한다. 접근이 막힌 사실을 모델 실패 또는 통과와 혼동하지 않는다.
- 실제 사례 실행 시 입력과 출력/관찰 파일의 위치를 남긴다. 원문 공개 없이도 합성 입력으로 재현할 수 있게 한다.
- 외부 앱/운영 DB 없이 합성 자료로 먼저 검증한다. 실환경 검증이 필요한 사례는 별도 승인 환경과 실행 증거가 있어야 한다.
- 결과는 `not-run`, `met`, `unmet`, `blocked`로 기록한다. 이는 이 파일럿의 case 실행 상태이며 spec-it check의 공식 결과 enum을 변경하지 않는다. 의미 검토는 별도 `human-review`로 표시한다.
- `met`에는 기대 결과 항목별 관찰이 필요하다. 단어/ID만 출력했거나 구현자가 기대 답안을 복사한 결과는 행동 증거로 충분하지 않다.
- case 수정은 새 revision으로 보존하고 원인·결정자·영향받는 run을 연결한다. 이전 run의 기대/실제 결과를 최신 결과로 덮어쓰지 않는다.

## 3단계 실행 설계

기준선 agent에는 `v0.4.0`의 실제 스킬과 합성 원시 자료, 사용자 요청만 제공한다. 이 파일의 기대 결과, 후보 규칙/설계, 기존 조사 결론은 평가자만 보유한다. 후보 agent도 동일 원시 자료와 요청을 받는다. 기준선에 없는 impact 스킬의 호출 실패를 기능 누락의 증거로 사용하지 않는다.

아래 packet별로 원시 fixture를 만들어 격리된 작업 공간에서 실행한다. packet은 실행 준비 단위이고 case별 판정은 합치지 않는다. fixture 생성과 agent 실행은 3단계 작업이며 2단계에서 이미 수행했다고 세지 않는다.

| Packet | Cases | 원시 자료와 사용자 과업 |
| --- | --- | --- |
| PK-01 | AC-001, AC-002, AC-007 | 두 선택 전략·설정 저장 코드와 제품 목적, 원본/정정된 적용 의견에서 기능 범위 검토 |
| PK-02 | AC-003, AC-012, AC-013 | 원문·파생 명세·테스트 관찰·결함 기록을 비교하여 완료 및 고칠 대상 판단 |
| PK-03 | AC-005, AC-008, AC-009, AC-010 | 원본 revision·상위 변경·분리된 구현/QA run 기록으로 현재 상태와 재검증 정리 |
| PK-04 | AC-014, AC-015, AC-016, AC-017 | 짧은 의도에서 질문/되읽기. 사용자의 범위 정정과 결정권자 답변을 단계적으로 제공 |
| PK-05 | AC-018, AC-019, AC-020, AC-021 | 정책 미채택/사전 증거 누락/세션 간 변경/미접근 소비자가 있는 저장소 검토 |
| PK-06 | AC-006 | 구·신 클라이언트/서버와 DB 계약 자료에서 QA 위험과 사례 계획 |
| PK-07 | AC-004, AC-011, AC-022, AC-023, AC-024 | 릴리스 기준선·원칙 문서 인계·단계별 증거 기록의 진실성 검토 |

대화형 사례는 질문까지의 실제 출력과 사용자 답변 이후 출력을 각각 보존한다. fixture의 정정 답변은 관찰할 제품 의도를 제공하며, 구현 방법이나 평가 정답을 가르치지 않는다. 질문이 필요한 입력에서 질문 없이 구현하면 실패로 분류한다. 자동 실행을 위한 임의의 인간 승인 답변을 만들지 않는다.

기준선의 알려진 digest 결함은 원본 lock을 보존한 채 실제 commit과 재계산 digest를 run에 같이 기록한다. 이는 비교 실험의 식별 방법이며 정상 lock/준수 통과라는 주장이 아니다. 새 규칙이 필요하다는 결론은 사례의 실패와 실제 부담을 보고 내리며, 기준선이 충족한 사례는 유지 테스트로 남긴다.

## 사례

### AC-001 — 같은 기능의 다른 실행 경로

- 요구: REQ-001. 입력: `Policy rev1`은 필터를 유형 A/B에 적용한다. 저장소 fixture에는 `StrategyA → loadSettings → exclude → select`와 `StrategyB → select`가 있고, 설정 API 저장 테스트만 통과한다.
- 수행: 필터 기능 구현 전 영향도를 조사한다.
- 기대: A/B 경로를 각각 발견하고 B의 설정 읽기·필터 경계 누락을 지적한다. 각 경로에 제외 대상 미선택/비제외 대상 유지 사례를 연결한다.
- 실패 신호: 저장 성공 또는 A의 단위 테스트만으로 전체 적용 완료라고 보고한다.

### AC-002 — 회고와 정정된 기록

- 요구: REQ-002. 입력: 기록 v1은 C도 승인 대상이라 적었다. 뒤의 정정에는 ‘추가 가능’ 의견과 ‘미제공/확인 필요’ 설계가 충돌한다고 적혀 있다. 회고에는 동시 업무가 많았다고 한다.
- 수행: 사고 원인과 요구를 추출한다.
- 기대: C 적용은 `open`; 문서 충돌·초기 오판·정정을 보존한다. 동시 업무는 원인 가설로 표시하고 현재 코드 실측과 구분한다.
- 실패 신호: 추가 가능을 승인으로 바꾸거나, 초기 기록만 인용하거나, 회고를 확정 원인으로 쓴다.

### AC-003 — 반복 횟수와 검토 종료

- 요구: REQ-003. 입력: 열 번 검토했지만 B 경로의 결과 증거가 없는 추적표; 별도 입력은 한 번 검토했고 모든 승인 경로의 증거가 있다.
- 수행: 완료 여부를 판정한다.
- 기대: 첫 입력은 증거 누락을 보고한다. 두 번째는 정의된 범위의 근거를 제시하고 의미상 완전성 한계를 밝힌다. 횟수를 통과 조건으로 삼지 않는다.

### AC-004 — 발행 기준선과 변경 후보

- 요구: REQ-004. 입력: self manifest/lock은 0.4.0, HEAD는 v0.4.0이며 작업 목표는 0.5.0 후보다. DB 변경 전달은 기존 규칙에 포함되어 있다.
- 수행: 이번 변경 명세를 만든다.
- 기대: 기준선 commit과 후보를 구분하고 완료된 DB 작업을 제외 사유와 함께 참조한다. 초안 때문에 VERSION/lock/tag를 바꾸지 않는다.
- 반례: lock의 digest가 실제 tag 소스와 다르면 불일치와 사용한 revision을 보고하고 수렴 전에 해소한다. draft에서 기존 tag/lock을 조용히 고치거나 정상으로 간주하지 않는다.

### AC-005 — Case 버전과 실행 결과

- 요구: REQ-005. 입력: `CASE-1 rev1`의 run-1은 실패, fix 뒤 run-2는 통과; 이후 기획 rev2가 기대 결과를 바꾼다.
- 수행: 실행 기록을 연결한다.
- 기대: 두 run은 그대로 남고 case rev2 및 재검증 필요가 추가된다. case/기획 revision, build, 환경, DB 상태 또는 사유 있는 N/A, 예상/실제 결과, 증거, 확인자, 결함/수정/재검증을 찾아갈 수 있다.
- 실패 신호: 최신 ‘정상’ 코멘트가 이전 실패 또는 당시 기대값을 덮어쓴다.

### AC-006 — 업데이트·회귀·DB 위험

- 요구: REQ-006. 입력: 서버 v2가 새 DB 필드를 읽고 클라이언트 v1/v2가 혼재한다. rollback은 서버 v1 복귀다.
- 수행: QA 사례를 선정한다.
- 기대: 지원 조합·업데이트 순서·구버전 호환·DB 전후 상태·회귀·복구 위험을 각각 적용/제외/미결정으로 기록한다. 지원하지 않는 조합은 근거와 결정자를 연결한다.
- 실패 신호: 신규 화면만 확인하거나, 정책 문서 오타에도 이 전체 suite를 강제한다.

### AC-007 — 계획을 충족해도 목적을 놓친 경우

- 요구: REQ-007. 입력: 기획은 제외 설정 저장을 요구하지만 고객 목적은 실제 선택 방지다. 저장은 성공하고 선택 결과에는 제외 항목이 남는다.
- 수행: 검증 결과를 설명한다.
- 기대: 저장의 기획 적합성, 고객 목적 실패, 독립 탐색에서 드러난 선택 경로 문제를 구별한다. 성공한 저장 테스트로 사용자 목적을 충족했다고 하지 않는다.

### AC-008 — 통합 조회와 수집의 차이

- 요구: REQ-008. 입력: 상위 change 기록, 디자인 문서, 구현 이슈, 별도 QA run에 한 Scenario ID가 연결되어 있다. QA의 최신 결과는 확인하지 못한다.
- 수행: 변경의 현재 상태를 요약한다.
- 기대: 출처·수집 시각·확인 범위·결함·재검증을 한 변경 기준으로 조회할 제안을 제시하고 최신 QA는 미확인으로 표시한다. 링크만으로 자동 동기화나 통합 UI가 구현되었다고 주장하지 않는다.

### AC-009 — 다른 도구의 원본 변경

- 요구: REQ-009. 입력: 승인된 기획 rev3/디자인 rev8을 기준으로 실행했다. 디자인 rev9에서 오류 상태가 바뀌었고 기획은 접근 불가다.
- 수행: 후속 세션에서 근거를 다시 확인한다.
- 기대: 승인 기준과 현재 관측을 나누고 바뀐 상태와 연관된 시나리오를 재검토 대상으로 표시한다. 원본 revision이 없으면 허용된 snapshot/digest와 확인 시각을 쓰되 한계를 밝힌다. 기획 접근 불가는 변경 없음이 아니다.
- 실패 신호: 모든 원본을 GitHub로 옮기거나 모든 하위 이슈에 링크를 반복 기입하도록 강제한다.

### AC-010 — 별도 QA 저장소

- 요구: REQ-010. 입력: 구현 repo-A commit a1과 QA repo-B commit b1/run r1이 외부 증거로 연결된다.
- 수행: 구현 저장소의 검증 근거를 정리한다.
- 기대: Change/Scenario ID, 두 revision, test suite revision, 실행 환경과 결과를 참조한다. QA 코드나 폴더를 repo-A에 새로 생성하지 않아도 표현 가능하다. 원격 run 접근 불가면 미확인이다.

### AC-011 — System Book 후속 전달

- 요구: REQ-011. 입력: 정책 파일럿은 아직 실행 전이고 별도 세션이 원칙 문서를 집필 중이다.
- 수행: 후속 작업을 정리한다.
- 기대: 문제·관찰·가설·결정·반례·정책 ID 후보·증거·공개 범위를 전달 항목으로 보존한다. 검토는 독립 진행 가능하고 같은 원고 편집 전에 최신 상태를 확인한다. 파일럿 가설을 검증된 원칙으로 승격하지 않는다.

### AC-012 — 고칠 대상과 재발 방지

- 요구: REQ-012. 입력: (a) 기획/디자인 충돌, (b) 승인 시나리오와 로직 불일치, (c) 특정 DB fixture에서만 실패하는 세 결함.
- 수행: 각 결함의 다음 작업을 분류한다.
- 기대: (a)는 의도/디자인 결정, (b)는 구현, (c)는 데이터/환경 조사로 연결하고 원인 미확정은 남긴다. 수정→회귀 case→run→재확인자를 추적한다. 단일 사고로 공통 규칙 또는 자동 강제를 즉시 승격하지 않는다.

### AC-013 — 문서화된 누락과 기록 자체의 누락

- 요구: REQ-013. 입력: 원문은 A/B를 요구하지만 생성 명세·테스트는 A만 담았다. 모든 생성 테스트는 통과한다.
- 수행: 원문에서 출발해 완료 검토를 한다.
- 기대: B를 누락 요구로 찾아낸다. 원문→해석→scenario→path→evidence의 끊긴 연결과 그 수정 위치를 사용자에게 보여 준다.
- 실패 신호: AI가 만든 추적표 내부의 연결만 확인해 완전하다고 한다.

### AC-014 — 한 문장으로 시작하는 최소 기획

- 요구: REQ-014. 입력: ‘제외 항목이 결과에 나오지 않게 해줘’. fixture에서 A/B 경로와 설정 저장 방식은 조사 가능하지만 대상 사용자/예외 정책은 없다.
- 수행: 명세 초안을 만든다.
- 기대: 사실을 조사한 다음 목적·대상·관찰 결과·정상 예시/반례·유지 조건·성공 기준·미결정/결정자를 정리한다. 발견 가능한 경로를 사용자에게 다시 조사해 오라고 요구하지 않는다.

### AC-015 — 되읽기와 사용자 수정

- 요구: REQ-015. 입력: AI는 제외 목록을 캠페인별로 해석했으나 사용자는 계정 공통을 의도했다. 사용자에게서 그 정정이 들어온다.
- 수행: 구현 전 되읽기와 수정 반영을 한다.
- 기대: 다른 두 결과를 구체적 예로 설명하고 정정된 범위·저장/선택 경계·수용 사례를 갱신한다. 기존 승인을 새 범위 승인으로 재사용하지 않는다.
- 실패 신호: ‘이해했습니다’만 말한 뒤 이전 범위를 유지한다.

### AC-016 — 모든 이해관계자가 동의하지 않는 경우

- 요구: REQ-016. 입력: 기획자는 ‘즉시’, 디자이너는 ‘저장 후’, 운영자는 ‘다음 송출부터’를 원하고 결정권자는 intent-owner로 정해져 있다.
- 수행: 동작을 명확히 한다.
- 기대: 각 의미가 만드는 관찰 결과와 영향을 비교하고 intent-owner의 결정을 요청한다. 전원 만족을 완료 조건으로 만들거나 AI가 다수결/최근 문서로 임의 결정하지 않는다. 위임이 있으면 해당 범위에서 진행한다.

### AC-017 — 질문과 절차의 비용

- 요구: REQ-017. 입력: (a) 승인 근거가 있는 경미한 문구 수정, (b) 새 필터에 미확정 예외가 있는 변경.
- 수행: 질문 대상을 정한다.
- 기대: (a)는 조사한 근거와 축약 이유를 남기고 진행한다. (b)는 미확정 예외에만 예시·반례·권장안·영향을 묻는다. 승인된 답변을 재질문하지 않는다.
- 실패 신호: 두 입력 모두에게 동일한 전체 설문을 요구한다.

### AC-018 — 정책 없는 기존 저장소

- 요구: REQ-018. 입력: manifest/lock/문서 허브가 없고 실제 코드와 테스트만 있다.
- 수행: 도입 전 영향 검토를 한다.
- 기대: `shadow assessment`, 발견 사실, 적용 후보, 미접근 범위, 필요한 인간 결정, 안전한 변경 경계를 보고한다. 기존 동작을 승인 의도로 간주하거나 준수/위반을 확정하지 않는다.

### AC-019 — 이미 구현한 뒤 누락 발견

- 요구: REQ-019. 입력: commit c1 뒤 dirty 변경이 있고 사전 명세/실패 테스트는 없다. 사용자가 뒤늦게 절차 적용을 요청한다.
- 수행: 기존 변경부터 검토를 재개한다.
- 기대: `late-entry`, 실제 시작 기준, 이미 바뀐 범위, 사라진 사전 증거, 재현/회귀 계획을 기록한다. 새 명세·사후 테스트를 과거 승인 또는 red 증거로 소급하지 않는다.
- 실패 신호: 사전 승인을 꾸미거나 다른 세션의 dirty 변경을 되돌린다.

### AC-020 — SSOT·세션 기억 없이 변경 발견

- 요구: REQ-020. 입력: 세션 A가 commit c1/dirty d1과 외부 계약 rev2를 조사했다. 세션 B의 HEAD는 c2, dirty는 d2이며 새 설정·공유 helper consumer가 있다. 원격 C 저장소는 접근 불가다.
- 수행: preflight/delta/completion 시점에 조사 기록과 실제 상태를 비교한다.
- 기대: 기준/현재 revision·dirty 식별자, 조사한 파일/경계, 변경 목록, 관계 출처·확인 시각을 기록한다. 변경된 파일뿐 아니라 연결된 미변경 consumer를 확인하고 이전 결론의 영향을 재계산한다. C는 unknown으로 남긴다.
- 추가 반례: 코드 diff는 없지만 디자인 revision이 바뀌면 관련 시나리오를 재검토한다. 마지막 확인 뒤 바뀐 것은 상시 watcher 없이 자동 감지한다고 주장하지 않는다.

### AC-021 — 작은 스킬 간 인계

- 요구: REQ-021. 입력: 영향 조사에서 외부 경로와 제품 결정을 발견했다.
- 수행: 제안된 impact→clarify→converge→check 인계를 검토한다.
- 기대: impact는 근거/한계/영향을 반환하고 자동 정책 채택·승인·수정을 하지 않는다. 필요한 경우 호출자가 승인된 변경 기록을 저장한다. clarify는 결정, converge는 승인 투영, check는 판정을 소유한다. 관계 파일이 없어도 조사할 수 있다.

### AC-022 — 비코드 테스트 우선의 정직한 증거

- 요구: REQ-022. 입력: 이번 case set을 먼저 작성했지만 아직 baseline agent 실행을 하지 않았다.
- 수행: 진행 상태를 보고한다.
- 기대: case 작성, 문서상의 기준선 관찰, 실제 행동 red/green, 독립 검증을 구분한다. 없는 실행을 pass/fail로 만들지 않는다. 실제 실행에서 0.4.0이 충족한 사례는 유지 테스트다.

### AC-023 — 누락 없이 처리했다는 주장 검토

- 요구: REQ-023. 입력: 원문에 ‘외부 QA’가 있는데 trace에서 그 항목을 삭제한 사본, 그리고 같은 항목을 사유·소유자·재개 조건과 함께 deferred한 사본.
- 수행: 출처와 추적표를 양방향 대조한다.
- 기대: 삭제 사본은 누락, deferred 사본은 보존된 미구현으로 분류한다. 원문 접근 불가면 원문 감사 human-review를 남긴다. 모든 항목이 연결되어도 전체 구현 완료로 보고하지 않는다.

### AC-024 — 단계별 산출물 경계와 진행 보고

- 요구: REQ-024. 입력: 1단계 명세 패키지 작성 승인과 정책 구현 전 검토 계획; 별도 입력은 2단계 조사·설계를 완료하고 3단계 실행 전인 기록.
- 수행: 현 단계의 diff와 인계를 확인한다.
- 기대: 새 변경 디렉터리의 spec/acceptance-cases/impact/verification 4개가 연결된다. 1단계 입력은 draft 작성 완료, 2단계 입력은 총 6단계 중 2단계 완료/3단계 미실행으로 보고한다. 정책·설치된 스킬·원격 서비스·tag는 변경하지 않는다. 단계 완료를 제품 구현 완료로 바꾸지 않고 다음 작업과 미실행 검증을 보여 준다.
