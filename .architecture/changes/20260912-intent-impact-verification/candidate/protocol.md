# 5단계 실행 규약 — 후보 CAND-STAGE4-20260913-01

상태: 실행 전 고정. 기존 24개 수용 사례 v1과 baseline 입력 9개의 bytes를 그대로 사용한다. PK-04는 첫 요청과 미리 고정된 사용자 답변의 두 차례 대화다. 7개 수행 문맥에서 8개 응답을 받고 각 사례별로 판정한다. 독립 의미 검토는 수행 응답과 구별한다.

## 입력·소스·권한

- 후보 전체 source: [4단계 snapshot](../implementation-snapshot.json), tree SHA-256 `8508df644e996e4f0f7d8916876acc18f721fe3785835e33f5bc46f61edbd0a5`, 221개 파일. 발행 버전이 아니다.
- 기대값: [고정 사례 v1](../acceptance-cases.md). 수행자는 이 파일과 부모의 판정/구현 근거를 보지 않는다.
- 원시 입력: baseline/inputs를 복사하되 변경하지 않는다. PK-05는 동일한 6개 app 파일도 제공한다.
- PK-07이 요청하는 release 점검 대상은 별도 v0.4.0 export 213개 파일이다. 후보 스킬은 source/skills에서 읽고, 평가 대상 release는 released-source에서 읽는다. raw 입력의 ‘v0.4.0 export’를 후보 source로 바꿔 해석하지 않는다.
- 수행자마다 새 문맥(fork none), 기본 상속 모델·override 없음. 정확한 serving ID/파라미터는 확인 가능한 범위만 기록한다. 제공된 파일과 해당 source의 관련 skill/rule/template만 읽는다. 다른 packet, 부모 workspace·대화·기억, 네트워크는 접근하지 않는다.
- 허용 출력은 해당 임시 response 파일뿐이다. 정책·프로젝트·원고·서비스·설치 경로는 수정하지 않는다. 실제 적용한 읽기/쓰기 범위는 결과와 사후 file hash로 확인한다. 이는 instruction-scoped 경계이며 OS 수준 격리 보장이 아니다.

## 비교의 한계와 기록

baseline과 같은 원시 입력을 사용하지만 바깥 실행 안내는 여기서 재구성한다. baseline 안내 전체의 byte 동일성을 주장하지 않는다. PK-07의 release/source 분리는 후보와 검토 대상을 구별하기 위한 경로 안내다. 입력 자체나 기대 결과를 바꾸는 것이 아니다.

스킬 없는 대조군, 다중 모델 반복, 실환경 QA, 자동 스킬 활성화 검증은 이번 24개 비교에 포함하지 않는다. single-run 합성 응답의 수용 판정이며 일반 성공률로 표현하지 않는다. 후보 판정은 기존 판정을 덮어쓰지 않고 새 run으로 남긴다. 실험 중 스킬을 고치면 기존 source/응답을 유지하고 새 후보 ID 및 재실행 근거가 필요하다.

## 종료 조건

1. 동결 입력·기준선·후보 source 동일성 확인.
2. 7개 과업의 8개 원본 응답을 보존하고 24개 기대 결과에 대한 관찰을 기록. 실패/미실행도 숨기지 않음.
3. 독립 검토자가 사람의 의도와 source·사례·관찰의 연결, 권한/범위와 부작용을 검토. 접근 가능한 사용자 원문만 감사하고 미접근 부분은 human-review.
4. 발견 사항을 근거와 함께 처리하거나 후속 조건으로 남기고, 실행 결과·구조 검사·릴리스 미완료를 분리하여 보고.

## 착수 시 발견한 실제 경계

기존 5개 설치 경로가 이 저장소 스킬 폴더를 가리키는 symlink임을 5단계 시작 시 확인했다. 따라서 4단계에서 설치 명령·링크 자체는 변경하지 않았지만 **링크로 읽는 기존 스킬 내용은 후보로 바뀌었다**. ‘설치된 스킬 변경 없음’이라는 이전 설명은 이 의미에서 정정한다. 새 impact의 전역 설치는 확인되지 않았으며 자동 설치하지 않는다. 평가 source는 이 설치 경로가 아닌 위 임시 고정본이다. live symlink는 발행 버전 고정 수단이 아니라는 부작용을 최종 검토에 포함한다.

## 독립 검토 뒤 후보 정정

첫 후보의 독립 의미 검토에서 정책 규칙 밖 advisory 관찰을 지속 기록하라는 지침과 기존 check-report schema의 `rule_id` 필수 계약이 충돌하는 IV-01이 발견됐다. 첫 후보·응답·감사 결과는 보존한다. `skills/spec-it-check/SKILL.md` 한 파일만 고쳐 정책 JSON과 호출자 소유 변경/issue/handoff 기록을 분리하고, 임의 규칙 ID·schema 밖 필드·기본 QA 디렉터리 생성을 금지했다.

중간 정정 후보 `CAND-STAGE5-20260915-02`는 첫 후보 대비 source 220개가 동일하고 check 스킬 한 파일만 바뀌었다. check를 사용해 완료·세션 간 인계를 판단하는 PK-02/03/05를 같은 입력의 새 문맥으로 다시 실행하며 다른 packet의 첫 응답은 영향 없음 근거와 함께 유지했다. 그 뒤 독립 의미 감사를 새 후보에 다시 수행했다. 이는 기대값을 바꾼 것이 아니라 감사 finding을 수정하고 선택적으로 회귀 검증한 절차다.

두 번째 독립 감사에서는 `spec-it-clarify`가 승인·위임된 선택을 재질문하지 말라고 하면서 종료 문구에서 무조건 확인 대기로 표현하던 F-1을 발견했다. 이를 실제 승인 상태를 보고하도록 정정한 중간 후보는 `CAND-STAGE5-20260915-03`이며, 4단계 후보에서 달라진 파일은 check와 clarify 두 개였다. PK-04 두 턴을 새 문맥에서 다시 실행하고, F-1과 IV-01의 해소 및 새 중대 누락 여부를 독립 재검토했다.

후보 3의 PK-04 재실행은 사용자가 범위·시점·예외를 확정한 뒤에도 관찰 근거 없는 동시 편집을 새 material-open으로 만들었다. 이 응답은 실패 회귀 증거로 보존한다. `spec-it-clarify`에 관찰된 요구나 기술 trigger가 없는 가상의 actor/concurrency/consumer/failure/integration을 제품 결정으로 승격하지 않는 guard를 추가한 최종 후보는 `CAND-STAGE5-20260915-04`다. 같은 두 턴과 이 guard의 독립 정적 감사를 다시 수행한다.
