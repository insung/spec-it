# CHG-17 현재 상태와 QA 기록안

CHG-17은 **이전 기획 기준의 결함 수정·재검증 통과는 기록되어 있으나, 승인된 기획 변경 이후의 완료 여부는 확인할 수 없는 상태**입니다. 종합 검토 상태는 `human-review`입니다. 아래는 제공된 snapshot을 대상으로 한 수동 검토와 기록 초안이며, 원본 도구나 저장소를 수정하거나 QA를 실행한 결과가 아닙니다.

`spec-it-check`의 quick 범위와 `spec-it-impact`의 delta 관점을 적용했습니다. 프로젝트가 채택한 manifest·lock·정책 버전은 제공되지 않았습니다. 정책 관점에서는 `shadow assessment`이며, 규칙 ID는 후보 지침에 근거한 검토 참조입니다. 채택된 정책 위반이나 준수를 확정하지 않습니다.

## 3. 기존 도구를 유지하는 QA 기록안

기획·디자인 정본은 기존 도구에, 구현은 repo-A에, 사례·suite·실행 기록은 repo-B/qa-17에 둡니다. 상위 CHG-17이 승인 기준과 상태 요약을 연결하고 dev-17·fix-17·qa-17은 기존대로 CHG-17/S-17을 참조하면 됩니다. 원본 복제나 구현 저장소로의 QA 코드 이전은 필요하지 않습니다.

상위 변경 기록에 사용할 수 있는 초안:

> CHG-17 / S-17, owner product-1. 자료 확인 기준 2026-09-12T08:10:00Z. 보존 자료의 최근 승인 기획은 plan://P17 rev4 export(decision-44, product-1, 08:05Z)이며 현재 원본 최신성은 미확인이다. 승인 디자인은 design://D17 rev8이고 관측 rev9는 승인 근거 확인이 필요하다. 최초 구현 대상은 repo-A a1, 수정·재검증 대상은 a2이며 당시 QA는 repo-B b1 / suite rev1이다. run-2는 CASE-1 rev1의 캠페인별 제외 동작에 통과했다. rev4 계정 공통 적용과 저장 실패 UI는 제공 증거로 검증 완료를 확인할 수 없다. run-3 내용·현재 환경은 미접근이다. 변경 전체의 완료 판단은 human-review다.

### 사례와 실행 이력

**CASE-1 rev1은 변경하지 않고 보존합니다.** 근거는 plan rev3/design rev8, 검증 종류는 기획 적합성, 대상은 c1의 a9 제외와 c2 유지입니다. run-1·run-2를 연결합니다. 구현자·테스트 작성자 관계와 독립 검증 세션 증거는 미제공으로 둡니다.

| Run / 공통 연결 | 고정 대상·조건 | 당시 예상 | 실제·결과 | 증거·확인자·연결 |
| --- | --- | --- | --- | --- |
| run-1 / CHG-17 / S-17 / CASE-1 rev1 | repo-A a1; repo-B b1; suite rev1; synthetic-stage-1; db-f1; plan rev3/design rev8 | c1 미선택, c2 유지 | c1에서도 선택됨; `failed`. c2 상세 실제값은 미제공 | log-1; qa-1; bug-17 → fix-17 → run-2 |
| run-2 / CHG-17 / S-17 / CASE-1 rev1 | repo-A a2; repo-B b1; suite rev1; synthetic-stage-1; db-f1; plan rev3/design rev8 | c1 미선택, c2 유지 | 실제 일치; `passed` | log-2; qa-1; fix-17(a2), bug-17 관련 재검증 |
| run-3 / qa-17 추가 링크 | case·revision·commit·suite·환경·DB 미확인 | 미확인 | 접근 불가, 결과 unknown | 링크 추가 알림만 확인. 증거·확인자·결함 연결 미확인 |

`failed/passed/unknown`은 보존된 실행 결과 또는 접근 상태이며 check enum과 구분합니다. run-1 실패를 run-2 통과로 덮어쓰지 않습니다. `bug-17 → fix-17(a2) → run-2(log-2, qa-1)` 연결은 확인되지만 bug-17 이슈가 실제로 닫혔는지는 미제공입니다. 근본 원인과 수정 diff도 미확인입니다.

run-1·run-2의 현재 사용 가능 여부에는 “plan rev3/design rev8과 해당 build·환경의 과거 관찰로 유효; plan rev4의 수용 완료 증거로는 사용 불가”를 적습니다. 실행 시각·실행자, dirty·artifact digest, 환경 설정·DB schema/migration 상태 등 미제공 항목은 unknown으로 둡니다. qa-1은 verifier이며 실행자까지 같았다고 추정하지 않습니다. log-1·log-2 원문을 열어 검증하지 않았으므로 모두 ‘제공 기록상 결과’입니다.

### 새 사례·실행 초안

| 사례 초안 | 기준·예상 관찰 | 현재 상태·필요 항목 |
| --- | --- | --- |
| CASE-1 rev2 | plan rev4 export + decision-44. 같은 계정의 c1·c2에서 a9를 제외 목록에 반영한 뒤 대상 선택에서 a9가 제외되는지 확인 | 미실행. c1·c2 계정 소속과 적용 시점 등을 명시. rev1의 c2 유지 기대를 새 revision에서 변경하고 과거 run은 유지 |
| CASE-1 rev2의 계정·비대상 경계 | 다른 계정에는 제외가 전파되지 않는지, 비제외 항목의 선택이 유지되는지 관찰하는 후보 | 미실행. 원문에서 계정 경계·유지 조건 확인 후 기대 고정. 미제공 세부 조건을 이미 승인된 사실로 추가하지 않음 |
| 오류 UI 별도 사례(새 ID는 QA 담당 지정) | 알려진 승인 design rev8에 따라 저장 실패 시 기존 값·재시도 버튼 관찰 | 미실행. rev9 승인 근거와 rev4 전체 오류 처리 조건 확인. rev9 채택 시 새 revision에 근거·변경 사유 기록 |

새 실행을 임의로 run-3이라 부르지 않습니다. run-3을 먼저 조회해 같은 범위를 이미 실행했는지 확인하고, 추가 실행이 필요하면 QA 담당이 새 ID를 부여합니다. 새 run에는 case revision, 승인 출처, 구현 commit·dirty/artifact, QA commit·suite, 환경 설정·DB fixture, 실제 관찰·증거·확인자·실행 시각을 고정합니다. 현재 환경이 미접근이므로 과거 synthetic-stage-1/db-f1을 현재 값으로 자동 채우지 않습니다.

검증 목적도 구분합니다.

- **기획 적합성:** rev4 계정 공통 적용과 승인된 오류 UI를 확인하는 사례입니다.
- **고객 목적:** 실제 선택에서 제외 의도가 달성되는지 확인합니다. run-2는 과거 캠페인별 범위의 제한적 근거이며 최신 계정 범위나 사용자 편익 전체를 입증하지 않습니다.
- **탐색 검증:** 저장 실패 후 재시도, 캠페인·계정 전환에서 상태 혼재를 조사할 수 있습니다. 제안된 가설이며 이미 실행한 테스트·확정 결함·승인된 새 요구가 아닙니다.

## 4. 다음 담당자의 처리 순서

1. product-1 또는 원본 접근 가능한 담당자가 plan://P17 현재 revision과 decision-44 이후 승인 기록을 확인합니다. rev4 승인 사실을 유지하고 이후 바뀐 범위만 확인합니다. CHG-17의 최신 승인 요약을 갱신할 근거를 준비합니다.
2. 디자인 담당은 rev9 승인 근거를 찾습니다. 없으면 product-1의 남은 결정은 rev8 유지 또는 rev9 채택입니다. 현재 근거로는 rev8 유지가 권고입니다. rev9는 실패 후 값·버튼·복구 동작을 바꾸므로 사용자 혼동과 재시도 경로 변경 위험을 검토해야 합니다. 결정에 따라 디자인·사례 기대값·필요한 구현 범위가 달라집니다. 현재 수정한 것이 없어 되돌릴 변경은 없으며, 향후 rev9 채택을 철회한다면 rev8 기준 복구·회귀 확인이 필요합니다.
3. QA 담당(기존 verifier qa-1과 연계하되 배정은 별도 확인)은 qa-17/run-3에서 case·출처·build·환경·결과·증거를 확인합니다. 접근 회복 전에는 최신 통과를 표기하지 않습니다.
4. 구현 담당은 a2 이후 HEAD·dirty·artifact와 계정 공통 설정의 저장·조회·선택 경로, 미변경 소비자를 조사합니다. 승인 조건과 다른 실제 관찰이 나오면 계약·코드·데이터·환경 중 원인을 조사하고 결함/수정/재실행을 연결합니다.
5. QA 담당은 최신 확정 수용 기준으로 필요한 case revision과 run을 연결·실행합니다. CHG-17에는 어떤 버전·조건에서 무엇을 확인했는지와 남은 범위를 요약합니다. 사례 작성이나 링크 추가만으로 완료 처리하지 않습니다.

재검토 조건은 새 세션에서 재개할 때, 기획·디자인 승인/revision 변경 시, repo-A·repo-B HEAD/dirty/artifact 변경 시, suite·환경·DB fixture 변경 시, run-3 접근 회복 시, 새 caller·필드·계약·소비자 발견 시입니다. 해당 위치와 관련 사례·run을 다시 대조하고 과거 결과와 현재 유효성을 분리합니다.

이 연결은 수동 인계 방식입니다. 자동 동기화 서비스나 통합 화면은 설치되어 있지 않으며, ID와 링크만으로 원격 변경 감지·상태 수집·QA 실행·자동 정책 검증이 생기지 않습니다. 후보 지침의 TST-003/TST-006 자동 실행도 planned/미구현이고 이번 검토는 수동입니다. check의 의미상 종료 분류는 증거·사람 결정이 남은 `2`에 해당하지만 실제 checker나 프로세스가 낸 종료 코드가 아닙니다.
