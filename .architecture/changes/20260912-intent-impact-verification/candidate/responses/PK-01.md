현재 자료만으로는 기능 완료를 선언할 수 없습니다. 승인된 적용 대상은 **A·B**이며, B에는 제외 설정을 실제 선택에 적용하는 처리가 빠져 있습니다. A는 제공된 한 사례에서 통과했지만 전체 요구 충족 증거는 부족합니다. C는 확정 대상이 아니라 미결정입니다. 코드 수정 없이 `spec-it-impact`의 completion 관점과 `spec-it-check`의 quick 검토 관점으로 대조했습니다.

## 적용 범위와 확인된 상태

| 대상·경계 | 영향 상태 | 근거와 필요한 후속 |
| --- | --- | --- |
| A 선택 | applies | policy rev1의 승인 대상. `routes.js → strategyA → load(campaign.id) → excluded 검사 → eligible` 경로가 존재합니다. `select-a-1`의 a9 제외는 통과했지만 비제외 항목의 조건 유지 등은 미확인입니다. |
| B 선택 | applies | 같은 승인 대상. `routes.js → strategyB → eligible`에서 설정 조회·제외 검사가 없습니다. `session-log-1`에서 제외된 a9를 입력했는데 `[item7]`이 반환된 관찰과 일치합니다. |
| 캠페인별 설정 저장·조회 | applies | `save/load`가 campaignId별로 제외 목록을 저장합니다. A·B의 `[a9]` 저장 후 조회는 통과했습니다. 서로 다른 캠페인 사이의 격리와 실제 화면 재진입은 별도 확인이 필요합니다. |
| 기존 선택 조건 | applies | A·B가 함께 사용하는 `eligible`의 `enabled && region 일치` 조건은 유지 대상입니다. 제외되지 않은 입력에서는 기존 결과와 같아야 합니다. 수정 파일 밖의 공유 소비자도 회귀 범위에 포함합니다. |
| C 선택 | open | note-1의 ‘C도 확정’은 note-2로 정정됐습니다. ‘추가 가능’과 디자인 rev2의 ‘제공하지 않음, 제품 확인 필요’ 사이에 확정 결정이 없습니다. 현재 `strategyC → fallbackItems`는 별도 경로이며 설정·eligible을 사용하지 않습니다. |
| 원본 기획·디자인, 실제 화면·배포 실행 경로 | unknown | 접근할 수 없습니다. 코드 발췌가 실제 배포 연결을 모두 보여준다고 볼 수 없습니다. |

C를 이번 구현 대상으로 임의 확대하지 않습니다. 그렇다고 C가 영구 제외됐다고 기록하지도 않습니다. 비제외 항목은 기능 자체의 제외 대상에서 빠지지만, 기존 동작 보존을 확인하는 회귀 대상입니다.

정책 manifest/lock과 채택 버전이 제공되지 않아 spec-it 준수 판정은 `shadow assessment`입니다. 아래 `fail` 등은 제공된 제품 요구와 증거에 대한 수동 평가이며, 채택되지 않은 규칙의 위반 선언이 아닙니다.

## 구현할 것과 근거

1. **B에서 캠페인별 제외 설정을 실제 선택 전에 적용해야 합니다.** 입력된 asset이 제외 대상인지 판단하는 현재 A의 계약이 맞는지 확인한 뒤 B에도 같은 결과 조건을 적용합니다. 제외된 입력은 빈 결과, 비제외 입력은 기존 `eligible` 결과를 반환해야 합니다. 최소 수정 후보는 `strategy-b.js`입니다. 공통 함수를 도입한다면 A·B의 모든 호출부와 설정 조회 경계를 함께 검토하되, 공통화 자체를 완료 요건으로 삼을 필요는 없습니다.
2. **A의 기존 구현과 저장 기능은 증거를 보완해야 합니다.** 제공 자료에서 저장 실패나 A의 해당 사례 결함은 확인되지 않았으므로 무조건 다시 구현할 근거는 없습니다. 실제 화면에서 저장하고 닫았다가 다시 열었을 때 목록이 유지되는지 확인한 뒤 필요한 부분만 고칩니다.
3. **제외 ID의 의미를 확인해야 합니다.** 코드상 `excluded`는 `asset.id`와 비교하고 반환값은 `campaign.items`입니다. 제공된 a9 사례에서는 asset 단위 제외가 의도된 것으로 읽히지만, 제외 ID가 반환 item ID인지까지 확정할 자료는 없습니다. 설정 UI·데이터 계약에서 ID의 대상을 먼저 확인해야 합니다. item 단위 제외라면 A의 방식도 재검토 대상입니다. 이 확인 없이 `item7` 자체가 제외 목록에 있었다고 단정하거나 반환 배열을 임의 필터링하면 안 됩니다.

B의 기술적 결함 후보는 소스에서 구체적으로 설명할 수 있습니다. 그러나 담당자가 다른 업무 때문에 집중하지 못했다는 회고는 개인의 사후 추정입니다. 이 기능 누락의 조직적·인적 원인이나 확정된 인과 증거로 사용하지 않습니다.

## 확인 방법과 완료 조건

현재 증거를 목적별로 구분하면 다음과 같습니다.

| 구분 | 현재 평가 | 관찰과 다음 확인 |
| --- | --- | --- |
| 기획 적합성: 저장 | pass, 제공된 조회 사례 한정 | `settings-save-1`은 A·B의 저장 후 load 결과만 입증합니다. 화면 재열기는 미확인이므로 화면 명세 완료는 `human-review`입니다. |
| 고객 목적: 실제 제외 | A의 한 사례 pass, B의 관찰 fail | `select-a-1`과 `session-log-1`은 서로 다른 실행 경로의 증거입니다. 저장 테스트나 A 통과로 B를 통과 처리할 수 없습니다. |
| 기존 조건 유지·캠페인 격리 | human-review | 소스 구조는 단서지만 실행 증거가 없습니다. 아래 회귀 사례로 확인해야 합니다. |
| 탐색 검증 | warn | asset ID와 item ID의 계약, 다른 선택 진입점·우회 호출 여부가 조사 후보입니다. 아직 확정 결함이나 추가 요구는 아닙니다. |
| 원본 의도 전체의 누락 여부·운영 완료 | human-review | 원본과 배포 서비스가 미접근이므로 완전성·현재 운영 결과를 판정할 수 없습니다. |

다음은 실행한 테스트가 아니라 후속 검증 계획입니다. 승인된 A·B 각각에서 확인합니다.

| 사례 | 입력·절차 | 기대 결과·관찰 위치 |
| --- | --- | --- |
| V1 제외 적용 | 원래 조건상 선택 결과가 나오는 fixture에서 a9를 제외하고 선택 실행 | 실제 선택 결과 `[]`. 저장값만 보지 않고 route를 통과한 결과를 관찰합니다. |
| V2 비제외 유지 | a9를 제외한 상태에서 제외 목록 밖의 입력을 선택 | 변경 전 기준과 동일한 결과. enabled·region 조건을 계속 만족해야 합니다. |
| V3 기존 조건 | 비활성 항목, 지역 불일치 항목, 활성·지역 일치 항목을 함께 준비 | 비활성·지역 불일치 항목은 계속 탈락하고 기존 적격 항목은 유지됩니다. |
| V4 캠페인 격리 | 캠페인 P에는 a9 제외, Q에는 빈 목록으로 설정하고 같은 입력 선택 | P에서만 제외 효과가 나고 Q는 기존 조건에 따라 선택됩니다. 동일 목록만 저장했던 기존 사례를 보완합니다. |
| V5 화면 유지 | A·B 설정 화면에서 저장, 닫기, 다시 열기, 이후 선택 실행 | 목록이 유지되고 재진입 이후 선택에도 저장된 제외가 반영됩니다. |
| V6 해제·기본값 | 제외를 빈 목록으로 저장하거나 설정이 없는 캠페인 사용 | 기존 선택 조건에 따른 결과로 돌아가며 오류가 없어야 합니다. |
| V7 비대상 회귀 | A·B 수정 뒤 C 실행 | C 범위를 결정하기 전까지 현재 fallback 동작에 의도치 않은 변화가 없어야 합니다. C 제외 기능의 통과 증거로 사용하지 않습니다. |

우선 B의 실패를 통제된 fixture에서 재현하고, 수정 revision에 같은 사례를 재실행합니다. 기존 `session-log-1`을 삭제하거나 성공으로 덮어쓰지 않고 `실패 관찰 → 결함 → 수정 revision → 후속 run → 확인자`로 연결합니다. A·B의 통과도 당시 기록으로 보존합니다.

각 후속 run에는 사례와 사례 revision, 구현 commit/artifact, QA revision, 실제 결과, 환경·사용한 설정 데이터, 증거 위치와 확인자를 남깁니다. 현재 세 기록은 실행 빌드·시각·환경·확인자가 제공되지 않아 `app-r1`과 정확히 동일한 빌드였는지 확인되지 않습니다. 따라서 오늘 소스나 운영에 유효한 통과로 승격할 수 없습니다. 별도 QA 저장소나 새 도구 구축은 필요 조건이 아닙니다.

완료 기준은 A·B의 실제 제외, 비제외 조건 유지, 캠페인 격리, 화면 재열기 유지가 식별 가능한 수정 빌드에서 확인되는 것입니다. 원본 접근 한계는 별도로 남기며, C의 결정 대기 때문에 승인된 A·B 분석과 검증 준비까지 멈출 필요는 없습니다.

## 사람이 결정할 사항

확정된 결정 묶음은 3개입니다: ① A·B 적용, ② 캠페인별 제외와 비제외 조건 유지, ③ 화면 재열기 유지. 이 범위는 intent-owner의 rev1 승인을 재사용하며 재승인을 요구하지 않습니다. 범위 결정의 열린 항목은 C 1개이고, 현재 질문 묶음도 C 하나입니다. 예상 1회 결정으로 범위를 정리할 수 있으며, C 확대를 선택하면 C 계약을 구체화하는 후속 논의가 필요할 수 있습니다. ID 의미는 우선 계약 조사 항목이고, 자료로도 해소되지 않을 때만 별도 의도 결정을 요청합니다.

**D1 — C의 이번 완료 범위를 intent-owner가 확정해야 합니다.** note-1은 폐기된 해석으로 보존하고, note-2 이후 상태를 현재 기준으로 사용합니다. 디자인 rev2가 더 나중이라는 이유만으로 제품 결정을 대신하지 않습니다.

| 선택 | 영향·예상 변경 | 위험·되돌림 |
| --- | --- | --- |
| 권고: 이번 완료는 A·B로 확정하고 C는 별도 결정 시 재검토 | C 코드 변경 없이 A·B의 확인된 결함을 처리합니다. 활성 범위 기록에 C 보류 이유, 결정자, 재검토 조건을 남깁니다. | C의 제외 기능은 미구현으로 남습니다. 향후 승인된 확장으로 범위를 변경할 수 있습니다. |
| 이번에 C도 포함 | 제품·디자인 충돌을 intent-owner가 해소하고 C 설정 UI, fallback의 제외 단위·유지 조건, 시나리오를 승인해야 합니다. 이후 C 코드와 테스트가 추가 변경 대상입니다. | 별도 실행 경로여서 A·B 코드를 단순 복제하면 의미가 달라질 수 있고 검증 범위가 늘어납니다. 되돌릴 때는 C 확장 변경을 분리 복구하고 저장 설정을 어떻게 다룰지도 정해야 합니다. |

권고 근거는 rev1의 확정 범위가 A·B이고, C 확대의 승인 증거가 없다는 점입니다. C를 보류한다면 재검토 조건은 제품 결정 또는 디자인 수정이며 담당은 intent-owner입니다. 현재는 권고일 뿐 C 보류가 이미 승인됐다고 기록하지 않습니다. 결정 안내에는 `spec-it-clarify`와 HITL-002의 선택지·영향·위험·되돌림 형식을 참고했으며, 미채택 규칙의 의무를 새로 부과하지 않았습니다.

## 조사 기준·인계와 관찰 한계

- 입력 locator: `inputs/PK-01.md`의 제품 문서, 소스 발췌, 테스트와 관측, 논의 기록 전부. 기준은 policy rev1, app-r1, 디자인 rev2의 간접 인용입니다. 원본 locator·승인 시각·각 실행 시각은 unknown입니다.
- `observed_at`: 정확한 시각 미확인. 이번 검토에서 허용된 입력과 source 문서만 읽었으며 시각을 별도로 조회하지 않았습니다. 검토 시각을 원본 승인 시각이나 관측 run 시각으로 대신하지 않습니다.
- 실제 repository root·HEAD·commit·dirty 상태는 미관찰입니다. 제공된 것은 snapshot이므로 변경 diff, 이전 구현 상태, 배포 artifact와의 동일성은 확인할 수 없습니다. 이미 구현된 내용을 사전 승인·사전 실패 테스트가 있었다는 증거로 소급하지 않습니다.
- 관계 근거는 제공된 함수 호출과 route 매핑입니다. 전체 저장소 검색, 원본 대조, 테스트 실행, 운영 실측은 수행하지 않았습니다. 제공된 요구에서 경로·증거로, 증거에서 요구로 되짚었으나 원본 전체의 양방향 완전성 감사는 아닙니다.
- 새 세션에서 재개하거나 policy/app/design snapshot, 실제 HEAD·dirty, 설정 계약이 바뀌면 해당 자료와 이 결론을 다시 대조해야 합니다. 새 caller나 C 결정이 발견되면 경로·시나리오·증거 유효성을 갱신합니다. 접근이 열리면 원본 승인 기록, 화면과 배포 연결, 실제 run 빌드부터 확인합니다. 접근 밖 변경을 자동 감지하는 장치는 없습니다.
- 본 작업은 수동 분석입니다. 실행형 정책 validator·QA runner는 실행하지 않았고 실제 exit code도 없습니다. 판정 의미상 미결정·증거 부족은 `2`에 해당하지만 프로세스 실행 결과는 아닙니다. 사용자 코드·정책·서비스는 수정하지 않았으며, 이 응답 파일 저장은 호출자의 별도 평가 기록 권한에 따른 것입니다.
