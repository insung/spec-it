# 현재 변경 조사 인계

이번 결과는 **shadow assessment / late-entry**다. 제공된 현재 소스를 읽고 이전 기록과 비교했으나, manifest/lock과 승인된 제품 의도가 없어 spec-it 준수·위반이나 변경 완료를 확정할 수 없다. 수동 검토 결과는 `human-review`이며, 코드·설정·정책·서비스·프로젝트 문서는 변경하지 않았다. 아래 내용은 다음 작업을 위한 조사 기록이다. 문서 허브를 먼저 만들 필요는 없다.

미발행 후보 source의 `spec-it-impact`를 중심으로 delta 조사를 수행하고, `spec-it-check`의 quick 읽기 전용 shadow assessment 기준과 specify/clarify의 인계 지침을 사용했다. 정책 채택, 승인된 명세 투영, 실제 clarification 인터뷰, 자동 validator 실행은 수행하지 않았다.

## 2. 以前 기록에서 바뀐 결론과 영향 관계

이전의 `filterFlag=false`, 기본값 `allow` 메모는 당시 기록으로 보존하되 현재 판단에는 재사용할 수 없다. 현재 파일 값은 각각 `true`, `deny`다. `select-a`의 helper 호출 관계는 현재 소스로 재확인했고, 이전에 조사하지 않은 **`select-b`에서도 동일한 실제 호출 관계를 발견했다**. 두 caller가 c1→c2에서 미변경이라는 사실은 영향 제외의 근거가 아니다.

아래 `applies / open / unknown / excluded`는 영향 조사 상태이며 check 결과 enum과 별개다. 이번에는 근거를 갖고 `excluded`로 확정할 관련 소비자가 없다.

| 경로·경계 | 상태 | 관찰 근거와 영향 |
| --- | --- | --- |
| `src/shared.ts:1-2`의 `allowed` | `applies` | 현재는 `!excluded.includes(assetId)`를 반환한다. 제공 diff의 이전 `return true`와 비교하면 제외 목록에 포함된 ID의 반환값이 달라진다. 실제 파일에는 `string[]`, `string` 타입 표기도 있다. handoff diff는 실제 파일 전체의 정확한 재현으로 취급하지 않는다 |
| `src/select-a.ts:1-3` → `allowed` → 반환 배열 | `applies` | `settings.excluded`, `asset.id`를 실제 인자로 전달한다. 유효한 문자열 배열에 대상 ID가 있으면 `[]`, 없으면 `['item-a']`가 되는 코드 경로다 |
| 미변경 `src/select-b.ts:1-3` → `allowed` → 반환 배열 | `applies` | A와 같은 인자로 helper를 실제 호출한다. 제외 ID가 있으면 `[]`, 없으면 `['item-b']`가 되는 코드 경로다. 이번 helper 변경 검증에 포함해야 한다 |
| `config.json:1` | 변경 자체는 `applies`, 승인된 의미는 `open` | `filterFlag: true`, `missingSettings: deny`를 직접 확인했다. 두 키의 reader/writer는 제공 앱에서 발견되지 않았다. 따라서 설정만 보고 런타임에서 필터 토글이나 누락 시 deny가 작동한다고 말할 수 없다 |
| 설정 저장·로드 → A/B 호출 | `unknown` | 제공 파일에는 저장, 로딩, caller의 상위 호출, 실행 진입점이 없다. A/B 함수 내부 경로를 확인했지만 실제 운영에서 누가 언제 실행하는지는 확인하지 못했다 |
| 디자인 rev3의 저장 실패·재시도 | 반영 범위·승인은 `open`, 구현 연결은 `unknown` | 코드 diff에 화면 변경이 없더라도 원본 revision 변화는 검토 대상이다. 제공 앱에 화면·저장 실패 처리·재시도 코드가 없어 반영 여부를 판단할 수 없다 |
| feed → 설정/자산 입력 | `unknown` | 계약 rev2의 존재 설명 외에 필드·오류·누락 규약이나 adapter 구현이 없다. 최신 계약과 입력 유효성을 검증할 수 없다 |
| 라이브러리 → 원격 서비스 C | `unknown` | 관계 메모만 있다. C가 실제로 이 helper를 호출하는지, 어떤 버전을 쓰는지, 변경이 배포됐는지 모두 미확인이다. C의 접근 불가가 A/B의 확인된 영향을 취소하지 않는다 |

위 반환값은 **정적 코드 해석**이며 테스트 실행 결과나 승인된 정답이 아니다. 예를 들어 `excluded=['x']`, `asset.id='x'`라면 A/B 모두 빈 배열로 해석되지만, 제품이 A만 제외해야 하는지 A/B/C 모두 제외해야 하는지는 아직 결정되지 않았다. 반례로 `excluded=[]` 또는 다른 ID만 포함한 배열은 각 item을 반환한다. 이 유지 동작도 수용 기준으로 승인되지는 않았다.

구체적인 경계 위험도 있다. `settings`는 있으나 `excluded`가 `undefined`/`null`이면 현재 helper의 `.includes` 접근에서 예외가 예상된다. 제공 diff의 이전 helper는 그 인자를 읽지 않았으므로 이 지점은 **이번에 바뀐 경로의 회귀 후보**다. 반면 `settings` 자체가 없을 때 caller가 `settings.excluded`를 읽는 구조는 미변경 caller에 이미 있는 **레거시 경계 후보**다. 둘 모두 실제 입력 계약이 없으므로 확정 제품 결함으로 판정하지 않는다. TypeScript 표기는 런타임 feed 검증을 증명하지 않으며, `missingSettings=deny`가 예외를 빈 결과로 바꾸는 연결도 발견되지 않았다.

프로필은 다음과 같이 제안한다. `capability/shared-domain-library`는 여러 독립 배포 단위가 소비하거나 독립 릴리스한다는 조건이 확인되면 적합하다. A/B 함수가 둘이라는 사실만으로 독립 배포 단위 둘을 증명하지는 않는다. `risk/standard`는 운영 사용자나 지속적인 업무 상태가 있을 때 후보이며, 지금은 위험도 선택 근거가 없어 확정하지 않는다. TypeScript 파일은 확인했지만 이 source의 언어 참조 프로필은 Python이므로 Python/Ruff를 억지로 선택하지 않는다. 언어·lint 계약은 프로젝트 상황에 맞게 별도 결정할 사항이다. backend·HTTP API·AWS·DB 프로필을 고를 근거도 없다. 설정 및 외부 계약은 관련 재평가 신호지만 인프라 채택 사실은 아니다.

참고로 `ARCH-006`은 transport adapter가 관찰되지 않아 적용 조건을 확인하지 못했고, `ARCH-004`는 이번 요청에서 언어 선택·변경을 수행하지 않으므로 그 변경 조건에 한해 `not-applicable`이다. 프로필의 다른 모든 규칙을 검사했다는 뜻은 아니다.

| D2. 설정 누락과 필터 비활성 의미 / 제품·운영 의도 담당 | 누락 시 허용하면 선택 지속성이 높지만 제외 누락 위험이 있고, 차단하면 제외 안전성이 높지만 정상 선택을 막을 수 있다. 현재 자료로 allow/deny 중 하나를 제품 정답으로 권고할 근거는 없다. 권고는 누락·빈 목록·비활성을 구분해 결정하고 예외를 의도된 deny로 취급하지 않는 것이다 | config reader와 입력 경계, helper/caller, 오류 또는 빈 결과 계약에 영향을 준다. 다른 세션의 config 변경은 현재 상태로 보존하고 작성자·승인 근거를 확인한다 |
| D3. rev3 재시도를 이번 완료 범위에 포함할지 / 디자인·제품 담당 | 권고는 rev3 원본과 승인 범위를 확인해 포함 또는 명시적 보류를 기록하는 것이다. 포함 시 실패→재시도→저장 결과를 확인해야 하고, 보류 시 사용자 실패 복구가 제공되지 않을 수 있다 | 화면·저장 경로가 제공된 뒤 구체적 수정과 중복 요청 영향을 조사한다. 보류라면 이유·담당자·재검토 조건이 필요하며 현재는 보류 승인도 없다 |
| D4. spec-it 채택 범위·버전·위험도 / 프로젝트·아키텍처 담당 | 권고는 이 인계를 근거로 정책 후보와 프로젝트 사실을 확인한 후 채택하는 것이다. 현재 분석만으로 lock을 확정하면 불명확한 선택을 의무로 고정하게 된다 | 제품 미결정 해소와 별도 투영 권한 이후 converge로 manifest/lock/ADR/AGENTS 등을 필요한 범위만 생성한다. 지금은 생성하지 않는다 |

C 저장소 접근·사용 버전과 feed 최신 계약 확보는 우선 **사실 조사**다. 사람에게 코드 caller를 찾아오라고 요구할 항목이 아니다. 접근이 확보되면 담당자가 직접 조사하고 그 결과로 필요한 계약·적용 결정을 좁힌다. D1/D2의 의도가 정해진 뒤 저장 전후 적용 시점, 진행 중 선택, 권한·계정 경계가 관련되는지 추가로 확인한다. 현재 코드에서 보이지 않는 경계를 임의 요구로 확정하지 않는다.

검증 복구는 다음의 관찰 결과를 목표로 한다. 사례 이름은 이 보고서의 임시 구분이며 승인된 QA ID가 아니다.

| 사례와 목적 | 현재 연결·공백 | 다음 실제 증거 |
| --- | --- | --- |
| 제외 ID가 A/B에서 반환되지 않는지 | helper→A/B 반환 배열은 확인; 적용 의도·run 없음 | 승인된 범위에서 제외 ID와 비제외 ID/빈 목록을 각각 호출한 실제 배열 결과 |
| 누락 설정·누락 excluded·비활성 필터 | 예외 후보는 확인; config→호출 연결과 기대 결과 없음 | 로딩 경로 확보 후 승인된 allow/deny/오류 및 flag 의미를 경계별로 검증 |
| 저장 실패 후 재시도 | 디자인 rev3 설명만 있고 화면·저장 경로 없음 | 원본 승인과 구현 확보 후 실패 화면, 재시도 결과, 저장 이후 실제 선택 결과. 저장 성공만으로 제외 성공을 대신하지 않음 |
| 외부 feed·C 호환성 | 계약 rev2 내용·최신성, C 사용·배포 버전 없음 | 최신 계약과 실제 사용 버전에 맞춘 입력·소비자 관찰. 원격 확인자와 증거 위치를 함께 기록 |

`package.json`에는 scripts나 runner가 없고 dependencies도 비어 있다. `tests/source.test.ts`는 과거 실행 기록과 실행 가능한 test command/runner가 없다는 주석만 있다. 따라서 테스트·lint·build를 실행했다고 보고하지 않으며 도구를 새로 설치하지 않았다. 현재는 기획 적합성, 고객 목적 달성 모두 `human-review`; 누락 입력 예외와 flag 연결 부재는 정적 탐색 finding이다.

다음 실행에서는 case revision, 실제 소스 파일 지문/snapshot과 working-change ID, build/환경, 입력·기대값·실제 결과, 실행 시각·증거·확인자를 남긴다. 실패→수정→재실행은 별개 run으로 보존한다. c1 전체 자료가 확보되면 격리된 사후 재현을 할 수 있지만 이를 개발 전에 실행했던 실패 테스트라고 쓰지 않는다. 이전 run은 제공되지 않았으므로 과거 통과도 현재 유효한 통과도 없다. DB·배포 조합은 실제 관련성이 발견될 때 추가한다.

## 5. 재개·재검토 조건

- 새 세션에서 이 기록을 재사용할 때 `app/` 파일 목록과 위 SHA-256, 요청의 snapshot/working-change 식별자를 대조한다. 특히 다른 세션이 작성한 `config.json`을 다시 읽고 변경 이력을 덮어쓰지 않는다.
- app-c2/patch-d2 또는 실제 파일 bytes가 바뀌면 변경 파일과 연결된 A/B 및 새 caller를 재검색한다. fixture 밖의 Git HEAD나 dirty 상태를 대신 추정하지 않는다.
- 제품 승인·디자인 rev3 이후 revision이 추가되면 원문 section과 승인 범위를 대조하고 관련 시나리오·증거 유효성을 갱신한다. 화면 diff가 없다는 이유로 이 재검토를 생략하지 않는다.
- feed 최신 계약 또는 C 접근 권한을 확보하면 필드·누락 의미·사용 버전·실행·배포 경계를 확인하고 `unknown` 항목을 다시 평가한다.
- config reader/writer, 저장 경로, 상위 caller, 신규 소비자가 발견되면 해당 관계부터 확장한다. 기존 확인 결과를 횟수만 채우려고 전부 반복하지 않는다.
- 사후 QA가 통과해도 사전 승인/실패 증거의 역사적 공백은 보존한다. 명시적 보류 요구는 미구현 상태와 이유·담당자·재검토 조건을 유지한다.

이번 범위의 인계는 완료할 수 있으나 구현 완료나 정책 채택 완료는 아니다. check의 요약 exit 의미로는 **2: 사람 결정 또는 증거 부족**에 해당한다. 실행 가능한 checker가 낸 실제 프로세스 exit code는 아니다. 이 절차에는 상시 watcher, 접근 밖 변경 자동 탐지, 모든 경로 발견 보장이 없다.
