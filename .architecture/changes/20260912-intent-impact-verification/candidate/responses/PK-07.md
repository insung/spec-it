# 다음 변경 준비 상태와 인계

## 결론

전체 준비 상태는 `human-review`다. 제공된 공개 소스의 정책 버전은 **0.4.0**이고, **0.5.0은 미발행 목표 후보**다. P1은 1단계, P2는 2단계까지 진행했으므로 어느 기록도 전체 완료·후보 검증 완료·릴리스 준비 완료로 볼 수 없다. 다음 작업은 기존 행동을 실제로 실행해 기준선을 확보하는 준비부터 이어가야 한다.

DB 변경 전달은 **기존 정책 정의를 재사용하는 범위로 제외**한다. DATA-009, capability/db-migration, 설명 문서가 이미 존재한다. 다만 여기서 완료는 정책 정의의 완료를 뜻한다. 공개 소스는 migration runner, DB lock integration, DB release manifest·environment history schema, definition reconciliation을 미구현으로 명시한다. 운영 자동화까지 완료됐다는 의미로 인계하면 안 된다. 이번 요청에 그 구현을 추가하지 않는다.

## 인계 사본 판정

| 원문 요구 | handoff-A | handoff-B | 필요한 다음 증거 |
| --- | --- | --- | --- |
| 되읽기 | 구현 대상·테스트 계획만 있음 | 계획만 있음 | 원문 locator/revision, 구현, 실제 실행 응답, 관찰 결과 |
| 영향 조사 | 구현 대상·테스트 계획만 있음 | 계획만 있음 | 변경·미변경 소비자 및 외부 경계 조사와 검증 근거 |
| 외부 QA 저장소 연계 | 누락. 요구→계획 연결이 끊김 | deferred: 의도적으로 미구현. owner intent-owner, 사유 ‘다중 저장소 실증 전’, 재개 조건 ‘실제 두 저장소 QA 파일럿 확보’ | A는 누락을 복구할 계획 또는 명시적인 범위 결정. B는 보류 결정의 승인 근거와 재개 조건 충족 시 실행 증거 |

두 사본의 ‘모든 작업 완료’는 제공된 설명과 모순되므로 정정할 대상이다. A의 누락과 B의 근거 있는 보류는 다른 상태다. B는 추적 가능한 보류 기록을 갖췄지만 외부 QA 연계가 완료되거나 통과한 것은 아니다. owner 기재만으로 사람이 보류를 승인했다는 증거가 되지도 않는다.

이는 제공된 원문 요약과 인계 설명 간 불일치 판정이다. 고정 lock에는 DATA-009가 없고 프로젝트가 선택한 profile은 risk/standard다. DATA-009는 기존 정책 자산 조사에 사용했으며 이번 작업이 실제 DB 변경을 수행한다고 보지 않았다. 외부 QA의 특정 저장소 구조를 강제하는 고정 의무도 이번 조사에서 확인하지 않았으므로 새로운 규칙 위반을 만들어내지 않는다. 완료 주장의 정정과 실행 증거 확보는 `human-review`로 인계한다.

## 다음 담당자가 이어갈 작업

1. P1/P2의 변경 식별자와 관계를 확인하고, 실제 초안·승인 기록·사례·인계 원본의 locator와 revision을 확보한다. 새 담당자가 모든 사용자 원문을 읽을 수 있는지는 현재 `unknown`이다. 확보한 원문 범위에서 요구→명세→사례를 대조하고, 명세·사례에서 원문으로도 역추적한다. 미접근 원문은 목록과 확보 담당·조건을 남기며 전체 원문 완전성 검사를 완료했다고 쓰지 않는다.
2. P1은 2단계를 먼저 완료한다. P2는 승인 범위와 사례 기준을 확인·고정한 뒤 3단계 실제 baseline run으로 진행한다. 공개 0.4.0을 기준선으로 식별하고 입력, 지침 revision, 실행 환경·모델 설정, 실제 응답, 관측 시각과 판정 근거를 기록한다. 정적 지원 표는 별도 보존한다. 기존 정책만으로 성공한 사례는 유지해야 할 사례이며 실패 사례로 꾸미지 않는다.
3. 원문 누락, 명시적 보류, 기존 DB 정책 재사용, 실제 실행 없는 완료 주장, 원문 접근 불가를 구별할 수 있는 사례를 후보 편집 전에 고정한다. 새로운 공통 의무가 필요한지 먼저 검토하고, 충분하다면 좁은 지침 개선으로 다룬다. 공통 정책·조건부 profile·프로젝트 결정·비공개 맥락의 대상을 분리한다.
4. 승인된 변경을 구현한 뒤 같은 사례로 후보 응답을 얻고, 원문과 실제 응답에 근거한 독립 검증을 수행한다. 기준선·후보·판정의 신원을 연결하고 과거 실패 및 수정 후 재실행을 보존한다. 수동 사례 판정은 validator나 일반적인 AI 성공률이 아니다.
5. 실제 변경 범위에 맞춰 호환성과 SemVer를 결정한다. 0.5.0은 아직 확정된 배포 사실이 아니다. 필요한 연결 문서·프로필·스키마·변경 이력·migration 영향과 project reconvergence 여부를 검토한 뒤 6단계로 이동한다. 자동 프로젝트 업그레이드나 Phase 0 밖의 실행기 구현·패키지 배포를 이번 범위에 추가하지 않는다.

재검토 조건은 새 세션·작업 재개, 공개 또는 후보 snapshot 변경, P1/P2 초안·승인·사례 변경, 새 소비자/외부 QA 계약 발견, 원문·원칙 원고 접근 권한 확보, 두 저장소 파일럿 확보다. 해당 조건이 발생하면 관련 원문과 조사 결과를 다시 비교한다. 현재 조사만으로 접근 밖의 변화를 감지할 수는 없다.

## 원칙 문서 담당자에게 넘길 묶음

- **문제:** 계획·정적 지원·실제 실행·구현·검증·릴리스의 단계가 섞이면 완료 주장에 근거가 사라지고, 외부 요구 누락이 다음 담당자에게 전달되지 않을 수 있다.
- **관측:** 제공 기록상 P1은 1단계, P2는 2단계다. A는 외부 QA 요구를 누락했고 B는 owner·사유·재개 조건을 갖춰 보류했다. 두 사본의 전체 완료 주장은 그 내용과 맞지 않는다. 실제 파일럿 결과는 아직 없다.
- **가설:** 단계별 증거 분리, 원문 양방향 대조, 접근 한계와 보류 조건의 명시가 인계 오류를 줄일 수 있다. 효과는 실제 baseline/candidate run과 독립 판정으로 검증해야 한다.
- **결정과 미결정:** 기존 DB 변경 전달 정책을 다시 구현하지 않는다는 것은 이번 사용자 범위다. 0.5.0은 미발행 목표다. B의 보류 승인, 새 공통 규칙 필요성, P1/P2 관계는 미확인이다.
- **반례·구별할 사례:** 기존 baseline이 이미 성공한 사례는 후보의 새 성과가 아니다. 명시적 deferred는 누락과 다르지만 완료도 아니다. 파일 네 개 작성은 네 단계 완료가 아니다. 사후 작성한 명세·테스트는 과거 사전 승인·사전 실패 실행의 증거가 아니다.
- **관련 규칙 후보:** DATA-009는 기존 DB 정책 재사용 근거이며 신규 규칙 후보가 아니다. lock에 포함된 TST-001은 행동 변경에 대한 실행 증거의 관련성 검토 대상이지만, instruction-only 변경의 구체 적용·면제 여부는 아직 확정하지 않았다. 신규 규칙 ID는 부여하지 않았다. 후보 지침의 권고를 곧바로 공개 공통 의무로 만들지 않는다.
- **증거 상태·획득 조건:** 파일럿 관측값, 효과 크기, 유지·회귀 사례, 독립 판정, 실행 환경은 pending이다. 실제 run과 원본 응답이 확보되면 채운다. 원칙 원고는 미접근으로 최신 상태·기존 내용·중복 여부 모두 unknown이다.
- **공개 경계·협업:** 공개 문서에는 검증된 일반 원칙과 비식별화된 근거만 반영하고 원문 대화·개인·회사 맥락은 공개 여부를 별도로 확인한다. 이번에는 원칙 원고를 수정하지 않았다. 편집 가능해지면 다른 세션의 최신 원고를 다시 읽고 겹치는 부분을 조율한 뒤 반영한다. 이 묶음은 분석 인계이며 파일럿 성과 보고서가 아니다.
