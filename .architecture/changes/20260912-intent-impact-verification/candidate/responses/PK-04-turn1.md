현재 기획의 목표는 **“사용자가 제외한 항목이, 합의한 적용 시점 이후의 결과에 나오지 않는다”**로 잡겠습니다. 적용 대상과 시점은 아직 확정하지 않습니다. 요청대로 코드·정책·서비스는 수정하지 않았습니다.

평가본의 `spec-it-specify`로 기획 초안을 정리하고, `spec-it-impact`로 q1의 영향 범위를 확인했으며, `spec-it-clarify`로 필요한 결정만 묻겠습니다. 아래는 이 응답 안의 `change / clarifying` 초안입니다. 프로젝트에 명세 파일을 생성하거나 정책을 채택한 상태는 아닙니다.

### 확인한 사실과 기획 초안

| 구분 | 내용 |
| --- | --- |
| 사용자 의도 | 제외한 항목이 결과에 나오지 않게 한다. 기능 사용자와 예외 정책은 미확정이다. |
| q1의 저장 코드 | `save(campaignId, excluded)`가 `settings[campaignId]`에 값을 대입한다. DB 저장, 재시작 후 유지, 저장 성공 처리까지 확인된 것은 아니다. |
| q1의 선택 경로 | `routes.A → chooseA → activeItems`, `routes.B → chooseB → activeItems`가 보인다. A와 B 모두 조사·검증 대상이다. |
| 확인하지 못한 부분 | 두 선택 함수에 제외 목록을 직접 읽는 코드는 보이지 않는다. `activeItems` 내부가 없으므로 필터가 전혀 없다고 단정하거나 결함 위치를 확정할 수는 없다. |
| 기존 초안의 지위 | ‘캠페인별 목록을 저장한다’는 **사용자 확인 없는 기존 해석**이다. 현재 코드의 캠페인 키와 부합하지만 제품 범위의 승인 증거는 아니다. 캠페인별 적용은 아래의 제안으로만 유지한다. |
| 역할 간 충돌 | 제품 ‘즉시’, 디자인 ‘저장 후’, 운영 ‘다음 송출부터’는 서로 다른 관찰 결과를 만들 수 있다. 발언 시점·원문 revision·승인 시점은 미제공이다. 최종 선택은 intent-owner에게 받으며 다수결로 정하지 않는다. |

잠정적으로는 기능 사용 권한이 있는 사람이 항목 X를 제외하고, 승인된 적용 시점이 지난 뒤 같은 적용 범위의 결과를 확인하면 A와 B 모두에서 X가 보이지 않는 기능으로 이해했습니다. 예를 들어 후보가 X·Y이고 X를 제외했다면 결과에 X가 없어야 합니다. 제외된 X가 A에서는 사라지고 B에서는 다시 나오는 것은 반례입니다. 단, Y가 반드시 선택된다고까지 요구하지는 않습니다.

유지할 동작의 제안은 “제외되지 않은 항목에 대한 기존 자격·선택 규칙과, 합의한 적용 범위 밖의 결과는 유지한다”입니다. 새로운 우선순위나 보충 항목 선정, 진행 중 송출 취소, 저장 형식 변경은 현재 승인된 요구가 아닙니다. 제외 후 후보가 하나도 남지 않는 경우는 별도 결정이 필요합니다.

### 지금 필요한 결정

주요 기능 결정은 **해결 0건, 미결정 3묶음**입니다. 이번 질문은 D1·D2 두 묶음이고, D3 예외 처리는 적용 범위·시점 답변을 반영해 다음에 구체화하겠습니다. 예상은 이번을 포함해 2~3회이며, 초기 추정이어서 변경 사유는 없습니다. 별도 오타 수정의 의도 승인은 이미 해결된 것으로 구분합니다.

**D1. 이 기능은 누가 사용하며, 한 번 제외한 항목은 어디까지 제외되어야 하나요?**

추천 초안은 “기존에 해당 캠페인 설정을 수정할 권한이 있는 사용자에게 제공하고, 해당 캠페인에 한정하여 A·B 결과에 공통 적용”입니다. 기존 권한 체계가 실제로 존재하는지는 현재 자료로 확인되지 않았습니다. 한 사용자의 개인 설정인지, 캠페인 구성원에게 공통인 설정인지도 이 답변에 포함해 주세요.

- 캠페인 공통 적용은 현재 저장 키와 맞고 영향 범위가 좁지만, 같은 항목을 다른 캠페인에서도 제외하려면 각각 설정해야 합니다.
- 사용자 개인 적용은 개인별 결과를 만들 수 있지만 사용자 식별·권한·저장 키 경계를 다시 정해야 합니다.
- 계정 또는 전체 공통 적용은 반복 설정을 줄이지만 다른 캠페인의 결과까지 바뀌며 접근 권한과 데이터 범위를 넓힐 수 있습니다.

지금 필요한 이유는 수용 기준의 대상과 경계가 이 선택에 달려 있기 때문입니다. 예상 변경 경계는 사용자 접근 조건, 설정의 소유 범위와 읽기·쓰기 경로, A·B 결과 검증입니다. 근거는 q1의 `settings[campaignId]`이며, 이것이 권고의 기술적 단서이지 의도 승인은 아닙니다.

**D2. intent-owner 기준으로, X를 제외했을 때 어느 순간부터 결과에서 빠져야 하나요?**

추천은 “저장 성공 후 시작되는 새로운 결과 선택부터 적용하고, 이미 진행 중인 송출은 완료”입니다. 아래는 역할 발언의 확정 해석이 아니라 선택을 구분하기 위한 구체적 선택지입니다.

- 편집 즉시: 저장 전 화면에서 X를 제외한 순간 새 결과도 바뀝니다. 반응은 빠르지만 취소·저장 실패 때 미저장 변경의 효력을 별도로 다뤄야 합니다.
- 저장 후 새 선택부터: 저장 전에는 기존 결과 기준을 유지하고 저장 성공 뒤 새 선택에는 X가 나오지 않습니다. 저장 성공과 결과 변경을 대응시키기 쉽지만 이미 선택되었거나 진행 중인 송출에는 X가 남을 수 있습니다.
- 다음 송출 시작부터: 저장해도 현재 송출 단위의 기준은 유지하고 다음 송출 단위부터 반영합니다. 송출 단위 내 일관성이 좋지만 반영이 늦으며 “송출 시작”의 실제 경계를 확인해야 합니다.

진행 중인 송출까지 즉시 중단·교체해야 한다면 그 의도를 함께 명시해 주세요. 이는 새로운 선택에 반영하는 것보다 영향이 큽니다. 예상 변경 경계는 편집/저장 상태, 설정을 읽는 시점, 선택·송출 시점과 안내 문구입니다. 근거는 세 역할의 충돌 발언과 q1이며, q1만으로 어느 선택이 이미 지원되는지 확인할 수 없습니다.

두 결정의 되돌림 경계도 초안으로 남깁니다. 기획 단계에서는 결정 기록과 시나리오를 갱신하면 됩니다. 향후 구현을 되돌릴 때에는 새 제외 적용을 중단하고 이전 선택 동작으로 복구할 수 있어야 한다는 제안이지만, 이미 완료한 송출은 소급해서 되돌릴 수 없습니다. 설정 데이터 복구 방식과 실제 구현 비용은 저장·실행 경로 확인 후 정하며 지금 수치나 복구 가능성을 확정하지 않습니다.

D3은 “모두 제외되었을 때 결과를 비워도 되는지, 어떤 항목은 제외할 수 없는지”입니다. 현재 추천은 제외 항목을 임의로 되살리지 않는 것이지만, 실제 사용자와 송출 경계가 정해진 뒤 빈 결과의 처리·안내와 함께 결정하겠습니다. 소유자는 intent-owner, 재개 조건은 D1·D2 답변입니다. 이 예외가 미정인 동안 해당 동작을 구현하거나 명세를 확정하지 않습니다.

### 수용 기준과 확인 계획

승인 전에는 아래를 테스트 통과 결과가 아닌 **검증 계획**으로 유지합니다.

| 의도 → 시나리오 | q1 경로·상태 | 예상 관찰 및 계획 |
| --- | --- | --- |
| 제외가 결과에 반영됨 → S1 | A·B 둘 다 `applies`: 결과 선택 경로로 확인됨. 최종 제품 적용 범위는 D1 `open` | 승인된 시점 이후 X의 결과 포함 건수가 0인지 A·B 각각 확인한다. 실제 결과를 관찰할 경계는 추가 소스 조사로 찾는다. |
| 시점 일관성 → S2 | 저장 전/저장 후/진행 중 처리 `open`: D2 | 저장 전 결과, 저장 성공 뒤 새 선택, 진행 중 및 다음 송출을 구분해 승인된 기대값과 대조한다. |
| 기존 동작 유지 → S3 | 제외하지 않은 후보와 범위 밖 소비자: 유지 제안, 실제 소비자는 `unknown` | 비제외 후보에 기존 규칙이 유지되는지, D1에서 범위 밖으로 정한 곳이 바뀌지 않는지 비교한다. 아직 특정 소비자를 `excluded`로 확정하지 않는다. |
| 후보 소진·예외 → S4 | `open`: D3 | 모두 제외 또는 제외 제한 항목에 대한 승인된 결과를 검증한다. |

`activeItems` 내부, `save`의 호출자, 실제 설정 읽기, 결과 소비자·송출 경계, 권한 및 테스트는 제공 범위 밖이므로 `unknown`입니다. 사용자가 호출자를 찾아 주어야 할 질문으로 바꾸지 않고, 다음에 허용된 소스를 조사할 때 확인할 기술 과제로 남깁니다. 구현 후에는 승인된 수용 기준에 기반해 구현과 논리적으로 분리된 검증도 계획합니다.

### 별도 요청 A: 도움말 오타

`제외목룍 → 제외목록`은 동작·용어 의미·저장 형식이 바뀌지 않는다고 명시되어 있고 intent-owner 승인도 있으므로, 별도 중대 변경 명세·인터뷰의 면제 사유를 기록할 수 있습니다. 기능의 D1~D3 때문에 이 작업까지 대기시킬 필요는 없습니다. 의도 승인을 다시 요청하지 않겠습니다.

다만 이번 요청은 “어떻게 진행할지 설명”이고 지금은 수정하지 말라고 하셨으므로 실제 파일은 바꾸지 않았습니다. 실행 단계에서는 도움말의 해당 위치와 현재 diff를 확인하고 그 문자열만 수정한 뒤, diff와 렌더된 도움말에서 오타 교정 및 주변 문맥 보존을 확인하면 됩니다. 기능 구현·저장 구조 변경이나 불필요한 동작 테스트를 묶지 않습니다. 추후 의미나 계약 변경이 발견되면 이 면제 근거를 재검토합니다.

### 정책·출처 및 관찰 한계

평가본 `VERSION`은 `0.4.0`이지만 대상 프로젝트의 AGENTS, manifest/lock, 승인 ADR은 제공되지 않았습니다. 설치된 전역 스킬은 사용하지 않았으며, 이 분석은 미발행 평가본에 대한 `shadow assessment`입니다. q1은 JavaScript 형태의 코드라는 것까지만 확인됩니다. 서비스 종류·위험 수준·HTTP API·DB·클라우드를 추정해 프로필을 선택하지 않았으며 채택된 프로필은 확인 불가입니다.
