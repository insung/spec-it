# 2차 읽기 결과 및 검증 사례

코드는 구현하거나 수정하지 않습니다.

## 반영된 최종 이해

`intent-owner`의 이번 답변으로, 제외 목록은 **캠페인별이 아니라 계정 공통 설정**입니다. 계정 운영자가 저장에 성공한 목록은 그 계정 안의 **A/B 캠페인 모두**에 적용됩니다. 다른 계정의 목록이나 결과에는 영향을 주면 안 됩니다.

적용 시점은 다음과 같이 확정되었습니다.

- 편집 중인 값은 저장 전에는 적용하지 않습니다.
- 저장이 성공한 뒤 **새로 시작하는 선택**부터 그 계정의 제외 목록을 적용합니다.
- 이미 시작한 송출은 기존 상태를 유지하며, 저장 성공을 이유로 중간에 결과를 바꾸지 않습니다.
- 제외하지 않은 항목에는 기존 선택 조건을 그대로 유지합니다. 이번 변경은 제외 목록에 있는 항목을 결과 후보에서 빼는 범위이며, 나머지 항목의 기존 선정 규칙을 재정의하지 않습니다.
- 별도 역할·항목·캠페인 예외는 없습니다.

1차 응답에서 제시한 “캠페인별” 소유 범위는 미승인 초안과 snapshot에 근거한 가설이었고, 이번 `intent-owner` 정정으로 **대체되었습니다**. 또한 사용자가 말한 “A/B 캠페인”과 snapshot의 `chooseA`/`chooseB`가 정확히 같은 실행 경계인지는 아직 확인되지 않았으므로, 이를 같은 것으로 단정하지 않습니다. 실제 구현 전 영향 조사에서 계정 공통 설정이 각 선택 경로에 연결되는 위치를 확인합니다.

## 검증할 수용 사례

아래는 구현 전 합의된 기대 결과입니다. 아직 실행 결과나 통과 증거는 아닙니다.

| ID | 사전 조건과 행동 | 기대 관찰 |
| --- | --- | --- |
| AC-01 저장 전 편집값 | 계정 X에 기존 제외 목록이 있고, 운영자가 항목 P를 편집 화면에서 추가하지만 저장하지 않는다. 그 뒤 새 선택을 시작한다. | P는 저장된 기존 목록에 없으면 기존 선택 조건에 따라 결과에 남을 수 있다. 편집 중 값만으로 제외되지 않는다. |
| AC-02 저장 성공 후 A 캠페인 | 계정 X 운영자가 P를 제외 목록에 넣어 저장에 성공한 뒤, 계정 X의 A 캠페인에서 새 선택을 시작한다. | P는 결과에 나타나지 않는다. P 외 항목은 기존 선택 조건이 충족될 때 이전과 같은 방식으로 결과에 남는다. |
| AC-03 저장 성공 후 B 캠페인 | AC-02와 같은 계정 X의 저장 성공 뒤, 계정 X의 B 캠페인에서 새 선택을 시작한다. | 동일한 계정 공통 목록이 적용되어 P가 결과에 나타나지 않는다. 캠페인마다 별도 목록을 저장하거나 해석하지 않는다. |
| AC-04 진행 중 송출 유지 | 계정 X에서 P가 포함된 선택/송출이 이미 시작된 뒤, 운영자가 P를 제외 목록에 저장한다. | 이미 시작한 송출은 저장 성공 후에도 기존 결과를 유지한다. 이후에 시작하는 선택만 새 목록을 사용한다. |
| AC-05 저장 실패 | 운영자가 P를 제외 목록에 넣어 저장을 시도하지만 저장이 실패한다. 그 뒤 새 선택을 시작한다. | 실패한 편집값은 적용되지 않는다. 마지막으로 성공한 목록만 적용된다. |
| AC-06 계정 격리 | 계정 X에서 P를 저장하고, 계정 Y의 A/B 캠페인에서 새 선택을 시작한다. | 계정 Y에는 계정 X의 P 제외가 적용되지 않는다. 계정 경계를 넘는 결과 변화가 없다. |
| AC-07 제외 해제와 기존 조건 보존 | 계정 X가 저장 성공한 목록에서 P를 제거한 뒤 새 선택을 시작한다. | P는 더 이상 목록 때문에 제외되지 않지만, 기존 선택 조건을 충족할 때만 결과에 나타난다. 제외 기능이 기존 조건을 우회하지 않는다. |
| AC-08 빈 목록 | 계정 X가 빈 제외 목록을 저장하고 새 선택을 시작한다. | 목록 때문에 제외되는 항목은 없으며, 모든 항목은 기존 선택 조건만 따른다. |

도움말 오타는 별도 소규모 변경으로 승인 상태를 유지합니다. 구현 단계에서는 `제외목룍`을 `제외목록`으로만 고치고, 변경 차이에서 그 문자열 외의 동작·의미·저장 형식 변경이 없는지 확인합니다. 이 요청에서도 구현하지 않습니다.

## 승인 상태와 남은 결정

현재 **승인·해결 3건 / material-open 1건 / 위임 0건**입니다. `intent-owner`가 직접 답했으므로 추천안에 대한 위임으로 해석하지 않습니다.

| 결정 | 실제 상태 | 근거 |
| --- | --- | --- |
| 결과 범위·사용자·예외 | 승인됨 | 계정 운영자가 사용하며, 계정 내 A/B 캠페인 전체에 적용, 별도 예외 없음, 계정 간 영향 금지 |
| 적용 시점과 진행 중 송출 | 승인됨 | 저장 성공 후 시작하는 선택부터 적용, 저장 전 편집값 미적용, 진행 중 송출 유지 |
| 목록 소유 범위 | 승인됨 | 캠페인별이 아닌 계정 공통 목록 |
| 목록 갱신 충돌 규칙 | **pending human confirmation** | 같은 계정에서 둘 이상의 운영자가 서로 다른 목록을 저장할 때 전체 교체, 항목 병합, 충돌 감지 중 어느 결과가 맞는지 승인되지 않음 |
| 도움말 `제외목룍` 오타 수정 | 승인됨, 구현 대기 | 동작·의미·저장 형식 불변인 단순 오타 수정으로 앞서 `intent-owner` 승인 |

남은 material-open은 동시 편집이 가능한 경우의 갱신 충돌 규칙 1건입니다. 단일 운영자만 저장할 수 있거나, 저장 인터페이스가 이미 충돌 규칙을 보장한다는 실제 증거가 확인되면 이 항목은 사람 결정이 아니라 조사로 닫을 수 있습니다. 반대로 여러 운영자가 저장할 수 있다면, 구현 전 아래 한 가지를 `intent-owner`가 정해야 합니다.

### D-04. 같은 계정의 동시 편집은 어떻게 처리할까요?

**권장안:** 저장 시점의 최신 목록과 내가 편집한 목록이 달라졌으면 저장을 멈추고 새 목록을 보여 준 뒤 운영자가 다시 저장하게 합니다(충돌 감지).

| 선택 | 결과와 위험 | 예상 변경·되돌리기 |
| --- | --- | --- |
| 권장: 충돌 감지 | 다른 운영자의 제외/해제를 조용히 잃지 않는다. 재편집 단계가 생긴다. | 저장 계약과 화면/수용 사례에 충돌 결과를 추가한다. 사용자는 최신 목록을 바탕으로 다시 저장한다. |
| 마지막 저장 전체 교체 | 단순하지만 뒤늦은 저장이 앞선 운영자의 변경을 덮을 수 있다. | 전체 목록 저장만 필요하다. 되돌리기는 이전 목록을 별도로 알아야 한다. |
| 항목 단위 병합 | 동시 추가에는 편하지만 추가/삭제가 충돌할 때의 우선순위를 추가로 정해야 한다. | 항목별 변경 추적과 충돌 사례가 필요하다. |

**답변 예시:** `D-04: 충돌 감지. 여러 운영자 저장 시 최신 목록을 보여 주고 재저장.`

이 한 결정이 승인되거나 실제 단일 편집 제약으로 불필요함이 확인되면, material-open은 0건이 되고 변경 명세와 수용 사례를 고정하는 단계로 넘어갈 수 있습니다. 지금은 그 전 단계이므로 구현·수정·실행 검증을 하지 않습니다.

## 실제 읽은 출처와 한계

실제 저장소 코드, 호출자, 화면, API 계약, 계정·권한 모델, 저장 형식, 동시성 보장, 송출 실행 경계는 읽지 않았습니다. 그러므로 AC-01~AC-08은 요구사항 기반의 검증 계획이며 실제 통과 결과가 아닙니다. 다른 과제 입력·응답·검토 자료·외부 정보는 열람하지 않았습니다.
