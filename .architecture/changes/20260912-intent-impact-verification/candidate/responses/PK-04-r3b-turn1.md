# 1차 기획 정리 및 확인 요청

코드는 아직 수정하지 않습니다. 현재 목표는 **캠페인에서 제외한 항목이 정해진 결과에 나타나지 않게 하는 것**으로 이해했습니다.

## 지금 확인된 사실과 경계

- 제공된 snapshot에서 `save(campaignId, excluded)`는 캠페인 ID별 제외값을 저장하는 형태입니다. 다만 이 snapshot만으로 저장값의 실제 형식, 저장 성공 시점, 기존 값의 교체/병합 방식, 권한은 확인할 수 없습니다.
- `chooseA`, `chooseB`는 모두 `activeItems(campaign, asset)`의 결과를 그대로 반환합니다. 따라서 둘 중 어느 결과가 사용자에게 보이는지, 두 경로 모두에 제외가 적용되어야 하는지는 아직 확정할 수 없습니다.
- 기존 분석 초안의 “캠페인별 목록 저장”은 승인 근거가 없으므로 현재 요구사항의 정본으로 취급하지 않습니다.
- 제품·디자인·운영 의견은 적용 시점에 관해 충돌하며, 주어진 정보상 최종 결정자는 `intent-owner`입니다. 다수 의견이나 코드 형태로 이 충돌을 해소하지 않습니다.

현재는 **확정 0건 / 중요한 미결정 3건**, 이번 질문 묶음 3건입니다. 현재 정보로는 답변 뒤 **1~2회**의 추가 확인이 예상됩니다. 실제 화면·API·권한·실행 중 송출의 경계를 확인하면 이 추정이 바뀔 수 있습니다.

## 1차 결정 질문

### D-01. 어느 결과와 사용자에게 제외를 적용할까요?

**결정이 필요한 이유:** “결과”의 범위가 정해져야 `chooseA`와 `chooseB`의 적용 여부, 운영자/일반 사용자 차이, 예외를 검증할 수 있습니다.

**권장안:** 이 캠페인의 결과를 보는 모든 대상에서 `A`와 `B` 모두 제외하고, 별도 예외 역할이나 항목 예외는 이번 변경에 두지 않습니다.

**선택지와 영향:**

1. 권장안 — 두 경로와 모든 대상에 동일 적용. 규칙이 단순하고 “제외 항목이 결과에 나오지 않게”라는 표현을 넓게 충족하지만, 운영 점검용 예외도 없어집니다.
2. 특정 경로 또는 특정 사용자만 적용 — 예: `A`만, 혹은 일반 사용자만. 점검·관리 목적은 보존할 수 있지만, 어떤 경로/역할에서 제외 항목이 보이는지가 명시되어야 합니다.
3. 조건부 예외 허용 — 항목 속성, 역할, 캠페인 상태 등에 따라 보이게 함. 운영 유연성은 높지만 예외 조건·우선순위·감사/검증 범위가 추가됩니다.

**예상 변경·되돌리기:** 승인안은 선택 결과를 만드는 경계와 수용 사례에 기록됩니다. 되돌리기는 해당 캠페인의 승인된 제외 적용만 해제하는 범위로 설계합니다. 아직 저장 데이터나 공개 계약 변경 여부가 확인되지 않아 구체적 코드·마이그레이션·롤백은 제안하지 않습니다.

**답변 예시:** `D-01: 1, A와 B 모두, 모든 사용자. 예외 없음.`

### D-02. 저장한 제외는 언제부터 결과에 반영할까요?

**결정이 필요한 이유:** 제품은 “즉시”, 디자인은 “저장 후”, 운영은 “다음 송출부터”라고 하므로 관찰 가능한 결과가 서로 다릅니다. 이는 구현 전에 `intent-owner`가 결정해야 합니다.

**권장안:** **저장 성공 직후부터 새로 시작하는 선택에 반영하고, 이미 진행 중인 선택/송출은 바꾸지 않는다.** 즉 “즉시”를 저장 후 새 선택의 즉시성으로 정의합니다.

| 선택 | 저장 전 | 저장 후 새 선택 | 이미 진행 중인 선택/송출 | 장단점 |
| --- | --- | --- | --- | --- |
| 권장안 | 기존 결과 | 제외 적용 | 기존 결과 유지 | 사용자는 저장 효과를 바로 확인하고, 실행 중 결과가 흔들리지 않습니다. |
| 제품 의견 해석 | 기존 결과 | 제외 적용 | 즉시 제외 적용 | 가장 빠르지만 실행 중 결과 변경·부분 송출의 처리 기준이 필요합니다. |
| 운영 의견 해석 | 기존 결과 | 다음 송출 시 적용 | 기존 결과 유지 | 운영 예측성은 높지만 저장 직후의 기대와 어긋날 수 있습니다. |

**예상 변경·되돌리기:** 승인된 시점은 저장 완료, 선택 시작, 송출 시작 중 어느 경계에서 필터를 평가할지와 수용 사례를 바꿉니다. 되돌리기는 이미 시작한 작업에 소급 적용하지 않는 것을 기본 안전 경계로 제안합니다. 이 경계를 바꾸려면 다시 승인과 검증이 필요합니다.

**답변 예시:** `D-02: 권장안. 저장 성공 뒤 새 선택부터 적용, 진행 중 송출은 유지.`

### D-03. 제외 목록의 소유 범위와 갱신 규칙을 승인할까요?

**결정이 필요한 이유:** snapshot의 함수명과 미승인 초안은 캠페인별 저장을 암시할 뿐, 누가 목록을 바꾸는지와 저장 시 기존 목록을 교체하는지/병합하는지는 결정하지 않습니다. 이는 다른 사용자의 설정을 덮어쓰거나 의도치 않은 캠페인 간 적용을 막는 데 필요합니다.

**권장안:** 목록은 **캠페인별**로 소유하고, 권한 있는 사용자가 저장한 전체 목록으로 이전 목록을 **교체**합니다. 다른 캠페인에는 적용하지 않으며, 동시 편집 충돌 처리 방식은 실제 저장 인터페이스를 확인한 다음 질문으로 남깁니다.

**선택지와 영향:**

1. 권장안 — 캠페인별 전체 교체. 범위가 명확하고 재현하기 쉽지만 동시 편집 시 최신 저장이 앞선 저장을 덮을 수 있습니다.
2. 캠페인별 항목 단위 병합. 여러 사람이 나눠 편집하기 쉽지만 삭제·충돌·최종 목록의 기준을 더 정해야 합니다.
3. 전역 또는 자산 단위 공유 목록. 관리 부담은 줄 수 있지만 한 캠페인의 제외가 다른 캠페인 결과에 영향을 줄 수 있습니다.

**예상 변경·되돌리기:** 승인안은 설정 모델, 편집 권한 경계, 저장/읽기 계약, 캠페인 간 격리 수용 사례를 결정합니다. 되돌리기는 승인된 이전 목록으로 복원할 수 있어야 하나, 이력 보관 요구는 아직 결정되지 않았습니다.

**답변 예시:** `D-03: 1, 캠페인별 전체 교체. 편집 권한자는 <역할>.`

## 승인 뒤의 진행 순서

1. 위 세 결정을 `intent-owner`의 명시적 승인으로 기록하고, 사용자에게 보이는 정상·경계·유지 사례를 확정합니다.
2. 실제 저장/선택/송출/권한 경로를 조사해 snapshot의 가설과 분리하여 영향 범위를 확정합니다.
3. 결정된 적용 시점과 범위를 기준으로 변경 명세와 수용 사례를 만들고, 동작 변경의 테스트 계획을 확정합니다.
4. 그 뒤에만 최소 구현과 독립 확인을 진행합니다. 현재 단계는 계획·사람 확인 단계이지 자동 통제가 아닙니다.

## 별도 요청 A — 도움말 오타 수정

`제외목룍` → `제외목록`은 이미 `intent-owner`가 승인했고, 동작·용어 의미·저장 형식을 바꾸지 않는다고 명시되어 있으므로 위 기능 결정과 분리해 진행할 수 있습니다.

진행 시에는 도움말의 해당 문자열만 바꾸고, 변경 전후 차이에서 그 한 글자 외의 변경이 없는지 확인합니다. 수용 확인은 도움말에 `제외목록`으로 표시되는지와 링크·동작·저장 형식이 변하지 않았는지를 독립적으로 비교합니다. 이는 동작 변경이 아닌 문서 오타이므로, 동작 변경용 TDD의 예외 사유와 확인 근거를 기록할 수 있습니다. 다만 현재는 “코드를 고치지 말아 달라”는 요청에 따라 이 오타도 수정하지 않습니다.
