# PK-04 2차 검토 — intent-owner 정정 반영

## 확정된 이해

기능 요구는 다음으로 확정되었습니다.

> 계정 운영자가 계정 공통 제외 목록을 저장하면, 그 **저장 성공 뒤에 시작하는** 해당 계정의 모든 A/B 캠페인 결과 선택에서 제외 항목은 나오지 않는다. 저장 전 편집값은 적용하지 않으며, 이미 시작한 송출은 기존 상태를 유지한다. 제외하지 않은 항목의 기존 선택 조건은 바꾸지 않고, 다른 계정에는 영향을 주지 않는다.

따라서 1차의 “캠페인 C의 제외가 D에 영향을 주지 않는다”는 반례는 **동일 계정의 A/B 캠페인에 대해서는 폐기**됩니다. 올바른 반례는 “계정 1의 제외가 계정 2의 결과에도 적용된다”입니다. 계정 운영자만 이 기능의 사용자이며, 별도 예외·재포함·캠페인별 덮어쓰기는 두지 않습니다.

`save(campaignId, excluded)`라는 제공 snapshot은 캠페인 키를 보이지만, 이는 승인된 제품 의도(계정 공통)와 일치하지 않습니다. 구현 전에는 이 차이를 조사해 계정 식별자, A/B 캠페인과 계정의 관계, 실제 저장 위치, `chooseA`/`chooseB`의 호출 경로를 확인해야 합니다. 이것은 발견 과제이지, 현재 제품 결정을 다시 묻는 항목은 아닙니다.

## 승인 상태

intent-owner가 직접 답변했으므로 아래 세 결정은 명시적으로 승인되었습니다.

| 결정 | 상태 | 승인 근거 |
| --- | --- | --- |
| 제외 목록의 소유 범위와 변경 사용자 | 확정 | 계정 공통, 계정 운영자, 계정 내 A/B 캠페인 모두 적용 |
| 적용 시점과 진행 중 송출 경계 | 확정 | 저장 성공 후 시작한 선택부터 적용, 저장 전 편집값 미적용, 이미 시작한 송출 유지 |
| 예외와 비변경 조건 | 확정 | 별도 예외 없음, 제외하지 않은 항목의 기존 선택 조건 유지, 계정 간 영향 금지 |

- 확정된 물질적 결정: 3개
- 남은 material-open: **0개**
- 위 0은 현재 관찰된 제품 의도에 대한 수치입니다. 아직 읽지 않은 코드·저장 구조·프로젝트 정책에서 별도 기술 제약이 발견되었다는 뜻은 아니며, 그런 발견이 실제로 생길 때만 필요한 기술 결정을 새로 엽니다.

저장 실패, 동시 편집자, 재시도·예약 작업, 외부 소비자·연동, 별도 메시지 방식은 이번 입력에 관찰된 요구나 기술 trigger가 없습니다. 그러므로 이를 새 material decision으로 만들지 않습니다. 구현 조사에서 실제 관련 경로가 발견되면 그 사실과 영향만 기록하고, 승인된 결과를 바꾸는 선택이 필요할 때에만 별도 확인합니다.

## 구현 전 검증할 수용 사례

아래는 승인된 요구를 고정하는 검증 계획입니다. 테스트 실행 결과가 아닙니다.

| ID | Given | When | Then |
| --- | --- | --- | --- |
| AC-01 계정 공통 A 경로 | 계정 1의 A 캠페인과 제외되지 않은 X·제외할 Y | 계정 운영자가 Y를 계정 공통 목록으로 저장 성공한 뒤 A 결과 선택을 시작 | Y는 결과에 없고, X를 포함한 나머지는 기존 선택 조건을 따른다. |
| AC-02 계정 공통 B 경로 | AC-01과 같은 계정 1, B 캠페인 | 저장 성공 뒤 B 결과 선택을 시작 | Y는 결과에 없고, 제외하지 않은 항목의 기존 조건은 유지된다. |
| AC-03 계정 격리 | 계정 1에는 Y가 저장되어 있고 계정 2에도 Y가 존재 | 각 계정에서 새 결과 선택을 시작 | 계정 1의 A/B에는 Y가 없으며, 계정 2의 결과는 계정 1 설정 때문에 바뀌지 않는다. |
| AC-04 저장 전 경계 | 계정 1에서 Y를 제외하려고 편집 중이나 아직 저장 성공 전 | 새 결과 선택을 시작 | 편집값만으로 Y를 제외하지 않는다. |
| AC-05 송출 경계 | Y가 포함될 수 있는 송출이 이미 시작되어 있고, 이후 계정 운영자가 Y 제외를 저장 성공 | 기존 송출을 관찰하고, 그 뒤 새 결과 선택을 시작 | 기존 송출은 유지되고, 새 선택에는 Y가 없다. |
| AC-06 전부 제외된 후보 | 승인된 계정 공통 목록이 해당 선택의 모든 후보를 제외 | 새 결과 선택을 시작 | 예외·재포함 규칙을 만들지 않으므로 제외된 항목은 결과에 나타나지 않는다. 결과가 비어 있을 수 있다는 것은 이 엄격한 요구의 귀결이며, 별도 대체 동작은 승인되지 않았다. |

실제 구현 단계에서는 위 사례에 A/B 경로의 실제 명칭, 고정된 입력 fixture, 승인된 명세 revision을 연결합니다. 동작 변경이므로 TST-001의 red/green/refactor 증거도 별도로 남겨야 합니다. 이 문서는 그 실행 또는 통과를 주장하지 않습니다.

## 별도 요청 A — 도움말 오타

‘제외목룍’ → ‘제외목록’ 정정은 intent-owner 승인이 계속 유효합니다. 기능 변경과 분리해, 다음 편집 단계에서 실제 사용자 노출 도움말 위치를 찾아 맞춤법만 수정합니다. 동작, 용어의 의미, 저장 형식, 링크와 키는 변경하지 않으며, 변경 diff 및 표시 확인으로 범위가 오타에 한정됐음을 검토합니다. 비동작 문서 변경이라는 근거와 승인 근거를 남기되, 이를 자동 검증 통과로 표현하지 않습니다.

## 실제로 읽은 출처와 한계

이번 턴에는 `inputs/PK-04-turn2.md`와 허용된 앞선 응답 `responses/PK-04-r4-turn1.md`를 읽었습니다. 1차에서 읽은 후보 지침은 `source/AGENTS.md`, `source/skills/spec-it-specify/SKILL.md`, `source/skills/spec-it-clarify/SKILL.md`, `source/templates/project/change-spec.md`, `source/templates/project/change-impact.md`, `source/templates/testing/acceptance-case.md`, `source/templates/testing/verification-run.md`, `source/rules/hitl/HITL-002.md`, `source/rules/governance/GOV-001.md`, `source/rules/governance/GOV-002.md`, `source/rules/testing/TST-001.md`입니다.

`inputs/PK-04.md`의 사실은 1차 응답에 기록된 범위에서만 이어 썼습니다. 그 밖의 `inputs`, `responses`, `review`, `.unlazy`, 원 작업공간, 메모리, 네트워크는 읽지 않았습니다. 따라서 실제 계정 모델·도움말 위치·저장 매체·호출 관계·프로젝트 manifest/lock/ADR은 미확인입니다. 구현, 자동 정책 판정, 테스트 실행, 저장 구조 변경은 수행하지 않았습니다.
