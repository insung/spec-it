# 제외 항목 처리 — 첫 기획 검토

상태: `clarifying`. 목표는 **사용자가 제외한 항목이 결과에 나타나지 않는 것**입니다. 누구에게, 어떤 범위로, 언제 적용할지는 아직 확정되지 않았습니다. 기능 코드와 프로젝트 문서는 수정하지 않았습니다.

## 확인한 사실과 기획 초안

- 원본: `inputs/PK-04.md`의 사용자 요청, 현재 소스 snapshot `q1`, 기존 분석 초안 설명, 역할별 발언, 별도 요청 A.
- `q1`에서 `save(campaignId, excluded)`는 `settings[campaignId]`에 값을 대입합니다. 현재 저장 구현의 키가 캠페인이라는 사실이며, 승인된 제품 의도라는 뜻은 아닙니다. 실제 영속 저장 여부도 알 수 없습니다.
- `routes`에는 A와 B가 있고 둘 다 각각 `chooseA`·`chooseB`를 거쳐 `activeItems(campaign, asset)`을 호출합니다. 두 함수에 직접적인 제외 처리나 `settings` 조회는 보이지 않습니다. `activeItems`의 내부가 없으므로 전체 시스템에 제외 처리가 없다고 단정할 수 없습니다.
- 기존 초안의 “캠페인별 목록을 저장한다”는 **미승인 해석**입니다. 최종 의도로 채택하지 않습니다.
- “즉시 적용”, “저장 후 적용”, “다음 송출부터 적용”은 서로 다른 결과를 낼 수 있습니다. 최신 발언이나 다수 의견으로 결정하지 않고, 아래 차이를 `intent-owner`가 결정하도록 정리합니다. 발언자의 의도를 특정 구현으로 확정해서 해석하지 않습니다.

제안하는 기본안은 “해당 캠페인을 관리하는 사용자가 제외 목록을 저장하면, 이후 새로 만드는 결과에서 A·B 모두 제외 항목을 제거한다”입니다. 대상 사용자·캠페인 단위·저장 후 적용은 모두 **제안**입니다.

정상 예시: 후보 X·Y 중 X를 제외하고 저장한 뒤 새 결과를 만들면 Y는 기존 선택 조건을 따르고 X는 나오지 않습니다. 반례: X가 후보 목록에 있다는 이유만으로 다시 선택되면 요구 위반입니다. 다만 저장 전 화면이나 이미 진행 중인 송출까지 바꾸는지는 아래 결정에 따라 달라집니다. 제외하지 않은 항목의 기존 자격·순서와 다른 설정은 유지하는 방향을 제안합니다.

## 발견한 경로와 조사 경계

| 대상 | 상태 | 근거와 다음 확인 |
| --- | --- | --- |
| A → chooseA → activeItems | open | q1에서 실제 함수 연결이 보임. 제외 요구의 적용 후보이며, 적용 범위 승인 필요 |
| B → chooseB → activeItems | open | A와 같은 형태의 별도 경로. B를 빼도 된다는 근거 없음 |
| save → settings[campaignId] | applies | 저장 단위 판단에 관련되는 현재 구현. 이 단위를 유지할지는 미결정 |
| activeItems 내부·settings 읽기·화면·송출 처리·기타 소비자 | unknown | 제공된 코드 밖이라 미관찰. 필터 위치·적용 시점·전체 경로 완전성 판단 불가 |
| 도움말 오타 수정 A | excluded | 기능 동작 변경 범위에서는 제외. 별도로 승인된 문구 작업으로 추적 |

`applies`는 조사 관련성을 뜻하며 승인이나 테스트 통과를 뜻하지 않습니다. A만 고치고 B를 놓치는 계획을 세우지 않겠습니다. 구현 준비 시 두 경로뿐 아니라 설정을 읽는 곳과 실제 결과를 내보내는 소비자까지 확인해야 합니다.

## 이번에 필요한 결정

기능 기준 확정 1건(제외 항목이 결과에 나오지 않아야 함), 중요 미결정 4건입니다. 이번 질문은 D1~D3 세 건이며, D4 예외 정책은 적용 범위와 시점 답변을 받은 뒤 결과를 바꾸는 예외만 묻겠습니다. 예상 잔여 질문은 이번을 포함해 2~3회이며, 현재는 첫 산정입니다. 별도 오타 수정의 승인은 이 집계와 분리합니다.

### D1. 이 기능을 사용하는 사람은 누구인가요?

추천은 해당 캠페인을 관리하는 사용자입니다. 실제 역할 이름은 확인되지 않았습니다. 운영 담당자만 설정한다면 운영 화면이 중심이고, 캠페인 관리자가 직접 설정한다면 관리 화면과 편집 권한이 달라집니다. 모든 사용자에게 허용하면 권한 범위가 넓어집니다. 지금 정해야 화면의 주체와 정상 사용 사례를 정할 수 있습니다.

### D2. 제외 설정은 어디까지 함께 적용되나요?

추천은 현재 저장 구현에 맞춘 캠페인 단위이며, 그 캠페인의 A·B 결과에 공통 적용하는 안입니다. 캠페인 전체에 적용하면 설정이 단순하지만 특정 자산만의 예외를 표현할 수 없습니다. 특정 자산별이면 더 세밀하지만 저장 키와 조회 계약이 달라질 수 있습니다. A·B별로 다른 제외를 원하면 두 결과가 달라지는 조건도 명시해야 합니다. q1은 캠페인 저장의 근거일 뿐 선택의 승인 근거가 아닙니다.

### D3. 어떤 순간부터 제외 항목이 사라져야 하나요?

추천은 **저장 성공 후 새로 만드는 결과부터 적용**하는 안입니다. 다음 세 장면에서 기대 결과를 `intent-owner`가 정해 주세요: X를 제외했지만 아직 저장하지 않은 상태, 저장한 뒤 새 결과를 만드는 상태, 저장 당시 이미 진행 중이던 송출.

| 선택 | 관찰되는 차이 | 비용·위험과 예상 변경 |
| --- | --- | --- |
| 저장 전부터 반영 | 미저장 편집만으로 결과가 바뀜 | 임시 상태 전달·취소 복원이 필요하며 저장 여부와 결과가 어긋날 수 있음 |
| 저장 후 새 결과부터 반영 — 추천 | 미저장 상태는 기존 결과, 저장 성공 후 새 결과는 제외 반영 | 저장 성공·조회 시점 연결 필요. 진행 중 결과에는 제외 항목이 남을 수 있음 |
| 다음 송출 경계부터 반영 | 저장 이후라도 다음 송출 시작 전까지 기존 동작일 수 있음 | 송출 경계와 설정 버전 관리가 필요. 즉시 반영을 기대하는 사용자와 차이 발생 |

“즉시”가 저장 전 편집만을 뜻하는지, 저장 직후를 뜻하는지, 진행 중 송출 변경까지 뜻하는지는 발언만으로 알 수 없습니다. 진행 중 송출도 바꾸려면 별도의 중단·교체 동작이 필요할 수 있고 실제 가능 여부는 송출 구현을 조사해야 합니다.

세 질문의 답은 대상·적용 범위·적용 시점과 정상/반례 시나리오를 바꿉니다. 예상 구현 영향은 권한·화면, 저장 키/읽기, A·B 선택 및 송출 경계이나 정확한 파일은 미확인입니다. 현재는 실행 변경이 없어 되돌릴 것도 없습니다. 이후 복구는 이전 제외 설정 복원과 이전 선택 로직 복귀를 후보로 검토하되, 이미 송출된 결과는 소급 복구할 수 있다고 가정하지 않습니다. 근거는 위 q1과 역할별 발언이며 비용 수치는 아직 산정하지 않았습니다.

기능 검증은 승인된 범위를 기준으로 A·B 각각에서 제외 항목 미노출, 제외하지 않은 항목의 기존 동작, 다른 설정 범위의 유지, 저장 전후 및 송출 경계 차이를 관찰하도록 계획합니다. 전부 제외된 경우의 기대 결과는 D4 전에는 만들지 않습니다. 아직 테스트를 작성하거나 실행하지 않았으며, 사전 실패나 통과 증거는 없습니다.

기획 지침으로 `spec-it-specify`·`spec-it-impact`·`spec-it-clarify`를 사용했습니다. 읽은 후보 규칙 중 `HITL-001`은 이 기능의 미확정 동작 변경을 보류하는 근거이고, `HITL-002`는 이번 결정 묶음의 구성 근거입니다. 행동 변경의 `TST-001`은 승인 후 검증 계획 후보입니다. 프로젝트 manifest/lock과 고정 정책 버전은 제공되지 않았으므로 이는 `shadow assessment`이며 정책 채택이나 준수 판정이 아닙니다. 프로필도 확정할 수 없습니다. 중요 미결정이 0이 되면 `spec-it-converge`가 다음 단계이며, 지금은 clarify가 필요합니다.

## 별도 요청 A의 진행

오타 수정은 동작·용어 의미·저장 형식을 바꾸지 않고 이미 승인됐으므로 별도 기능 의사결정이나 재승인이 필요하지 않습니다. 비동작 변경이라는 면제 사유를 기록하고, 실제 도움말 위치를 확인해 해당 문자열만 바꾼 다음 변경 차이와 표시 문구를 확인하면 됩니다. 기능의 D1~D4를 기다릴 이유는 없습니다. 다만 이번 요청은 코드를 고치지 않는 읽기 전용 기획 검토이므로 실제 수정은 수행하지 않았습니다. 기능 테스트나 과도한 명세 절차를 이 오타 작업에 부과하지 않습니다.
