이제 의도는 **“계정 운영자가 저장한 계정 공통 제외 목록을, 저장 성공 뒤 시작하는 계정 내 A·B의 모든 선택에 적용한다”**로 확정해 이해했습니다. 이미 시작한 송출은 유지하고, 다른 계정에는 영향을 주지 않습니다. 요청대로 구현하지 않았습니다.

앞선 ‘캠페인별 목록’ 해석과 추천은 이번 intent-owner 답변으로 **대체됨(superseded)** 처리합니다. 예전 해석을 승인된 요구였던 것처럼 남기지 않겠습니다. `spec-it-specify`의 초안과 `spec-it-clarify`의 결정 기록에 반영할 내용은 다음과 같습니다. 이번에는 프로젝트 파일을 만들거나 수정하지 않고 응답으로만 정리합니다.

| 결정 | 확정한 내용 | 승인 근거 |
| --- | --- | --- |
| D1 사용자·적용 범위 | 계정 운영자가 사용하는 계정 공통 목록. 계정 내 A·B 캠페인 모두 적용하며 다른 계정에는 영향 없음 | 두 번째 답변의 intent-owner 명시와 범위 정정 |
| D2 적용 시점 | 저장 전 편집값은 적용하지 않음. 저장 성공 뒤 시작하는 선택부터 적용. 이미 시작한 송출은 유지 | 두 번째 답변의 시점·진행 중 송출 지시 |
| D3 예외·유지 조건 | 별도 예외 없음. 제외하지 않은 항목의 기존 선택 조건 유지 | 두 번째 답변의 예외 및 유지 조건 지시 |

주요 기능 결정은 **해결 3묶음, 미결정 0묶음**, 현재 질문 0건, 예상 추가 결정 라운드 0회입니다. 앞서 예상한 추가 질문은 이번 답변에서 사용자·범위·시점·예외가 함께 해결되어 필요 없어졌습니다. 구현 전 기술 조사에서 새로운 중대한 경계가 실제로 발견되는 경우에만 그 차이를 다루겠습니다.

예를 들어 계정 U의 운영자가 X를 제외 목록에 추가했지만 아직 저장하지 않았다면, A·B의 새 선택에는 기존에 저장된 목록이 적용됩니다. 저장이 성공하면 그 뒤 시작하는 A·B의 선택에서는 X가 나오지 않습니다. 그 전에 이미 시작한 X의 송출은 중단하거나 교체하지 않습니다. 계정 V의 선택은 U의 저장 때문에 바뀌지 않습니다.

이번 정정의 관찰 가능한 차이는 **U의 공통 목록에 한 번 저장한 제외가 U의 A·B 캠페인 모두에 적용된다는 것**입니다. 설정 화면의 실제 위치는 아직 확인하지 않았습니다. X가 A에서는 빠지고 같은 계정 B에서는 다시 선택되거나, U의 제외 때문에 V에서 X가 사라지는 것은 모두 실패입니다. 비제외 항목 Y는 기존 조건에 따라 선택될 수 있지만, X가 빠졌다는 이유만으로 Y의 자격·우선순위를 새로 바꾸거나 Y의 선택을 보장하지는 않습니다.

검증할 사례는 다음과 같습니다. 아래는 승인된 의도에서 도출한 **검증 계획**이며 실행 결과가 아닙니다.

| 사례 | 조건과 동작 | 기대 결과 |
| --- | --- | --- |
| S1 계정 공통 제외 | U에서 X 제외 저장 성공 후, U의 서로 다른 A·B 캠페인에서 새 선택 시작 | A·B 모두 X를 선택하지 않음. 같은 계정 내 모든 적용 캠페인에서 제외 결과가 일관됨 |
| S2 저장 전 편집 | 저장된 목록에는 X가 없고, 편집 화면에서만 X를 추가한 상태로 A·B 새 선택 시작 | 편집값이 효력을 갖지 않음. X는 기존 조건을 만족하면 여전히 선택 후보가 될 수 있음 |
| S3 저장 실패 | X 추가 저장이 실패한 뒤 A·B 새 선택 시작 | 마지막으로 저장에 성공한 목록을 적용. 실패한 편집값으로 제외 결과가 바뀌지 않음 |
| S4 진행 중 송출 | X의 송출이 이미 시작된 뒤 X 제외 저장 성공. 이어서 새 선택 시작 | 진행 중 X 송출은 유지. 저장 성공 뒤 시작한 새 선택에서는 X 제외 |
| S5 계정 간 격리 | U에서만 X를 제외 저장하고 U·V의 A·B 결과 비교 | U에서는 X 제외. V는 자신의 목록과 기존 선택 조건을 유지하며 U의 변경을 받지 않음 |
| S6 비제외 항목 유지 | X를 제외하고 Y·Z는 제외하지 않은 상태에서 선택 | Y·Z의 기존 자격·선택 조건 유지. 제외 기능이 새 자격이나 우선순위를 만들지 않음 |
| S7 후보 전부 제외 | 기존 조건을 만족하는 후보를 전부 제외하고 저장 성공 뒤 새 선택 시작 | 제외 항목을 예외로 되살려 선택하지 않음. 선택 가능한 항목이 남지 않는다는 결과를 확인 |
| S8 제외 해제 | X가 저장된 제외 목록에 있다가 제거 편집 후 저장 성공 | 저장 전에는 X 제외 유지. 저장 성공 뒤 새 선택부터 X가 기존 조건에 따라 다시 후보가 될 수 있음 |

S7의 “제외 항목을 되살리지 않는다”는 별도 예외가 없다는 승인에서 도출한 기준입니다. 후보가 없을 때의 화면 문구·빈 응답 표현·기존 무후보 처리 방식은 q1로 확인되지 않습니다. 기존 처리를 조사하여 승인된 기준을 만족하는지 확인하고, 임의의 보충 송출 정책을 추가하지 않겠습니다. 확률적 선택이라면 V나 Y가 특정 실행에서 반드시 선택되었는지가 아니라, 제외 적용과 기존 선택 조건이 유지되는지를 검증해야 합니다.

q1에서 확인된 `routes.A → chooseA → activeItems`, `routes.B → chooseB → activeItems`는 이제 모두 승인된 적용 대상(`applies`)입니다. **코드가 같아 보인다는 이유로 한 경로만 검증하면 안 됩니다.** 다른 계정은 이번 계정 설정의 영향 범위에서 `excluded`이며, 그 근거는 이번 intent-owner의 계정 격리 지시입니다. 다른 계정의 경로도 변경 영향이 없다는 회귀 검증에는 포함합니다.

q1의 `settings[campaignId]`는 캠페인 키를 쓰는 현재 코드 관찰로 남습니다. 계정 공통이라는 승인과 어떻게 맞출지는 다음 기술 조사 대상입니다. 계정 식별을 어디서 얻는지, 설정의 실제 저장·읽기 위치, A·B의 다른 호출자, 저장 성공과 선택 시작 경계를 확인해야 합니다. `activeItems` 내부와 실제 소비자가 없어 지금 저장 키 변경만으로 충분하다고 결론 내릴 수 없으며, DB 변경이나 데이터 이전이 반드시 필요하다고도 단정할 수 없습니다. 이런 발견 가능한 사실을 다시 사용자에게 설계 선택 질문으로 넘기지는 않겠습니다.

기존 검증 계획의 캠페인 단위 격리 가정은 계정 단위 격리로 고치고, A·B 공통 적용·저장 전후·진행 중 송출·다른 계정 회귀를 이번 승인에 연결합니다. 번호를 확장해 다시 정리한 대응은 이전 S1 → 이번 S1, 이전 S2 → 이번 S2·S3·S4, 이전 S3 → 이번 S5·S6, 이전 S4 → 이번 S7이며, 이번 S8은 해제 시점 확인을 위한 추가 사례입니다. 앞선 계획은 당시 초안으로 보존하되 최종 수용 기준으로 재사용하지 않습니다. 아직 실행한 검증이 없으므로 폐기할 과거 ‘통과 결과’도 없습니다. 향후에는 승인된 사례를 기준으로 구현과 논리적으로 분리한 검증을 수행하는 계획입니다.

오타 수정 `제외목룍 → 제외목록`의 승인은 그대로 유효하고 재승인은 필요 없습니다. 동작·용어 의미·저장 형식이 변하지 않는 별도 오타 작업으로 진행할 수 있습니다. 이번에는 결과와 검증 사례를 설명하고 구현하지 말라는 요청에 따라 실제 파일 수정은 하지 않았습니다. 실행할 때 해당 도움말 문자열만 고치고 diff와 표시 결과를 확인하면 되며, 본 기능의 기술 조사와 묶어 지연시킬 이유는 없습니다.
