# 완료 여부와 후속 조치 검토

M1은 원본 의도 누락으로 완료 처리할 수 없습니다. M2는 B의 실행 증거가 없어 완료 판단을 보류해야 합니다. M3은 제공된 승인 범위와 실행 조건에서 완료로 판단할 수 있습니다. 검토 횟수는 이 판단을 바꾸지 않습니다.

제공된 평가본의 `spec-it-check`와 `spec-it-impact`를 각각 수동 `quick` 검토와 `completion` 영향 검토에 적용했습니다. 프로젝트별 manifest/lock과 고정 정책 버전은 제공되지 않았으므로 정책 검토는 `shadow assessment`입니다. 아래 규칙 ID는 검토 근거를 설명하는 후보 매핑이며, 해당 프로젝트가 채택한 정책의 위반을 확정하는 판정은 아닙니다. 행동 완료 여부는 제공된 승인 의도와 관찰을 직접 대조해 판단했습니다.

## 변경별 판정

| 변경 | 결과 | 근거와 끊긴 연결 | 필요한 후속 조치 |
| --- | --- | --- | --- |
| M1 | `fail` — 원본 요구의 파생물 반영 실패; B 동작은 미확인 | intent-owner가 승인한 req-r1은 A/B 모두를 포함하지만 spec-r1은 A만 포함합니다. trace-r1 내부 연결과 run-A 통과는 이 누락을 드러내지 못합니다. A 제외 결과와 비제외 유지에 대한 관찰은 유효하지만, B의 명세·사례·실행 증거가 없습니다. A helper만 고쳤다는 설명은 B가 같은 경로를 사용한다는 근거가 아닙니다. | req-r1의 B 요구를 파생 명세와 수용 사례에 복원하고, 실제 B 선택 경로와 helper의 미변경 소비자를 조사합니다. B에 구현 누락이 확인되면 그 경로를 수정합니다. A/B의 실제 선택 결과와 관련 비제외 유지 조건을 사람 소유 기준에서 독립 검증하고 새 run으로 연결합니다. |
| M2 | `human-review` — B 실행 증거 부족 | 승인 의도는 A/B 제외 및 비제외 유지를 요구합니다. A-excluded `[]`, A-allowed `[i1]` 관찰만 있고 B는 미실행인지 기록 누락인지도 알 수 없습니다. 검토 10회는 B 결과를 대신하지 않습니다. | B 실행 경로를 확인하고 B-excluded와 B-allowed의 예상값·실제값을 남깁니다. A/B 결과의 승인 기준 revision, 대상 build, 환경·fixture, 확인자와 독립 검증 맥락도 연결합니다. 현재 자료만으로 B 코드 결함을 단정해 수정하지 않습니다. |
| M3 | `pass` — 제공된 범위의 수동 행동 완료 판정 | 승인 의도에서 지원 유형을 A/B로 닫았고, inventory-r2와 runtime 등록도 이에 일치합니다. qa-1의 run-3은 의도 rev2, build b3, 환경 e3, fixture f3에서 A/B 각각 제외·비제외 네 결과의 예상값과 실제값 일치를 제공합니다. 별도 경로 selectA/selectB 모두에 관찰이 있습니다. | 이 표를 run-3의 원문 증거로 참조하고 승인 범위·버전·조건·확인자를 상위 기록에 남기면 됩니다. 제공된 범위의 완료를 위해 검토 횟수를 늘리거나 다른 유형을 가정해 추가 실행할 필요는 없습니다. |

M1은 원본→파생 명세 방향으로 B가 사라졌고, 파생 명세·테스트→원본 방향으로 되짚어도 B를 설명할 수 없습니다. TST-002가 다루는 ‘구현자가 만든 테스트만을 유일한 정답으로 사용하는 문제’에 해당하는 검토 신호입니다. 파생 명세를 보완하면서 원본의 A/B 범위를 새 의도처럼 다시 승인받을 필요는 없지만, 조사 중 새로운 의미 차이가 드러나면 그 차이만 결정자에게 넘겨야 합니다. 비제외 유지가 M1 원본에 명시적으로 승인되었는지는 알 수 없으므로, A에서 관찰된 회귀 조건과 B에서 확인할 회귀 후보를 원본 요구와 구별해 기록합니다.

M3에서는 네 선택 결과가 기획 적합성과 ‘실제 선택에서 제외된다’는 고객 목적을 함께 뒷받침합니다. 검토 1회라는 이유로 이 증거를 낮게 평가하지 않습니다. DB는 사용하지 않는 순수 함수이므로 DB 검증은 `not-applicable`입니다. 다른 배포 환경, fixture, 승인 revision 및 탐색 경계의 안정성까지 증명한 것은 아닙니다. 이 한계는 해당 실행 범위의 통과를 취소하는 사유가 아닙니다. 자동 정책 validator의 통과나 현재 배포 상태를 확인했다는 의미도 아닙니다.

## 결함별 수정 대상과 수정 뒤 남길 증거

### D1 — 적용 시점에 대한 동급 승인 문서 충돌

상태는 `human-review`이며, 우선 수정할 대상은 의도 결정과 그 결정을 표현하는 제품 명세·디자인·관련 계약입니다. 같은 승인 수준이므로 문서 종류만 보고 한쪽을 우선하거나 현 구현을 정답으로 삼을 수 없습니다. GOV-001·GOV-002가 관련되며 결정자는 지정된 intent-owner입니다.

결정 요청에는 두 문서의 해당 절과 revision, 승인 근거를 함께 붙이고 다음 두 의미를 비교해야 합니다.

- 저장 직후 적용: 저장 이후 같은 실행의 선택에도 새 제외 설정을 적용하는지, 이미 선택한 결과까지 다시 계산하는지 적용 경계를 정해야 합니다.
- 다음 실행부터 적용: 현재 실행은 시작 당시 설정을 유지하고 다음 실행에서 새 설정을 사용합니다. 변경 반영이 늦어지는 동작을 사용자에게 설명해야 합니다.

추천은 먼저 ‘저장 성공 뒤 현재 실행에서 새로 선택하는 경우’와 ‘다음 실행을 시작하는 경우’를 구체적 수용 사례로 만들어 intent-owner가 적용 시점을 결정하도록 하는 것입니다. 현재 자료로 두 의미 중 하나를 제품의 정답으로 추천할 근거는 부족합니다. 적용 지연과 실행 중 결과 변경의 영향을 함께 제시하고, 예상 수정 범위는 두 문서·설정 안내·선택 경로·수용 사례로 한정해 조사합니다. 되돌림은 선택한 의미에 맞춘 구현 변경의 복구 방법과 이미 진행된 선택의 처리 가능성을 확인해야 하며, 현재는 코드·환경 자료가 없어 미확정입니다. 이는 HITL-002에 따른 결정 묶음이며 이번 검토에서 결정을 대신 내린 것은 아닙니다.

수정 뒤에는 충돌 원문 참조, 결정 내용·소유자·승인 revision, 문서 정정 이력, 해당 시점의 회귀 사례, 구현 수정이 있었다면 commit/build, 새 QA run과 재확인자를 남깁니다. 기존 run을 바뀐 적용 시점의 통과로 재해석하지 않습니다.

### D2 — 승인된 제외 동작 실패

상태는 `fail`입니다. 승인 기준에서 제외되어야 하는 a9가 실제 결과에 남았고, 해당 분기에 제외 조회가 없다는 구체적 구현 누락이 있습니다. 우선 수정 대상은 그 선택 분기의 코드와 관련 제외 처리 연결입니다. 기대값을 a9 포함으로 바꾸는 방식은 승인 의도를 훼손합니다.

해당 분기에서 승인된 제외 설정이 최종 선택 결과에 반영되도록 수정하고, 같은 로직의 caller·미변경 소비자에서 우회가 있는지 확인해야 합니다. 제외 조회 부재는 직접 조사·수정할 결함 단서이지만 이것만이 유일한 원인이라고 단정할 필요는 없습니다.

수정 뒤에는 a9가 남은 원래 실패 run과 재현 입력을 보존하고, 수정 commit/build, 승인 시나리오와 연결한 a9 회귀 사례, 비제외 선택 유지 확인, 새 run의 예상값·실제값·환경·fixture·확인자를 연결합니다. TST-002 관점에서 구현자 설명만으로 닫지 않고 독립 맥락에서 최종 선택 결과를 재확인해야 합니다. 이번 검토에서는 수정이나 재실행을 하지 않았습니다.

### D3 — fixture에 따라 달라지는 실패, 원인 미확정

관찰된 f4 실행 실패는 `fail`, 원인과 수정 대상 판단은 `human-review`입니다. 동일 build b3에서 f3 성공·f4 실패가 관찰되었지만 데이터 차이와 배포 환경 차이가 조사되지 않았으므로 코드·데이터·환경 중 하나를 확정 원인으로 기록할 수 없습니다. f4의 정확한 기대값과 실제 실패 내용도 보완해야 합니다.

우선 두 run의 승인 기준, build 식별자, 설정·의존성·환경, fixture 내용과 생성 경로를 비교합니다. 가능한 격리 환경에서 동일 조건에 f3/f4를 각각 실행해 데이터 차이를 좁히고, 필요하면 같은 fixture를 서로 다른 환경에서 실행해 환경 차이를 분리합니다. f4가 승인된 입력 범위에 속하는지도 확인해야 합니다. 이 확인 없이 실패 fixture를 버리거나 기대값을 성공하도록 바꾸지 않습니다.

수정 위치는 조사 결과에 따라 코드 분기, 잘못된 fixture·데이터 생성, 환경·배포 설정으로 확정합니다. 외부 인프라·공유 상태·운영 유래 데이터를 사용하는 재현이라면 TST-006의 격리·데이터·부수효과 경계가 적용 후보가 됩니다. 현재 자료만으로 DB나 운영 데이터를 사용한다고 가정하지 않습니다.

수정 뒤에는 f3 성공과 f4 실패를 모두 보존하고, 확인한 차이·원인·수정 대상을 뒷받침하는 증거, 수정 revision/build, 관련 회귀 사례, 같은 승인 기준으로 재실행한 두 조건의 결과와 QA 재확인자를 남깁니다. 원인 미확정 상태에서 ‘수정 완료’로 닫지 않습니다.

## 상위 변경 이슈에 남길 내용

각 독립 프로젝트의 기존 상위 변경 이슈에서 다음 연결을 유지하면 됩니다. 전용 QA 저장소나 새 서식 파일을 의무로 만들 필요는 없습니다.

`승인 원본@revision → Scenario/Case@revision → 실행 경로 → 실패 run → 결함 → 결정·수정 revision → 새 run → QA 재확인자`

완료 코멘트에는 ‘어떤 승인 버전·build·환경·fixture에서 어떤 예상 결과와 실제 결과가 일치했는지’, 증거 위치, 확인자, 남은 실패·미확인 범위를 적습니다. 구현 revision과 QA 코드 revision은 해당되는 경우 연결하고, 관찰 표가 원문인 경우 그 표를 그대로 참조하면 됩니다. 없는 revision·실행 시각·확인자를 만들지 않습니다. D1의 의도 변경은 새 사례 revision과 후속 run으로, D2/D3의 수정은 이전 실패를 보존한 새 run으로 연결합니다. 세 결함의 수정·재확인은 아직 수행되었다는 자료가 없으므로 현재 시점에는 완료 문구를 기록할 수 없습니다.

같은 유형의 사고가 다른 프로젝트에서 반복되었다는 증거는 없습니다. 이번 결과는 각 프로젝트의 결정·결함·회귀 기록으로 남길 사안이며, 새 공통 규칙이나 정책 강화의 필요성을 입증하지 않습니다. 공통 정책 개정과 프로젝트별 수정은 별도 판단입니다.

## 관찰 범위와 한계

입력은 `inputs/PK-02.md`에 제공된 텍스트 snapshot뿐입니다. M1의 req-r1/spec-r1/trace-r1, M3의 inventory-r2·의도 rev2·run-3 식별자는 제공된 그대로 사용했습니다. M2와 결함의 별도 source revision, 실제 저장소 HEAD·dirty 상태, 구현·QA 원문, 승인 및 실행 시각은 제공되지 않았습니다. `observed_at`의 정확한 시각·시간대도 이번 제공 자료에는 없어 미확인으로 남깁니다. source 파일과 입력을 읽었지만 실제 실행·외부 원문 조회·자동 validator는 수행하지 않았습니다.

새 승인 revision, build/commit·dirty 상태, 지원 유형·routing/runtime 등록, fixture·환경이 바뀌거나 추가 caller·계약이 발견되면 해당 연결과 결과의 현재 사용 가능 여부를 재검토해야 합니다. 접근할 수 없던 원문이 제공되거나 다음 세션에서 이 보고서를 재사용할 때에도 관련 원본을 다시 확인해야 합니다. 과거 run은 그 당시의 결과로 보존합니다. 독립 프로젝트 사례 사이에서 동일 문자열의 build ID만으로 같은 산출물이라고 간주하지 않았습니다.

수동 검토의 결과 의미를 모델링하면 전체에는 의사결정·필수 증거 공백에 해당하는 `2`가 남습니다. 이는 실제 checker의 프로세스 종료 코드가 아니며, 정책 채택 여부도 불명확하므로 정책 위반 exit `1`을 확정한 것은 아닙니다.

파일 경로 목록은 관련 자료를 찾기 위해 source 안에서 조회했으며, 위 목록 외 파일의 내용을 검토했다고 주장하지 않습니다. 프로젝트 코드·정책·서비스는 수정하지 않았고, 이 응답 파일만 평가 harness의 지정 경로에 저장했습니다.
