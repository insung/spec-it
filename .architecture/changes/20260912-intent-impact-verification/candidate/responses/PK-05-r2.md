# PK-05 — 현재 변경 영향 조사 및 인계

현재 구현의 영향은 수정되지 않은 `select-b`에도 이어진다. 설정 파일은 `filterFlag=true`, `missingSettings=deny`로 바뀌었지만, 제공된 코드에는 이 두 값을 읽는 경로가 없어 실제 적용을 입증할 수 없다. 제품 의도와 deny 승인 근거가 없으므로 현재 구현을 정답이나 승인된 정책으로 채택하지 않는다.

## 조사 기준

- 모드: `shadow assessment`에서 brownfield·late-entry를 기본으로 이전 관측과의 delta를 조사했다. 문서 허브·manifest·lock이 없다는 입력을 기준으로 하며, 정책 준수 합격/불합격이나 정책 채택 완료를 선언하지 않는다.
- `observed_at`: 2026-09-15 00:57:34 UTC / 2026-09-15 09:57:34 Asia/Seoul. 이번 파일 조사 시각이며 과거 승인 시각이 아니다.
- 조사 root: `/private/tmp/spec-it-candidate-WygDiD`. 과제 입력은 `inputs/PK-05.md`만 읽었다. 현재 소스는 `app/`의 아래 6개 파일 전체를 직접 읽고 `allowed|choose|filterFlag|missingSettings|excluded|asset|config`를 검색했다.
- 사용 지침: `source/skills/spec-it-impact/SKILL.md`, 선택적 기록 형식 `source/templates/project/change-impact.md`. 후보 정책 `source/VERSION`은 `0.4.0`이다. 이 버전 문자열만으로 설치·고정 또는 후보 파일 묶음의 동일성을 증명하지 않는다.
- 완독한 후보 규칙: `source/rules/testing/TST-001.md`, `source/rules/hitl/HITL-001.md`, `source/rules/architecture/ARCH-005.md`, `source/rules/architecture/ARCH-006.md`, `source/rules/testing/TST-006.md`. 관련성 탐색으로 `source/rules/{project,testing,hitl,architecture}` 및 `GOV-004.md`에서 키워드 검색도 했다. 전 규칙을 완독한 정책 감사는 아니다.
- 다른 inputs의 내용, 과제 정답 사본, 기존 responses/review, 원 작업공간, 메모리, 네트워크는 조사하지 않았다. Git 조회나 테스트 실행도 하지 않았다. `app-c1/c2`, `patch-d1/d2`는 입력이 제공한 합성 식별자이며 실제 Git commit/HEAD가 아니다.

## 영향 관계와 조사 상태

`applies/excluded/open/unknown`은 조사 상태다. 자동 검증 결과나 check-report enum이 아니다. 아래 시나리오는 이번 조사의 식별용 이름이며 기존 승인된 Scenario ID를 뜻하지 않는다.

| 후보 시나리오·경계 | 상태 | 근거와 영향 |
| --- | --- | --- |
| 제외 목록에 asset.id가 들어 있는 경우 → `allowed` → A 선택 | applies | `shared.ts:2`, `select-a.ts:3`. 배열에 ID가 있으면 helper는 false, A는 `[]`를 반환하는 코드다. 이전 true 구현과 달라지는 동작이다. 실행 결과가 아닌 정적 추론이다. |
| 동일 입력 → `allowed` → B 선택 | applies | `select-b.ts:3`에서도 실제 호출한다. 파일이 미변경이어도 helper 동작 변경을 받는다. 이전에 조사하지 않았다는 이유로 제외할 수 없다. 포함되지 않은 ID면 A/B 각각 `['item-a']`/`['item-b']`를 반환하는 코드다. |
| 호출자가 A/B를 실행하는 상위 경로·배포 | unknown | 함수 내부의 실행 관계는 확인했지만 A/B를 호출하는 진입점, 라우팅, 배포 자료는 6개 파일에 없다. 실제 서비스에서 둘 다 실행된다고 단정할 수 없다. |
| config → filterFlag 분기 | unknown | 값이 false→true로 바뀐 사실은 확인했다. 6개 파일 검색에서 읽기·쓰기·로드 연결이 없고 A/B는 조건 없이 helper를 호출한다. flag가 실제 실행을 제어하거나 특정 경로를 끈다는 주장은 불가능하다. |
| missingSettings 누락 처리 의도 | open | allow→deny는 관측된 설정 변경이다. deny가 뜻하는 반환값·오류·사용자 경험 및 승인권자의 선택이 없다. 다른 세션의 변경을 되돌리거나 승인으로 해석하지 않는다. |
| missingSettings 설정의 실제 적용 | unknown | 설정 소비·기본값 적용 코드가 없다. 현재 함수는 `settings.excluded` 및 `excluded.includes`에 직접 접근한다. settings 또는 excluded가 누락되면 예외가 날 수 있으며, 이것을 승인된 deny 처리라고 간주할 수 없다. |
| 디자인 rev3 저장 실패 → 재시도 | open / unknown | 원본 revision 변화는 재검토 사유다. 버튼·재시도 의도와 승인 범위는 open, 저장·UI·재시도 구현과 관측 증거는 unknown이다. 화면 diff가 없다는 이유만으로 영향 없음 처리하지 않는다. |
| 외부 feed 계약 → 입력 → 선택 | unknown | rev2 사본 존재 설명만 있다. 입력 타입/누락 값 의미/최신 계약과 코드 사이의 매핑을 확인할 수 없다. |
| 공유 라이브러리 → 원격 서비스 C | unknown | 관계 메모만 있고 C 저장소·사용 버전·호출 경로는 미접근이다. C의 미확인을 근거로 확인된 A/B 영향까지 무효화하지 않는다. |
| 현재 테스트 관찰 경계 | applies: 증거 공백 | `package.json:1`에는 scripts·runner가 없으며 `tests/source.test.ts:1`은 이전 실행 기록·현재 runner가 없다는 주석뿐이다. 실행 가능한 assertion이나 성공/실패 run을 확인하지 못했다. |

승인이나 실행 근거로 제외할 수 있는 후보 경로는 이번 조사에서 없다. 범위 밖 자료는 `excluded`로 바꾸지 않고 미접근/미관측으로 남겼다.

## 과거 기록의 현재 사용 가능 여부

과거 기록은 삭제·수정하지 않는다. `filterFlag=false`, 기본값 allow는 당시 관측이며 현재 config의 근거로는 만료되었다. A→helper 관계는 현재 소스로 재확인하여 계속 사용할 수 있다. 과거에 조사하지 않은 B가 새로 확인되었다. 디자인 rev2 기준의 결과는 rev3의 저장 실패·재시도 시나리오에 관해 재검토가 필요하다. feed rev2가 최신이라는 증거는 처음부터 없으며 현재도 unknown이다.

일부 구현은 이미 완료되었다는 개발자 진술과 현재 코드만 있다. 사전 기획 승인, 사전 실패 테스트, 과거 실행 결과는 복구되지 않았다. 향후 명세·회귀 테스트를 작성하더라도 그 시점의 사후 증거로 남겨야 하며 과거 승인이나 TDD red 단계로 소급하면 안 된다. 후보 TST-001의 관점에서 증거 공백은 설명할 수 있지만 미채택 프로젝트에 위반 판정을 소급하지 않는다.

## 다음 담당자에게 인계할 결정과 검증

1. 제품 의도 담당자가 제외 목록 적용의 대상(A/B/C), flag의 역할, 설정 누락 시 기대 동작을 결정하고 근거 위치·revision·승인 시점을 남겨야 한다. 현재 코드와 누락값 예외를 요구사항 대신 사용하지 않는다.
2. 디자인/제품 담당자가 rev3의 재시도 버튼이 이번 변경 범위에 속하는지, 저장 실패와 결과 미확인을 어떻게 구분할지, 재시도 시 중복 저장을 어떻게 다룰지 정한다. 저장 경로를 확인하기 전 특정 복구 구조나 인프라를 강제하지 않는다. 후보 ARCH-005는 상태 변경 경로 확인 후 검토할 관점이다.
3. 다음 조사자는 config 로더·설정 기본값·상위 caller·저장 및 UI 경로·feed 계약 원본을 확보한다. C 담당자에게는 라이브러리 버전, 호출 위치, 누락값 계약과 회귀 증거를 확인할 인계 항목을 남긴다. 이번에는 외부 연락을 수행하지 않았다.
4. 승인된 의도를 기반으로 재현 가능한 테스트 실행 환경을 마련하고, 제외 ID/비제외 ID/빈 목록, A/B 양쪽, settings 및 excluded 누락, flag·설정 기본값의 실제 연결을 검증한다. 디자인 범위가 확정되면 저장 실패·재시도 결과와 중복 실행도 검증한다. 기대값이 미결정인 사례는 먼저 결정해야 한다. C·feed는 계약과 접근 범위에 맞는 별도 증거가 필요하다.
5. 시작 기준은 이번 현재 6개 파일과 digest다. 과거 동작 재현이 필요하면 c1 및 patch-d1 자료부터 확보한다. 제공된 diff로 사후 재현을 하더라도 재현 범위와 생성 시점을 표시한다. 테스트 계획을 테스트 통과로 보고하지 않는다.

`spec-it-specify` 역할로 의도 초안을, `spec-it-clarify` 역할로 위의 중요한 미결정을 인계할 수 있다. 정책 투영은 승인 후 `spec-it-converge`, 고정 규칙 판정은 이후 `spec-it-check`의 역할이다. 이번에는 이 스킬들을 실행하거나 manifest/lock·관계 저장소·문서 허브를 생성하지 않았다. 후보 HITL-001은 미결정에 의존하는 구현 전 판단이 필요하다는 근거이며, 읽기 전용 조사나 승인 범위가 명확한 무관한 작업을 막는 근거로 확대하지 않는다.

## 재검토 조건과 종료 범위

- 새 세션/재개: 현재 `app/`의 6개 digest 및 snapshot/working-change 식별자를 다시 대조한다.
- app-c2·patch-d2 내용 변경, 특히 다른 세션의 `config.json` 변경: helper·A/B·설정 경로에 해당하는 결론을 갱신한다. 실제 Git을 사용하는 후속 환경에서는 HEAD뿐 아니라 미커밋 내용도 식별한다.
- 디자인 revision 또는 승인 변경: rev3 저장 실패·재시도 영향과 승인 범위를 대조한다.
- feed의 최신 계약 확보·변경: 입력/누락값 계약과 선택 동작의 관계를 다시 본다.
- 새 caller·설정 소비 코드·저장 경로 발견, C 접근 가능: 해당 경계를 추가 조사하고 기존 결론과 연결한다.
- 테스트 환경/run 확보: 코드로 추론한 동작과 실제 관찰을 구분하여 갱신한다.

이번 종료는 제공된 6개 파일에서 확인한 관계, 미결정과 미접근 영역을 다음 작업자가 다시 찾을 수 있다는 의미다. 전체 경로 발견, 외부 변경 자동 감지, QA 완료, 정책 채택을 보장하지 않는다. 프로젝트 소스·설정은 변경하지 않았고 요청된 조사 응답 파일만 작성했다.
