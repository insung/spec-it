# 배포 전 QA 계획 — PK-06

## 결론

현재 상태에서는 **QA를 실행할 준비와 릴리스 승격 준비가 모두 끝나지 않았다**. 신규 화면을 개발자가 확인한 사실은 참고 증거이지만, 구·신 클라이언트 혼재, API payload 변화, DB schema 변화, 서버 롤백을 검증하지 못하므로 배포 승인 근거로는 부족하다.

가장 큰 차단 위험은 서버 복구 계획이 v1인데 client v2가 배포된 뒤 서버만 v1로 되돌리면, architecture-owner가 명시적으로 미지원으로 정한 `client v2 / server v1` 조합이 만들어진다는 점이다. 따라서 기능 QA 전에 배포 순서와 client v2 차단·복구 방법을 확정해야 한다.

이 계획은 QA 환경을 실행하거나 변경하지 않은 읽기 전용 `preflight` 결과다.

- `observed_at`: 2026-09-15T09:51:56+09:00
- 확인한 정책 후보: 제공된 source snapshot의 `VERSION 0.4.0`
- 정책 적용 상태: 프로젝트 manifest/lock 및 채택 승인을 확인하지 못했으므로, 아래 규칙 참조는 확정된 프로젝트 준수 판정이 아니라 **shadow assessment와 QA 설계 근거**다.

## 1. 확인된 사실과 아직 증명되지 않은 것

### 확인된 기록

- 지원 조합: `client v1 / server v1`, `client v1 / server v2`, `client v2 / server v2`
- 미지원 조합: `client v2 / server v1`
- 배포 중 client v1과 v2가 혼재한다.
- server v2는 새 column `excluded_ids`를 읽는다.
- client v1은 `{value}`, client v2는 `{value, excludedIds}`를 전송한다.
- QA 데이터는 synthetic fixture만 쓴다.
- QA DB 시작 상태는 db1이고 신규 DDL 적용 상태는 db2다.
- 준비됐다고 기록된 신규 artifact는 server `s2`, client `c2`다.
- 운영 가이드 오타 수정은 동작·계약을 바꾸지 않으며 intent-owner가 승인했다.

### 아직 증명되지 않은 것

- `s1`, `s2`, `c1`, `c2`의 immutable digest와 실제 배포 identity
- DDL의 정본, checksum, 적용 순서, 실행 주체, lock, post-apply 검증, recovery class
- server v2의 column 없음·NULL 처리 및 client v1 payload의 `excludedIds` 누락 의미
- client v1 저장 이후 기존 `excluded_ids`를 보존할지, 비울지, NULL로 만들지
- server v1이 db2 및 `excluded_ids`가 기록된 행과 안전하게 공존하는지
- stage의 목적, 격리, 접근, 외부 side-effect 차단, 정리/TTL, 비용 한도, 중단 조건
- 사람 소유 수용 기준에 대한 구현 맥락과 분리된 검증 결과

## 2. QA 실행 전에 닫아야 할 결정 관문

아래 네 묶음은 의존 순서대로 결정해야 한다. 결정되지 않은 기대값을 테스트 코드나 현재 구현에서 역으로 만들어서는 안 된다.

### D1. 저장 계약과 호환성 의미

결정 owner: intent-owner, architecture-owner, data-owner

다음을 API/DB 계약에 명시해야 한다.

1. `{value}`처럼 `excludedIds`가 **누락**된 요청의 의미
2. `excludedIds: null`, 빈 배열, 값이 있는 배열의 서로 다른 의미와 허용 여부
3. db2로 전환된 기존 행에서 `excluded_ids = NULL`의 읽기 결과
4. client v1 저장이 이미 기록된 `excluded_ids`를 보존하는지
5. server v2가 db1의 column 없음 상태에서 동작해야 하는지, 아니면 배포 gate로 그 상태를 금지할지

권고 기본값은 legacy client의 필드 누락을 “새 필드 변경 없음”으로 처리하고, client v1의 저장이 `excluded_ids`를 지우지 않게 하는 것이다. 이것이 기존 consumer 때문에 새 데이터가 조용히 소실되는 위험을 가장 작게 한다. 다만 제품 의도에 따라 “항상 비움”이 맞을 수 있으므로 owner 승인 없이는 기대값으로 확정할 수 없다.

### D2. 배포 순서와 복구 전략

결정 owner: architecture-owner, data-owner, release/operations owner

권고 순서는 다음 expand-first 흐름이다.

1. checksum이 고정된 DDL로 db1을 db2로 확장
2. `server v1 / db2`의 호환성을 확인한 뒤 server `s2` 배포
3. `client v1 / server v2`를 확인한 뒤 client `c2`를 점진 배포
4. 혼재 구간과 주요 지표를 관찰한 뒤 승격

이 순서를 쓰려면 `server v1 / db2`가 안전하다는 증거가 필요하다. 반대로 s2를 DDL보다 먼저 배포하려면 `server v2 / db1`의 column 없음 처리가 승인된 계약이어야 하고 그 조합을 별도로 검증해야 한다.

서버 롤백 권고는 **db2를 유지한 채, client v2를 먼저 회수하거나 feature gate로 저장을 차단한 후 s1로 되돌리는 것**이다. client v2가 남아 있는 상태에서 s1만 복구하는 절차는 승인된 미지원 조합을 만들므로 허용하면 안 된다. 새 값이 기록된 후 `excluded_ids` column을 즉시 제거하면 데이터가 사라질 수 있으므로, DB 복구는 단순 down migration으로 가정하지 말고 `expand-contract 또는 forward-fix` 후보로 분류해 승인해야 한다. 실제 recovery class는 DDL과 쓰기 의미를 본 뒤 data-owner와 architecture-owner가 확정한다.

### D3. DB release unit

결정 owner: data-owner, architecture-owner

QA 전에 다음을 하나의 고정 release definition으로 묶는다.

- object decision owner, DDL definition authority, executor
- DDL 원본 revision/path, 대상 DB/schema/object, 실행 순서와 checksum
- 호환되는 application artifact 및 DB 상태 범위
- 단일 실행/serialization과 migration history 방식
- 실행 전 stop condition, post-apply schema/data 검증
- `reversible`, `expand-contract/forward-fix`, `replayable`, `restore-dependent` 중 recovery class
- db2를 유지한 server rollback과 DB까지 되돌리는 절차를 분리한 복구 기대값

QA 실행 결과는 release definition 자체를 바꾸지 않고, 해당 digest를 참조하는 별도 environment history로 남긴다.

### D4. stage 안전 계약

결정 owner: intent-owner, architecture-owner, data-owner 및 해당되는 security/operations owner

synthetic fixture만 사용한다는 점은 확정됐지만 충분하지 않다. 실행 전에 다음을 채운다.

- 목적: DB/API contract 검증인지, 실제 배포·network/IAM 경계 검증인지
- 격리 단위: 전용 DB/schema/namespace/account 등과 병렬 실행 충돌 방지
- 접근 주체와 허용 egress
- email, webhook, scheduler, queue 등 외부 side-effect가 있다면 production sink 차단
- fixture owner, 초기화, 매 run cleanup, 임시 자원의 TTL
- 관찰 지표와 abort condition, 중단 권한자, 허용 blast radius
- 예상 실행 시간과 비용 상한

이 항목이 승인되기 전에는 현재 QA DB에 DDL을 적용하거나 stage를 실행하지 않는다.

## 3. 버전·전이 QA 매트릭스

| ID | Client | Server | DB | 분류 | 확인 목적 |
| --- | --- | --- | --- | --- | --- |
| M1 | c1 | s1 | db1 | 기준선, 필수 | 기존 읽기·저장 회귀와 fixture 기준값 확보 |
| M2 | c1 | s1 | db2 | 전이/복구, 조건부 필수 | DB-first 배포와 s1 rollback 시 기존 동작 및 새 column 보존 |
| M3 | c1 | s2 | db2 | 지원 조합, 필수 | 구 client payload 누락 처리, 기존 값과 NULL 처리 |
| M4 | c2 | s2 | db2 | 지원 조합, 필수 | 신규 화면, 신규 payload, 저장·재조회·회귀 |
| M5 | c1+c2 혼재 | s2 | db2 | 배포 현실, 필수 | 교차 저장 순서와 새 데이터 소실 여부 |
| M6 | c1 | s2 | db1 | 배포 순서가 허용할 때만 필수 | column 없음 처리; 금지 상태라면 실제 배포 gate 증거로 대체 |
| G1 | c2 | s1 | db1/db2 | **미지원, 정상 통과 대상 아님** | rollout/rollback이 이 조합에 도달하지 않도록 gate·feature flag·client 회수 절차 검증 |

M2는 공식 client/server 지원표를 새로 확장한다는 뜻이 아니라, 제안한 DB-first 배포와 server rollback이 실제로 만드는 DB 전이 상태의 검증이다. M6도 선택한 배포 순서에 따라 `applies` 또는 `excluded`로 확정하고, 제외 시 결정자와 gate 근거를 남긴다.

## 4. 테스트 사례 묶음

### A. DB migration과 post-apply 검증

synthetic fixture를 최소 다음 상태로 고정한다.

- 빈 데이터셋
- 기존 `value`가 있는 db1 행
- 기존 `value`가 NULL인 db1 행
- db2에서 `excluded_ids`가 NULL, 빈 값, 값이 있는 행

각 상태에서 확인할 항목:

1. db1 → db2 DDL 적용 전 checksum·현재 schema·lock 선행 조건
2. DDL 실행 결과와 migration history 기록
3. column 이름, 타입, NULL/default 제약 등 실제 정의가 승인본과 일치하는지
4. 기존 `value`와 행 수가 보존되는지
5. 기존 행의 `excluded_ids` 초기 상태가 승인 계약과 일치하는지
6. 실패 또는 중단 시 승인된 stop/recovery 절차가 동작하는지
7. 지원 대상이라면 빈 DB에서 db2 신규 설치 결과와 upgrade 결과의 등가성
8. 중복 적용이 안전하게 거부·인식되고 동시 실행이 serialization되는지

SQL 명령 성공만으로 통과시키지 않고 schema/data post-apply 결과와 application compatibility를 별도로 판정한다.

### B. API 계약과 저장 의미

- c1의 정확한 `{value}` 요청을 s1과 s2에 보내 동일한 기존 결과를 얻는다.
- c2의 `{value, excludedIds}` 요청을 s2에 보내 저장 후 새 세션/재조회에서도 값이 유지되는지 본다.
- 누락, NULL, 빈 배열, 값이 있는 배열을 승인된 의미대로 구분한다.
- 잘못된 타입, 허용되지 않은 ID, 중복 ID 등 제품 계약에 존재하는 유효성 경계를 확인한다.
- 응답 status/body와 실패 시 DB 상태를 함께 관찰한다.
- retry나 동시 저장이 가능한 API라면 중복·stale·부분 실패 의미를 승인 계약대로 확인한다.

### C. 구·신 client 혼재와 데이터 보존

다음 순서 기반 사례가 핵심이다.

1. c1 저장 → c2 조회
2. c2가 `excludedIds` 저장 → c1 조회
3. c2가 `excludedIds` 저장 → c1이 `value` 수정 → c2 재조회
4. c1과 c2가 같은 대상을 연속 또는 동시에 저장
5. NULL/빈 값이 있는 기존 행을 c1과 c2가 각각 열고 저장

특히 3번에서 `value`만 바뀌고 `excluded_ids`가 승인 없이 사라지지 않아야 한다. 동시성 정책이 아직 없다면 해당 사례의 기대값을 먼저 owner 결정으로 돌린다.

### D. UI와 독립 수용 검증

- c2 신규 화면에서 빈 데이터, 기존 값, NULL, exclusion 없음/있음의 표시를 확인한다.
- 수정, 저장, 새로고침/재진입 후 표시와 실제 API/DB 관찰을 연결한다.
- c1의 기존 화면·저장 흐름이 s2/db2에서 그대로 동작하는지 회귀 확인한다.
- 구현자가 확인한 화면 결과를 유일한 oracle로 쓰지 않는다. 사람 소유의 수용 기준을 고정한 뒤 구현 결론이 주입되지 않은 별도 검증 context에서 관찰한다.

### E. 배포와 복구 rehearsal

고정 artifact와 DDL digest를 사용해 선택된 순서를 rehearsal한다.

1. db1 + s1 + c1 기준 확인
2. db2 전환 후 s1/c1 확인
3. s2 배포 후 c1 확인
4. c2 점진 배포 후 c1/c2 혼재 확인
5. c2로 `excluded_ids`가 기록된 상태에서 client v2 회수/차단
6. s1로 rollback하되 db2 유지
7. c1 읽기·저장, 이후 s2 재승격 및 `excluded_ids` 보존/승인된 손실 여부 확인

DB까지 되돌리는 rehearsal은 D3에서 별도 절차가 승인된 경우에만 수행한다. 승인 없이 column drop을 복구로 간주하지 않는다.

### F. 부하·용량 검증 범위

입력에는 성능·용량 또는 critical path 변화가 명시되지 않았으므로 광범위한 load test를 자동으로 요구하지 않는다. 다만 실제 DDL이 큰 테이블 lock, 긴 실행 시간, 추가 query 비용을 만들 가능성이 있거나 선택된 risk profile이 trigger한다면 migration rehearsal과 위험 기반 부하 증거를 추가한다. 축소 stage와 synthetic fixture의 통과를 운영 용량 증명으로 표현하지 않는다.

## 5. 실행 기록과 합격 기준

각 run은 다음을 보존한다.

- case/suite revision과 사람 승인 수용 기준
- c1/c2/s1/s2 및 DDL의 immutable identity
- client/server 지원 조합, DB 상태, fixture revision
- stage 목적·격리·sink·cleanup·비용·abort 계획
- 실행 시각, 실제 관찰, 상태, 증거 위치, 독립 확인자
- 결함 수정 전 run을 덮어쓰지 않은 후속 재검증 연결

릴리스 합격 조건은 다음과 같다.

- M1~M5가 승인된 기대값을 충족하고, M6는 통과하거나 배포 gate로 도달 불가가 증명됨
- G1(`c2/s1`)이 rollout과 rollback에서 도달 불가함
- db1 → db2 적용 및 post-apply 검증과 recovery rehearsal이 성공함
- c1 저장이 `excluded_ids`를 어떻게 다루는지 승인된 계약과 관찰이 일치함
- stage cleanup/TTL과 비용 한도 준수가 확인됨
- 미결정·미확인 항목이 릴리스 성공으로 뭉뚱그려지지 않음
- 구현 맥락과 분리된 verifier가 사람 소유 수용 기준에 대해 결과를 확인함

하나라도 충족하지 못하면 해당 조합과 환경을 `blocked` 또는 `not-run`으로 남기고 승격하지 않는다. 이 문서 작성 자체는 테스트 실행이나 승인 증거가 아니다.

## 6. 운영 가이드 오타 수정의 QA 범위

제품 변경과 같은 DB/API/호환성 QA는 **필요하지 않다**. 동작·계약을 바꾸지 않는 한 글자 오타이며 intent-owner 승인도 있으므로, 별도 소규모 문서 검증으로 충분하다.

- 실제 diff가 승인된 한 글자와 주변 문맥만 바꾸는지 확인
- 링크, 명령, 식별자, 코드 예시의 의미가 우연히 바뀌지 않았는지 확인
- 문서 생성물이 있다면 정상 render/build되는지 확인
- 비동작 변경 사유와 TDD·통합 테스트 비적용 근거 기록

같은 릴리스에 포함된다는 이유만으로 이 오타가 제품 변경의 QA 매트릭스를 추가로 확장하지는 않는다. 반대로 제품 변경에 필요한 QA를 오타의 단순성으로 축소해서도 안 된다.

## 7. 재검토 조건

다음 중 하나가 바뀌면 관련 결론과 case revision을 다시 대조한다.

- API 계약 또는 누락/NULL/쓰기 의미 결정
- DDL 내용·checksum·순서·recovery class
- c1/c2/s1/s2 artifact identity나 dirty 상태
- 배포/rollback 순서, feature gate 또는 client 회수 방법
- stage 구성, 접근 권한, 외부 의존성, 비용·abort 조건
- 새 client/server/consumer 발견 또는 지원 조합 변경
- 새 세션에서 QA 실행을 재개하거나 기존 증거의 출처 revision이 바뀜

### 관찰 한계

- 입력 문서와 위 source snapshot 외에는 읽지 않았다. 프로젝트 저장소, manifest/lock, 코드, API 명세, DDL, artifact, pipeline, QA/stage 환경, 로그, 기존 테스트와 운영 데이터에는 접근하지 않았다.
- source의 `VERSION 0.4.0`은 확인했지만 source commit/digest와 프로젝트의 채택 revision은 확인하지 못했다. 따라서 특정 규칙이 해당 프로젝트에 이미 승인·고정됐다고 판정하지 않았다.
- QA나 DDL을 실행하지 않았고, 환경·코드·정책·서비스를 수정하지 않았다. `s2`, `c2`가 실제로 준비됐는지와 어떤 digest인지도 재검증하지 않았다.
- 제공된 지원 조합은 승인 기록으로 받아들였지만, 알려진 consumer 전체 목록이나 실제 호출 경로의 완전성은 검증하지 못했다.
- 권고 배포 순서와 recovery class는 현재 기록에서 도출한 안전 제안이며, DDL 및 구·신 server의 실제 쓰기 동작을 본 확정 사실이 아니다.
