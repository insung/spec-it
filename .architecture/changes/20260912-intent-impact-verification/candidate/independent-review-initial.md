# 사용자 의도와 후보 구현의 독립 감사

## 범위와 결론

검토 입력은 `review/user-requests.md`와 `source/`의 관련 스킬·규칙·설명·템플릿·예제·자기 투영 파일뿐이다. 원 작업공간, 메모리, 네트워크, `inputs/`, `responses/`, `.unlazy/`, 기존 평가 결론은 읽지 않았다. 실행 응답 재현이나 운영 QA를 수행하지 않은 정적 의미 감사다.

**핵심 요구는 대부분 후보의 실행 지침에 반영됐다. 다만 규칙에 없는 의도 검토 의견을 지속 보관하는 `check` 계약에 P2 충돌 하나가 있다. 실제 모델 행동 개선, 최초 사고 원인 확정, 이번 작업의 자기 적용 완료는 이 범위에서 입증되지 않는다.** 이 세 항목의 미확인을 곧바로 후보 소스의 구현 누락으로 판정하지 않는다.

아래의 ‘반영’은 해당 행동을 지시하는 구체적 소스가 있다는 뜻이다. 실제 실행 성공·자동 활성화·원문 전체 무누락을 뜻하지 않는다.

## 발견 사항

### IV-01 — P2 · 지침 충돌 / 지속 추적의 누락: 규칙 밖 검토 의견을 저장할 자리가 없다

- 관련 사용자 의도: 기획·디자인·구현·QA를 추적하고 누락 및 고칠 대상을 다음 작업자가 알 수 있어야 한다 (`review/user-requests.md:31-33`, `:49`).
- 후보는 고정 정책 의무가 없는 검토 의견을 `advisory observations`로 분리하라고 한다 (`source/skills/spec-it-check/SKILL.md:18`). 출처 관측 시각·dirty 상태·미접근·재검토 조건과 끊긴 연결도 보고해야 한다 (`:20`).
- 하지만 같은 스킬은 저장 파일을 요청받은 `.spec-it/reports/`의 보고서 하나로 제한하고 (`:12`, `:20`), 그 보고서는 기존 JSON schema를 따라야 한다 (`:32`).
- 해당 schema는 모든 결과에 `rule_id`를 요구한다 (`source/schemas/check-report.schema.json:26-35`). 루트의 임의 속성을 금지하고 (`:6-7`), `summary`에도 숫자 카운터만 허용한다 (`:14-24`). 규칙 밖 의견이나 보고서 전체의 조사 맥락을 독립적으로 담는 자리도 없다.
- 재현 조건: 사용자가 의도 검토 결과의 저장을 요청했는데, QA 통합 상태나 고객 목적 관련 권고처럼 잠긴 규칙 위반이 아닌 관찰만 발견한다. 현재 계약대로면 의견을 버리거나, 관련 없는 규칙 ID에 억지로 붙이거나, schema/파일 저장 제약을 어겨야 한다. 기존 규칙의 `message` 안에 추가 설명을 넣는 방법은 관련 규칙이 실제로 있는 경우에만 자연스럽고, 이 조건을 해결하지 못한다.
- 영향: 대화에서는 발견한 공백이 다음 세션용 기록에서 사라질 수 있고, 임의 규칙 연결은 선택 절차를 정책 의무처럼 보이게 한다. 사용자 요구 중 지속 추적과 QA 영역 비강제가 같은 지점에서 충돌한다.
- 수정 방향: 공개 schema를 이번 후보에서 유지하려면 정책 판정 JSON과 의도 검토 인계를 구분하고, 호출자가 기존 권한 안에서 별도의 기존 변경 기록에 advisory/조사 맥락을 남길 수 있다는 예외를 `check`에 명시한다. 또는 schema 확장을 별도 호환성 결정으로 다룬다. 임의 rule ID 추가로 우회하지 않는다.
- 심각도 근거: 읽기 전용 대화 검토 자체를 막지는 않지만 저장을 요청하는 정상 사용 경로와 세션 간 인계를 깨뜨리므로 P2다.

## 도입·부작용·자동화 표현의 판단

- **새 보편 QA 의무의 과잉 도입은 확인하지 못했다.** 선택 템플릿과 기존 규칙의 적용을 구별한다 (`source/docs/intent-and-verification.md:3,49`, `source/docs/migrations/0.4.0-to-0.5.0.md:7-11`). 다만 선택적 형식이라는 뜻이 이미 고정된 TST/GOV 규칙까지 선택 사항으로 만든다는 뜻은 아니다.
- **실행 비용과 운영 데이터 부작용의 경계가 있다.** 위험에 맞는 범위, 격리·fixture·sink·cleanup·비용·중단 조건을 기존 TST-003/TST-006/DATA-009에 연결한다. 운영 QA의 실제 실행 권한을 새로 부여하는 표현은 확인하지 못했다.
- **후보 채택에는 수동 인계 유지 비용이 남는다.** 변경 기록의 위치·원본 접근·revision 확보·기록 저장 주체를 실제 프로젝트가 정해야 한다. 스킬이 읽혔다는 것만으로 분산 도구의 상태가 모이지 않는다. 후보는 이 한계를 숨기지 않는다 (`source/docs/intent-and-verification.md:33-45`).
- **자동화되었다고 오해하기 쉬운 지점을 대부분 명시적으로 차단했다.** instruction-only, 미구현 validator/CI, watcher 부재, 합성 run, 자동 스킬 선택 미검증, 정책 digest와 스킬 동일성 차이를 직접 밝힌다 (`source/docs/intent-and-verification.md:3,39,45,51`, `source/examples/intent-verification/README.md`, `source/docs/migrations/0.4.0-to-0.5.0.md:11,28`). README의 흐름도는 목표 작업 흐름으로 읽어야 하며 실행 로그가 아니다.
- **알려진 self lock 불일치는 도입 시 주의 사항이다.** 후보가 이를 공개적으로 기록하고 있으므로 새로 발견한 숨은 누락으로 세지 않는다. 최종 채택/발행 전에 해결 또는 검토 상태의 명시가 필요하다. 이번 단계에 승인되지 않은 발행이나 전역 설치를 요구할 근거로 사용해서는 안 된다.

## 원문 발췌와 이번 검토의 한계

`review/user-requests.md:3`이 밝히듯 첨부 사고 문서, 주석의 정확한 대상 위치, 과거 대화 전체와 중간 AI 제안은 제공되지 않았다. “좋아”, “계획에 동의”가 승인한 구체적 범위 전체를 재구성할 수 없다. 따라서 특정 답변의 약속이 빠졌다고 추정하거나 원 사고 원인을 확정하지 않았다.
