신규 화면 확인은 개발자의 관찰 증거입니다. 배포 전 QA에서는 승인된 구·신 클라이언트 조합, 기존 데이터의 읽기·쓰기, DB 변경, 서버 복구 이후까지 별도로 검증해야 합니다. 현재는 저장 의미·DB 복구·배포 순서·환경 조건이 미정이므로 배포 준비 상태는 `human-review`입니다. 실제 QA 환경을 실행하거나 수정하지 않았습니다.

제공된 정책 스냅샷은 참고 기준이며 이 제품이 채택한 manifest·lock·risk profile은 제공되지 않았습니다. 따라서 아래는 `shadow assessment`에 기반한 QA 계획이며, 제품의 정책 준수·위반을 확정한 결과는 아닙니다. `spec-it-clarify`로 필요한 결정을 정리하고 `spec-it-check`의 증거 구분을 적용했습니다. Phase 0의 계획이나 수동 검토를 자동 검사 통과로 표현하지 않습니다.

## 1. 검증 기준과 범위

QA의 기준은 intent-owner가 승인한 동작과 architecture-owner가 승인한 지원 조합입니다. 구현 코드나 개발자가 만든 테스트의 기대값만을 정답으로 삼지 않습니다. 동일인이 검증하더라도 구현 결론을 전달받지 않은 별도 검증 세션에서 승인된 수용 기준에 따라 관찰합니다(TST-002).

| 클라이언트 / 서버 | 승인된 범위 | QA 계획 |
| --- | --- | --- |
| client v1 / server v1 | 지원 | 기존 `{value}` 저장·재조회 기준선을 확인하고, 배포 전 및 복구 후 도달하는 DB 상태에서 회귀 검증 |
| client v1 / server v2 | 지원 | `excludedIds`가 없는 요청, 기존 값·null 데이터, v2가 저장한 데이터를 v1이 다시 수정하는 경로 검증 |
| client v2 / server v2 | 지원 | `{value, excludedIds}` 저장·재조회, 신규 화면 결과, 기존 데이터에서 신규 기능으로 넘어가는 경로 검증 |
| client v2 / server v1 | 명시적 미지원 | 정상 기능 호환성 합격을 요구하는 대상은 `not-applicable`. 다만 배포·복구 중 이 조합에 트래픽이 도달하지 않게 하거나, 승인된 미지원 안내·차단 동작이 작동하는지는 별도 검증 |

client v2/server v1의 미지원 결정을 다시 승인받을 필요는 없습니다. 해결할 것은 서버 복구 시 client v2가 남아 있는 상황의 처리 방식입니다.

DB 버전은 위 조합과 별도의 축입니다. db1은 현재 QA DB 상태, db2는 신규 DDL의 결과일 뿐, 각 서버가 모든 DB 상태를 지원한다는 증거는 없습니다.

- server v1/db1: 현재 동작의 기준선. 실제 실행 증거는 아직 없습니다.
- server v2/db2: 이번 릴리스의 주요 검증 대상입니다. null 및 쓰기 의미를 먼저 확정합니다.
- server v2/db1: column 없음 처리가 미정입니다. 이 상태를 허용할지, 배포 전 호환성 검사로 실행·트래픽을 막을지 결정합니다. 지원하지 않는 상태에서 기능 정상 동작을 임의로 요구하지 않습니다.
- server v1/db2: DB를 유지한 채 서버만 복구하거나 DB를 먼저 확장할 경우 필요한 검증 대상입니다. v2가 쓴 데이터까지 포함해 읽기·쓰기와 보존 여부를 확인해야 하며, 현재 호환된다고 단정할 수 없습니다.

## 2. QA 시나리오와 필요한 증거

아래 항목은 모두 계획이며 실행 결과는 `human-review`입니다. API·DB 경계 변경이 있으므로 신규 화면 확인이나 단위 테스트만으로 통합 검증을 대체할 수 없습니다(TST-003, COMP-001).

| 검증 묶음 | 수행할 시나리오 | 판정 기준과 증거 |
| --- | --- | --- |
| 기존 기능 회귀 | client v1의 `{value}` 저장·재조회, 기존 화면 결과 | 승인된 기존 수용 기준, 요청·응답, 저장 전후 DB 값 |
| 데이터 상태 | 빈 테이블/대상 레코드 없음, 기존 `value` 보유, null 포함 데이터를 구분한 synthetic fixture | fixture ID·초기 schema·초기 값·최종 값. column 없음과 column의 null은 별도 사례 |
| 신규 입력 경계 | `excludedIds` 생략·명시적 null·빈 배열·유효한 값. 잘못된 타입 등은 승인된 API 계약에 따라 포함 | 각각 유지·초기화·거절 중 승인된 기대 결과와 실제 응답·DB 결과. 기존 계약에 없는 의미를 QA가 정하지 않음 |
| 필드 연결 | API의 `excludedIds`와 DB의 `excluded_ids` 사이 저장·조회 mapping | 실제 응답과 DB 값의 대응. 새 물리 column 명명은 프로젝트 DB 규약 확인 후 검토(DATA-010) |
| 혼재 클라이언트 | 동일 레코드를 v2 저장 → v1 수정 → v2 재조회. 역순 및 동시 수정도 승인된 충돌 처리 기준에 맞춰 확인 | 기존 `value`와 신규 제외 목록이 의도대로 유지·변경되는지 확인. v1이 필드를 보내지 않았다는 이유로 신규 값을 지우는지 특히 관찰 |
| DB upgrade | synthetic db1에서 DDL을 적용해 db2가 되는 과정과 기존 데이터 보존. 신규 설치 경로를 지원한다면 빈 DB 설치도 포함 | 정확한 DDL identity, 적용 전후 정의, 이력·직렬화 결과, 데이터 검증. SQL 성공과 릴리스 준비 완료를 구분 |
| 실패와 복구 | 적용 실패·중단에 대한 승인된 중지/재개 절차, v2 쓰기 전과 후의 서버 복구, 복구 중 client v1/v2 접근 | 복구된 서버·DB 조합, 접근 제어/미지원 안내, 기존·신규 데이터 보존 또는 승인된 손실, 소요 시간 |
| 배포 산출물 | stage에 s2·c2를 배포한 결과와 환경 설정·의존성 경계 | digest와 source revision, 실제 배포 identity, 설정 identity, 테스트 실행 identity를 연결 |

관찰 기록은 `수용 기준 ID → 지원 조합 및 DB 상태 → fixture → 절차 → 기대값 → 실제값 → 확인자 → 증거 위치`로 남깁니다. 서버·클라이언트 v1도 정확한 복구 artifact를 식별해야 재현 가능한 검증이 됩니다. s2·c2라는 이름만으로 immutable identity가 입증되지는 않습니다(CICD-001).

동작 변경의 기존 red/green/refactor 기록도 확인합니다(TST-001). 사전에 실패하는 테스트를 만들었다는 증거가 없으면 사후 테스트를 TDD 증거로 꾸미지 않고, 기록 부재와 필요한 예외 판단을 남깁니다. 이번 요청은 계획 작성이므로 테스트를 새로 실행하지 않습니다.

## 3. 환경과 실행 순서

환경 실행 전 TST-006의 다음 항목을 채워야 합니다.

- 목적과 격리: 실제 DB 엔진을 사용하는 로컬/CI 격리 검증과, 배포 artifact·중요 외부 경계를 확인하는 stage의 역할을 구분합니다. 엔진·버전·의존성·설정·실제/대체 의존성을 명시합니다.
- 데이터와 접근: synthetic fixture만 사용합니다. fixture 생성·복원·정리 담당자와 접근 주체를 정합니다. 운영 자료 반입은 이번 범위에 없으며 마스킹 승인을 새로 요청할 필요도 없습니다.
- 외부 효과: 실제 존재하는 이메일·결제·webhook·queue·scheduler 등을 조사하고 테스트 sink 또는 비활성화 방법을 지정합니다. 운영 목적지로 나가지 않는 증거를 남기고, 없는 경계는 사유와 함께 제외합니다.
- 비용과 중단: 실행 예상 시간·비용, 승인된 비용 상한, 오류·부하·격리 이탈 시 중단 조건, 감시·중단 책임자를 명시합니다. 임의의 수치를 합격선으로 만들지 않습니다.
- 정리: 데이터·인프라 TTL, fixture 초기화·삭제 방법, 실패 시에도 정리할 담당자, 정리 완료 증거를 정합니다. 테스트 정리와 제품 DB 복구는 별개로 기록합니다.

권장 검증 순서는 ① 계약·복구 기준 확정 ② 격리된 기준선과 API/DB 통합 검증 ③ db1→db2 upgrade 및 구·신 데이터 검증 ④ 동일 s2·c2를 사용한 stage 배포·혼재 클라이언트 검증 ⑤ 새 데이터가 있는 상태의 복구 리허설 ⑥ 독립 검증 결과와 잔여 위험 검토입니다. 실제 제품 배포 순서는 아직 승인되지 않았으므로 이 검증 순서를 배포 결정으로 취급하지 않습니다.

부하 검증은 위험 profile 또는 성능·용량 변화가 요구할 때 범위를 정합니다(TST-004). 신규 column만으로 일률적인 전면 부하 테스트를 요구하지도, 화면 1회 성공으로 용량을 입증하지도 않습니다. DDL lock·실행 시간, 조회·쓰기 비용과 데이터 크기 증가가 판단에 영향을 주는지 조사해야 합니다. 실행 대상으로 결정되면 workload·환경 차이·시간·합격선과 함께 latency 분포, 처리량, 오류·포화, 단위 비용, 준비·분석·복구 시간을 기록합니다(TST-005). 축소된 synthetic stage 결과로 운영 용량을 확정할 수는 없습니다.

## 4. 필요한 결정

현재 명시적으로 정해진 결정 묶음은 5개입니다: 지원 조합, client v2/server v1 미지원, synthetic 전용 데이터, 서버 v1 복구 방향, 비동작 오타 수정 승인. 열린 결정 묶음은 5개이며, 이번에 먼저 정할 항목은 Q1~Q3입니다. Q4~Q5는 선행 답변에 따라 구체화합니다. 예상은 2~3회이며 이는 문답 계획이지 완료 약속이 아닙니다. 코드·DDL·환경 증거를 확인하면서 새 제약이 발견되면 이유와 함께 갱신합니다.

| 결정 | 지금 필요한 이유와 권장안 | 대안·비용·위험 | 승인 및 변경될 자료 / 복구 영향 |
| --- | --- | --- | --- |
| Q1. 저장·조회 의미와 서버/DB 지원 범위 | 구버전 요청의 필드 생략이 신규 데이터를 지우는지 판정할 기준이 없습니다. 권장 초안은 생략 시 기존 제외 목록 유지, 빈 배열은 명시적 해제, DB null은 승인된 기본값으로 읽기입니다. 명시적 요청 null의 허용·거절과 기본값의 업무 의미는 intent-owner가 확정해야 합니다. server v2/db1 지원 여부도 명시합니다. | 생략 시 초기화는 구현이 단순할 수 있지만 v1 사용자가 신규 데이터를 지울 수 있습니다. column 없음까지 fallback을 지원하면 배포 조합이 늘지만 검증 복잡도가 증가합니다. db2를 필수로 하면 호환성 gate가 필요합니다. | intent-owner·architecture-owner·data-owner. API·데이터 계약, mapping, 수용 기준에 반영합니다. 실제 변경 diff는 구현 확인 후 산정하며, 신규 쓰기 이후 되돌릴 때 데이터 의미를 보존해야 합니다. 현재 증거는 payload와 지원 조합 기록뿐입니다. |
| Q2. 새 데이터 기록 후 DB 복구와 client v2 처리 | 서버 v1 복구만으로 DB 및 client v2 상태가 해결되지 않습니다. 권장 후보는 db2를 보존하는 확장 방식과 server v1/db2 호환 검증입니다. 복구 중 v2 트래픽은 승인된 차단·안내 또는 검증된 호환 경로로 처리합니다. client v2/server v1 지원 자체를 새로 요구하지 않습니다. | 신규 column 제거는 이미 기록된 제외 목록을 잃을 수 있습니다. restore는 복구 시점 이후 다른 쓰기도 잃을 수 있어 허용 손실과 시간, 복원 검증이 필요합니다. 트래픽 분리는 운영 복잡도가 있고, 차단은 신규 클라이언트의 일시 사용 중단을 동반합니다. 실제 topology가 없어 어느 수단이 가능한지는 미확인입니다. | data-owner·architecture-owner, 허용 손실·중단은 intent-owner. DB release의 recovery class, RPO/RTO·backup/restore 방법·담당자, 클라이언트 대응과 복구 runbook을 확정합니다. DATA-009와 REL-001에 맞는 리허설 증거가 필요합니다. DDL 제거를 자동 rollback으로 약속하지 않습니다. |
| Q3. QA stage 운영 경계 | 환경 구성·격리·정리·비용 한도가 없어 실행 조건이 없습니다. 권장 후보는 격리된 임시 stage, synthetic fixture, 운영 연결 차단, 명시적 TTL·비용 상한·중단 담당자입니다. | 공유 stage는 비용을 줄일 수 있지만 다른 작업과 충돌·정리 범위를 통제해야 합니다. 임시 stage는 생성·정리 비용이 듭니다. 엔진·계정 등 확인되지 않은 인프라는 임의로 정하지 않습니다. | architecture-owner와 데이터·보안·비용 책임자. 환경 계획·접근/sink 설정·정리 절차가 바뀝니다. 복구는 fixture 초기화와 임시 자원 정리 범위로 기록합니다. 현재는 synthetic 사용만 확정되어 있습니다. |

후속 결정은 다음 두 묶음입니다. 아직 확정 요청을 앞당기지 않습니다.

- Q4. 배포 순서와 중지·복구 지점: Q1·Q2 뒤에 DDL→s2→c2와 같은 후보를 실제 지원 범위에 대입해 정합니다. DDL을 먼저 적용하려면 server v1/db2 검증이 필요하고, s2가 db1에서 동작하지 않는다면 s2를 먼저 승격할 수 없습니다. 신규 쓰기 활성화 시점과 v2 클라이언트 접근 조건까지 연결합니다. DB 객체 결정 소유자·정본·실행자, checksum·순서·호환 범위·직렬화와 환경별 이력을 고정합니다(DATA-009).
- Q5. 수용 기준·위험별 검증 수준: Q1~Q3 및 실제 변경 영향 조사 후 통합 테스트 수준, 부하 필요성, 성능·비용 합격선, 증거 유효기간과 재실행 조건을 정합니다. 미제공 manifest/profile을 먼저 확인할 수 있다면 기존 결정에서 가져오고, 없으면 채택된 정책인 것처럼 만들지 않습니다. 담당 확인자와 예외 승인 범위도 기록합니다.

위 권장안은 승인된 결정이 아닙니다. 답변 또는 명시적 위임을 얻은 범위만 결정 기록으로 옮기며, 중요한 미결정이 남아 있으므로 현재 `spec-it:converge`로 확정할 단계는 아닙니다.

## 5. 운영 가이드 오타 수정

한 글자 오타 수정은 제품 변경과 동일한 API·DB·호환성·복구·부하 QA가 필요하지 않습니다. 동작·계약을 바꾸지 않고 intent-owner가 승인했다는 근거를 별도 변경 기록에 연결하면 됩니다.

확인은 해당 한 글자 diff와 주변 문맥을 읽어 의미가 의도대로인지, 명령어·설정 값·링크 등 실행에 영향을 주는 내용이 바뀌지 않았는지 보는 범위로 충분합니다. TST-001의 비동작 변경 면제 사유와 확인자 기록을 남깁니다. 실제 diff를 제공받지 않았으므로 이 확인을 완료했다고 표시하지 않습니다. 같은 릴리스에 포함되었다는 이유만으로 제품 QA를 복제하지 않으며, 오타 승인이 제품 변경의 배포 승인을 대신하지도 않습니다.

배포 판단에는 승인된 수용 기준, 지원 조합별 독립 관찰, 정확한 artifact·DDL identity, 안전한 환경의 통합 결과, 새 데이터 쓰기 후 복구 증거가 필요합니다. 현재 확보된 것은 입력에 적힌 제품 기록과 개발자의 신규 화면 확인이며, 계획상의 검사를 통과했다고 보고할 근거는 없습니다.
