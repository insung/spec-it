현재 자료 기준으로 이 기능은 아직 완료되지 않았습니다. 승인된 적용 대상은 A·B이며, B는 저장된 제외 목록을 실제 선택에 반영하지 않습니다. A는 제외 항목 한 건의 결과만 확인됐고, 화면 재진입과 기존 선택 조건 보존까지 확인된 상태는 아닙니다. C는 확정 대상이라는 초기 보고가 정정되었으므로 추가 적용 여부를 미결정으로 남겨야 합니다.

이번 검토는 `spec-it-check`의 quick 방식과 `spec-it-clarify` 지침을 참고한 읽기 전용 **shadow assessment**입니다. 애플리케이션이 채택한 manifest·lock은 제공되지 않았으므로 정책 준수 여부를 판정하지 않습니다. 아래 규칙 ID는 검토 근거이며, 제품 요구 충족 여부와 정책 준수 여부는 구분합니다. 코드·서비스 변경이나 테스트 실행 없이 제공된 합성 자료만 수동 검토했습니다.

### 적용 범위와 확인된 상태

| 대상 | 관찰과 판단 | 남은 확인 |
| --- | --- | --- |
| A·B 설정 저장 | `settings-save-1`에서 두 유형의 `[a9]` 저장·조회가 통과했습니다. 이 관측 범위는 `pass`입니다. | 실제 화면에서 저장 후 닫았다가 다시 열어 유지되는지 확인해야 합니다. 함수 조회 결과만으로 화면 명세 충족을 단정할 수 없습니다. |
| A 실제 선택 | `strategyA`가 현재 캠페인 설정의 `asset.id`를 검사하고, `select-a-1`에서 제외된 a9의 결과가 `[]`였습니다. 해당 사례는 `pass`입니다. | 다른 캠페인과의 분리, 미제외 항목, 빈 목록, 제외 해제 및 기존 선택 조건의 회귀 증거가 부족합니다(`human-review`). |
| B 실제 선택 | `strategyB`는 설정을 읽지 않고 `eligible`만 호출합니다. `session-log-1`에서도 제외된 a9가 `[item7]`을 반환했습니다. 승인된 rev1 요구에 대해 `fail`입니다. | B의 누락을 재현하는 테스트와 수정 후 결과가 필요합니다. |
| C | 라우트와 `strategyC`는 존재하지만 승인된 rev1은 A·B만 명시합니다. note-2에 따르면 제품 의견은 추가 가능성이며 디자인은 제품 확인을 요구합니다. 추가 적용 결정은 `human-review`입니다. | 담당자 초기 보고를 확정 근거로 사용하지 말고, 제품 담당자의 적용 여부 결정을 기록해야 합니다. |

캠페인별 제외 목록만 적용해야 하므로 한 캠페인의 제외가 다른 캠페인에 전파되어서는 안 됩니다. 제외되지 않은 경우에는 기존 `enabled` 및 `region` 조건에 따른 선택 결과가 유지되어야 합니다. C는 현재 승인된 A·B 구현 범위에는 포함하지 않되, 영구 제외로 확정하지도 않습니다.

### 구현할 것

1. B가 현재 캠페인의 제외 목록을 읽고 제외 대상이면 선택 결과를 비우도록 보완합니다. 제공된 코드와 테스트가 표현하는 대상은 입력 `asset.id`입니다. A와 같은 의미의 제외 판단을 적용하고, 미제외 대상은 기존 `eligible` 결과를 유지하는 것이 최소 변경입니다. 반환된 `item` 전체에 다른 의미의 필터를 추가할 근거는 없습니다.
2. A·B의 제외 조건이 서로 어긋나지 않도록 유지합니다. 공통 함수 추출은 구현 선택 사항이며, 모든 유형의 공통 진입점에 무조건 적용하면 C의 동작까지 바뀔 수 있으므로 현재 확정 범위에 맞춰야 합니다.
3. 설정 저장 함수에는 현재 확인된 실패가 없습니다. 실제 화면의 저장·재진입 경로를 검증하고, 연결 누락이 확인되면 그 범위만 보완합니다. 제공되지 않은 화면 코드나 저장소의 영속성 구현을 정상이라고 가정하지 않습니다.

수정 예상 범위는 B 선택 경로와 관련 테스트입니다. A와의 공통화 또는 화면 보완은 실제 코드 확인 결과에 따라 추가될 수 있습니다. 변경 중 문제가 생기면 해당 선택 로직 변경을 되돌릴 수 있도록 설정 데이터 변경과 분리하는 방안을 권합니다. 다만 되돌리면 B의 기존 제외 누락도 다시 생기므로, 단순 코드 복구를 기능 정상화로 취급해서는 안 됩니다.

### 확인 방법과 완료 기준

승인된 rev1을 기준으로 A·B 각각 다음 사례를 확인해야 합니다.

| 사례 | 기대 결과 |
| --- | --- |
| 캠페인의 제외 목록에 a9가 있음 | a9에 대한 실제 선택 결과 `[]` |
| a9가 목록에 없거나 목록이 비어 있음 | 변경 전 `eligible` 결과와 동일 |
| a9를 제외했다가 해제함 | 해제 후 기존 선택 조건에 따른 결과로 복귀 |
| 캠페인 1만 a9를 제외함 | 캠페인 1에서는 제외되고, 캠페인 2는 자신의 설정대로 선택 |
| 미제외 대상에 활성·비활성 항목 및 같은·다른 region이 섞여 있음 | 기존 `enabled && region 일치` 조건을 그대로 유지 |
| 화면에서 저장 후 닫고 다시 열어 실제 선택 실행 | 제외 목록이 유지되고 실제 선택에도 반영 |
| C의 기존 선택 호출 | 이번 A·B 보완으로 기존 `fallbackItems` 결과가 변하지 않음 |

`TST-001` 관점에서는 B의 현재 실패를 먼저 고정한 테스트, 최소 수정 후 통과, 리팩터링을 했다면 이후에도 유지되는 결과를 남기는 것이 적절합니다. 기존 session-log는 결함의 관측 근거지만 수정 전후 테스트 실행 이력은 아닙니다.

`TST-002` 관점에서는 구현자가 만든 테스트의 통과만으로 완료를 판단하지 말고, 승인된 rev1과 위 기대 결과를 기준으로 구현 결론과 분리된 검증을 수행해야 합니다. 각 결과에는 사용한 앱 버전·환경·입력·기대 결과·실제 결과를 연결해야 합니다. 특히 설정 저장과 실제 선택은 서로 다른 확인 항목입니다.

이 사례들의 결과와 화면 유지 증거가 확보되면 A·B 완료 여부를 판단할 수 있습니다. 현재는 B의 명시적인 실패와 검증 공백이 있어 완료로 보고할 수 없습니다. 원본 기획·디자인 및 배포 서비스에 접근할 수 없으므로 현재 운영 상태나 배포 완료도 확인할 수 없습니다. `TOOL-001`의 자동 검사기는 이 정책에서 구현 예정이며, 이번에 실행한 검사기나 실제 종료 코드는 없습니다. 결정·증거 보완이 필요하다는 점에서 의미상 종료 상태는 `2`에 해당합니다.

### 결정할 부분

범위 결정은 1건 확정(A·B에 rev1 적용), 1건 미결정(C 확장)입니다. 현재 결정 가능한 질문은 C의 추가 적용 여부 한 건이며, 예상 확인은 1~2회입니다. 추가 적용을 선택하면 C의 선택·화면 동작을 구체화하는 후속 확인이 필요할 수 있습니다. A·B의 승인된 요구를 다시 결정할 필요는 없습니다.

`GOV-002`와 `HITL-002`를 참고하면 C는 다음과 같이 정리할 수 있습니다.

- **권고: 이번 마무리는 승인된 A·B로 진행하고 C 확장은 별도 결정으로 유지합니다.** B 결함과 A·B 검증을 먼저 마무리할 수 있습니다. C의 변경은 없으며, C에도 제외가 필요했던 운영 상황은 해결되지 않는다는 한계가 있습니다. 제품 담당자가 C 적용 여부를 확정할 때 다시 검토합니다.
- **이번 변경에 C를 추가합니다.** 제품 담당자의 명시적 승인과 디자인 충돌 해소가 필요합니다. `strategyC`는 `eligible`과 다른 경로이므로, 어떤 대상을 제외하고 `fallbackItems`에 어떻게 반영할지 및 설정 화면 제공 여부를 함께 정의해야 합니다. 예상 변경은 C 선택·설정 화면·검증 사례까지 넓어집니다. 되돌릴 때에는 C의 이전 선택·화면 동작 복구와 새로 저장한 제외 설정의 처리도 정해야 합니다.

결정 근거는 승인된 rev1 및 정정된 note-2입니다. C 확장이 미정이라는 이유만으로 A·B의 확정 요구까지 미정으로 돌릴 필요는 없습니다. 다만 C까지 포함한 전체 완료를 선언해서는 안 됩니다.

담당자가 여러 업무를 병행했다는 회고는 당사자의 해석으로 보존할 수 있지만, 그것이 누락의 원인이라는 근거는 충분하지 않습니다. 현재 직접 확인되는 문제는 B 경로의 제외 검사 부재와 실제 선택을 충분히 검증하지 못한 증거 공백입니다.
