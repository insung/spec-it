# 다음 변경 준비 상태와 인계

현재 판정은 `human-review`입니다. 제공된 기준선은 v0.4.0 릴리스 소스이며, 0.5.0은 미발행 후보입니다. P1은 명세 작성, P2는 설계·정적 기준선 조사까지 진행됐습니다. 실제 AI 행동 실행, 정책 구현, 후보 검증과 릴리스 준비 완료를 입증하는 자료는 없습니다. 두 인계 사본의 “모든 작업 완료” 문구는 제공된 진행 기록과 맞지 않습니다.

`spec-it-check`의 `full` 관점으로 다음 변경 준비에 관련된 자료를 수동 검토했습니다. 저장소 전체 검사나 실행 validator의 통과 결과는 아닙니다. 정책·프로젝트 파일과 릴리스는 변경하지 않았고, 요청된 실험 응답 파일만 작성했습니다.

## 기준선과 기존 DB 범위

제공자가 명시한 source identity는 `v0.4.0`, Git revision `6a4ea01eb09bfb116ff24fd2d5253889086f9a77`의 export입니다. 직접 확인한 `VERSION`, `.architecture/manifest.yaml`, `.architecture/lock.yaml`, `AGENTS.md`도 모두 정책 버전 `0.4.0`을 가리킵니다. lock의 `schema_version: 0.2.0`은 artifact 형식 버전이며 정책 버전과 다릅니다. export 밖의 Git tag와 원격 공개 상태는 이번 검토에서 독립 확인하지 않았습니다.

이 프로젝트는 `.architecture/project.md`와 승인된 자기 투영이 있는 `policy-ssot`입니다. 따라서 manifest·lock이 없는 프로젝트에 대한 `shadow assessment`로 분류하지 않습니다. manifest는 `risk/standard`, Phase 0, `git-source-only`, `validator: not-implemented`를 선언하고 예외는 없습니다. lock의 자동 검사 대상 상당수도 `planned`입니다. 미발행 0.5.0 후보를 승인된 policy source로 취급하거나 현재 자기 투영을 0.5.0으로 바꿀 단계가 아닙니다.

수동 무결성 확인에서는 manifest 파일의 SHA-256이 lock의 `33970ecf52950c1cf9826ff5b02cef7b34996a37eaeb2fd5c0d55c2deb60fffd`와 일치했습니다. 정책 파일을 `VERSION → rules → profiles → schemas` 순서로 묶고 각 디렉터리 내부 상대 경로를 정렬해 path·NUL·내용·NUL을 해시하면 lock의 `2e54ebfe90ee889af1cc581ee209936b387ee5f913f9504a3ac83611f69b6b4f`와 일치합니다. 다만 TOOL-002의 “repository-relative POSIX path로 정렬”을 전체 경로의 전역 정렬로 해석하면 `3360e1545cf9fe85469f484e3cbd2ba1ebc2ffbdfe4ded2f72255a5bc4c3a5b1`이 나옵니다. 이는 정렬 규약을 명확히 할 `warn` 사항입니다. release identity가 다르다고 단정할 근거는 아니며, 다음 재수렴 전에 규범 문구와 생성 규약을 맞출 필요가 있습니다. 이 계산은 deterministic generator의 구현·재생성 통과를 뜻하지 않습니다.

기존 DB 변경 전달 정책은 재구현 대상으로 올리지 않습니다. `DATA-009`는 0.3.0에 도입됐고 0.4.0에서 책임과 증거 경계를 정밀화했습니다. 기존 정본과 연결 자료는 다음입니다.

- `rules/data/DATA-009.md`: 객체 의사결정 소유자, 정의 정본, 실행 책임, immutable release identity, 적용 순서·직렬화, application compatibility, 환경 증거, 적용 후 검증, 복구 분류.
- `profiles/capability/db-migration.yaml`: 해당 DB 변경을 작성·요청·적용하는 프로젝트에 조건부 적용.
- `docs/database-change-delivery.md`: 자동 실행·위임 실행, 현재 정의 projection, 사후 reconciliation과 정상 사전 승인 증거의 차이 설명.

“완료”는 이 정책·설명 범위의 기존 릴리스 완료로 인계해야 합니다. 0.4.0 release checklist는 DB release manifest·environment history schema, migration runner, DB lock integration, definition reconciliation의 실행 구현이 없다고 명시합니다. 이 제한을 새 구현 과제로 자동 확대하지 않습니다. 이번 정책 저장소의 lock에는 DATA-009가 없으므로, DB 정책을 보유한다는 이유만으로 이 저장소를 DB 실행 프로젝트로 판정하지도 않습니다. 새 변경에서는 기존 계약의 보존과 영향 여부를 확인하면 됩니다.

## 진행 상태와 완료 주장

P1·P2 상태는 `inputs/PK-07.md`의 작업 기록에 근거합니다. draft 4개와 사례 문서·지원 표의 원문은 직접 검토한 것이 아니므로 내용의 적합성이나 승인 여부까지 확인했다고 주장하지 않습니다. 서로 다른 작업 기록을 합쳐 한 작업의 완료 증거로 사용하지 않습니다.

| 단계 | P1 | P2 |
| --- | --- | --- |
| 1. 명세 작성 | 완료 기록 있음. draft 4개 작성; 승인 여부 미확인 | 2단계까지 완료했다는 기록에 포함; 내용·승인 여부 미확인 |
| 2. 설계·기준선 조사 | 미완료 | 완료 기록 있음. 사례 문서·정적 지원 표 수준 |
| 3. 기존 행동 실행 | 미실행 | 실제 AI baseline run 없음 |
| 4. 구현 | 미시작 | 미실행 |
| 5. 후보 검증 | 미실행 | candidate run·독립 검증 없음 |
| 6. 릴리스 준비 | 미완료 | 미완료 |

정적 지원 표는 기존 규칙에 관련 문구가 있다는 근거가 될 수 있지만, AI가 실제 요청에서 그 행동을 수행한다는 관측 결과는 아닙니다. 현재는 개선 효과, 회귀 없음, 파일럿 성공을 결론 낼 수 없습니다.

| 인계 사본 | 요구 추적 판정 | 정정할 완료 표현 |
| --- | --- | --- |
| handoff-A | 되읽기·영향 조사의 구현 대상과 테스트 계획만 있음. 원문 요구인 외부 QA 저장소 연계가 누락됨 | 계획 작성 범위만 표현하고, 외부 QA 연계를 누락된 요구로 복구해야 함. 구현·검증 완료로 쓰면 안 됨 |
| handoff-B | 외부 QA 연계를 `deferred`로 유지하며 owner·사유·재개 조건을 보존함 | 요구가 추적되고 있다는 점은 인정할 수 있으나 구현 완료가 아님. “현재 계획과 보류 기록 작성” 정도로 범위를 한정해야 함 |

handoff-B의 보류 기록은 그대로 이어갑니다: owner `intent-owner`, 사유 “다중 저장소 실증 전”, 재개 조건 “실제 두 저장소 QA 파일럿 확보”. 이는 요구를 삭제한 것과 다릅니다. 다만 owner 표기만으로 그 사람이 보류를 승인했다고 추정하지 않습니다. 제공된 자료에는 승인 근거가 없으므로, 원문 범위를 축소하는 결정의 승인 여부는 미확인입니다. 이 보류를 자동으로 GOV-003의 규칙 예외라고 취급하지도 않습니다. 먼저 요구 범위의 결정인지 실제 규범 완화인지 구분해야 합니다.

## 다음 담당자에게 전달할 내용

원문 전체를 다음 사람이 볼 수 있는지는 미확인입니다. 따라서 이 문서를 읽었다는 사실을 “모든 사용자 원문 되읽기 완료”로 기록하지 마세요. 현재 확인 가능한 요구를 다음과 같이 인계합니다.

> 이 정책 프로젝트의 다음 변경 준비 상태를 점검하고 인계를 작성한다. 기준선은 제공된 v0.4.0 release source이며 목표 0.5.0은 미발행 후보다. 기존 DB 변경 전달 정책은 완료된 범위로 보존하고 다시 구현하지 않는다. 파일 수정이나 릴리스는 하지 않는다. 변경 요구에는 되읽기, 영향 조사, 외부 QA 저장소 연계가 있다. 원칙 문서에는 아직 실제 파일럿 결과가 없다는 사실을 반영한다.

위 인용은 제공된 패킷의 요구를 모은 인계용 요약이며, 확인하지 못한 이전 원문 전체를 대체하지 않습니다. 다음 담당자는 원문·결정·산출물의 위치와 접근 가능 범위를 먼저 확인하고, 접근하지 못한 부분을 계속 표시해야 합니다.

권장 재개 순서는 다음과 같습니다. 이는 이번에 실행하거나 승인한 새 정책이 아니라, 현재 증거에서 도출한 작업 인계입니다.

1. P1은 2단계 설계·기준선 조사부터, P2는 기존 2단계 자료를 확인한 후 3단계 실제 baseline 실행부터 재개합니다. 어느 기록을 이어받는지와 산출물 revision을 구분합니다.
2. 되읽기·영향 조사·외부 QA 연계를 각 수용 기준과 연결하고, 누락·보류·진행 중·완료를 증거와 함께 기록합니다. handoff-A의 누락과 두 사본의 전체 완료 문구를 정정할 대상으로 인계합니다.
3. 기존 v0.4.0 instruction-only 스킬을 실제 사례에서 실행해 입력, 소스 identity, 관측 응답과 실패를 남깁니다. 정적 지원 표와 실행 결과를 별도 근거로 유지합니다.
4. 관측된 부족분을 대상으로 기존 규칙·스킬·문서와 중복 여부, 영향받는 프로필·스키마·템플릿·예제, 유지 비용과 호환성을 조사합니다. 기존 DB 기능의 재구현은 제외합니다. 0.5.0 후보의 정확한 범위와 승인되지 않은 판단을 구분합니다.
5. 구현 권한이 있는 후속 작업에서만 후보를 만들고, 같은 수용 기준에 대한 candidate run과 독립 검증으로 개선·회귀를 확인합니다. 현재 “파일 수정 금지” 요청을 구현 승인으로 해석하지 않습니다.
6. 검증 이후 changelog·migration·연결 자료와 자기 투영의 갱신 범위를 검토합니다. 의무·artifact 계약 변화에 맞는 SemVer를 판단하며, 0.5.0이라는 후보 이름만으로 적합성을 확정하지 않습니다. 공개 정책 릴리스와 소비 프로젝트의 재수렴은 별도 작업이며 자동 업그레이드하지 않습니다.

외부 QA 연계는 handoff-B의 owner·사유·재개 조건을 유지한 보류 항목으로 남깁니다. 실제 두 저장소 파일럿을 확보하면 두 저장소의 기준 revision, 요구와 QA 결과의 연결, 검증 책임과 증거 위치를 구체화해야 합니다. 현재는 그 파일럿이나 연계를 완료했다고 쓸 수 없습니다.

원칙 문서 담당자에게는 다음 문구를 전달할 수 있습니다.

> 현재 파일럿 준비는 P1의 draft 명세 작성과 P2의 설계·정적 기준선 조사까지다. 실제 AI baseline run, candidate run, 구현과 독립 검증은 아직 없으므로 파일럿의 효과나 일반화된 교훈은 확정하지 않았다. 되읽기·영향 조사·외부 QA 연계의 요구 보존과 단계별 완료 구분은 검토할 논점이다. 실제 결과를 확보한 뒤 관측 사실, 해석, 제안과 승인된 원칙을 구분해 반영한다. 외부 QA 연계는 intent-owner 소유로, 다중 저장소 실증 전이라는 이유로 보류 기록이 있으며 실제 두 저장소 QA 파일럿 확보 시 재개한다. 이 보류의 승인 여부는 추가 확인이 필요하다.

원칙 문서 원고의 경로와 접근 권한은 제공되지 않았습니다. 따라서 위 문구는 전달 가능한 초안이며, 원칙 문서에 반영·동기화·전달을 완료했다고 보고하지 않습니다.
