M1과 M2는 전체 변경을 완료 처리할 수 없습니다. M3는 제시된 승인 의도와 A/B 선택 동작의 검증 범위에서는 완료로 볼 수 있습니다. D1은 의도 결정, D2는 구현 수정, D3는 원인 조사부터 필요합니다.

이번 검토는 `quick` 수준의 수동 `shadow assessment`입니다. 각 프로젝트가 채택한 manifest·lock이 없으므로 아래 규칙 ID는 참고 근거이며, 프로젝트의 정책 준수·위반 판정은 아닙니다. 실행은 새로 수행하지 않았고 PK-02에 제공된 관찰을 검토했습니다. Phase 0의 자동 검증기는 미구현입니다.

| 변경 | 판단과 근거 | 후속 조치와 남길 증거 |
|---|---|---|
| M1 | `human-review` — 완료 근거 부족. req-r1에는 A/B가 있지만 spec-r1에는 A만 있습니다. trace-r1이 이어져 있고 생성 테스트가 모두 성공해도, 빠진 B를 검증하지 못합니다. test-A는 A의 제외와 비제외 유지만 입증합니다. A helper만 수정했다는 설명으로 B의 실제 성공·실패를 확정할 수 없습니다. | req-r1을 기준으로 spec-r1의 B 누락을 보완하고 실제 B 선택 경로와 제외 설정 전달을 확인해야 합니다. 누락이 구현에도 있으면 해당 경로를 수정합니다. 원본의 A/B 요구 각각을 명세·테스트·실행 관찰에 연결하고, 구현 맥락과 분리된 검증으로 A/B 제외 및 비제외 결과를 남깁니다. TST-002는 구현자가 만든 테스트만으로 요구 해석을 검증하는 문제에 직접 관련됩니다. |
| M2 | `human-review` — 완료 근거 부족. A-excluded와 A-allowed만 관찰했습니다. 10회 검토했다는 코멘트는 B 동작의 증거가 아닙니다. B가 실패했다고 확정할 수도 없습니다. | B의 제외·비제외 실행 결과를 확보하고 승인 의도와 대조합니다. 검증한 build, 환경, fixture, 기대값·실제값, 검증자와 독립 검증 맥락을 연결합니다. 추가 검토 횟수를 채우는 대신 빠진 행동 증거를 보완합니다. TST-002를 참고합니다. |
| M3 | `pass` — 제공된 동작 증거에 한정한 수동 판단입니다. 승인 의도는 지원 유형을 A/B로 닫았고 inventory-r2와 runtime 등록도 일치합니다. qa-1의 run-3은 승인 의도 rev2, build b3, 환경 e3, fixture f3와 네 경우의 기대값·실제값을 연결합니다. 검토 1회라는 이유로 이를 부족하다고 볼 근거는 없습니다. | inventory-r2와 run-3의 관찰 원문을 그대로 보존하고, 완료 범위를 이 승인 의도와 build·환경·fixture로 명시합니다. 다른 배포나 유형의 성공으로 확대하지 않습니다. 순수 선택 함수이며 DB를 사용하지 않으므로 DB 통합 검증을 추가 완료 조건으로 만들 이유는 없습니다. TST-002의 독립 관찰은 충족하며, 제공 범위에서 외부 경계 변경을 전제로 하는 TST-003 및 외부 인프라·공유 상태를 전제로 하는 TST-006은 `not-applicable`입니다. |

세 사례 모두 실패 테스트→최소 성공→리팩터링 과정은 제공되지 않았습니다. 따라서 TST-001의 TDD 이력은 `human-review`로 남습니다. 이는 M3의 네 동작이 관찰되었다는 사실을 취소하지 않으며, 반대로 M3의 동작 성공만으로 TDD 과정이나 배포 완료까지 입증되는 것도 아닙니다. 실제 채택 규칙에서 TDD 증거가 수용 조건이라면 기존 기록 또는 승인된 예외를 별도로 확인해야 합니다. 과거의 실패 이력을 사후에 만들어 TDD로 기록해서는 안 됩니다.

결함별 수정 위치와 종료 증거는 다음과 같습니다. 실제 파일·라인은 제공되지 않았으므로 확인된 문서 역할과 실행 분기를 기준으로 지정합니다.

| 결함 | 현재 판단·수정 위치 | 수정 뒤 남길 자료와 QA 재확인 |
|---|---|---|
| D1 | `human-review` — 같은 승인 수준의 제품 명세와 디자인 문서가 적용 시점에 관해 충돌합니다. GOV-001·GOV-002 및 HITL-001에 따라 intent-owner의 결정이 필요합니다. 어느 문서가 자동으로 우선한다고 정할 수 없습니다. 먼저 의도 결정 기록을 확정하고 두 문서의 적용 시점을 맞춘 뒤, 결정과 다른 저장·실행 경로를 수정합니다. | 상충 문구와 문서 revision, 결정자·승인 내용, 최종 적용 시점, 영향을 받는 문서와 코드 위치를 남깁니다. 저장 직후와 다음 실행 시점을 구분하는 승인 시나리오를 작성하고 독립 QA의 기대값·실제값을 연결합니다. |
| D2 | `fail` — 승인 시나리오와 관찰 결과가 명확히 다릅니다. 제외 a9가 남았으며 해당 분기에 제외 조회가 없습니다. 현재 수정 대상은 이 선택 분기의 제외 정보 조회·전달·적용 경로입니다. 승인 의도를 바꿔 실패 결과에 맞출 이유는 없습니다. | a9가 남는 실패 재현, 수정한 분기와 revision/build, 수정 후 a9가 빠지는 결과를 남깁니다. 같은 경로의 비제외 선택이 유지되는 회귀 결과도 확인합니다. TST-001·TST-002를 참고해 실패→수정→성공 증거와 독립 QA 관찰을 승인 시나리오에 연결합니다. |
| D3 | `human-review` — f3 성공과 f4 실패는 확인되지만 원인은 미확정입니다. build가 같다는 사실만으로 코드·fixture·환경 중 하나를 원인으로 지목할 수 없습니다. 우선 f3/f4의 입력·기대값·설정 및 각 실행 환경 차이를 조사해야 합니다. | 두 fixture와 실행 환경의 revision·차이, 동일 조건에서의 재현 결과, 원인 가설별 관찰을 남깁니다. 실패가 승인 동작 위반이면 해당 코드 경로를, fixture나 기대값 오류이면 테스트 자료를, 환경 설정 문제이면 해당 설정을 수정합니다. 수정 후 f3와 f4를 다시 확인하고 동일 build·환경인지 또는 다른 조건인지 명시합니다. 의미 있는 기대값 자체가 미정인 경우에만 그 지점을 사람 결정으로 넘깁니다. |

D1에서 intent-owner가 확정할 결정은 하나입니다. 저장 직후 적용하면 저장 이후 현재 선택 상태를 갱신하는 시점과 이미 진행 중인 선택의 처리 범위를 명확히 해야 합니다. 다음 실행부터 적용하면 현재 실행의 상태를 유지하지만 저장 이후에도 이전 설정이 쓰이는 기간이 생깁니다. 두 선택의 비용과 사용자 기대를 비교해야 하며, 현재 자료로 특정 동작을 우선 추천할 근거는 없습니다. 추천 조치는 적용 시점을 승인된 문장으로 먼저 확정하는 것입니다. 예상 수정 범위는 두 명세, 선택 설정을 읽는 시점, 관련 테스트이며, 되돌릴 때도 문서·코드·테스트를 같은 승인 revision으로 맞춰야 합니다. 이 판단은 GOV-001·GOV-002와 HITL-002를 근거로 합니다. 요청이 읽기 전용 검토이므로 여기서는 결정 필요 사항만 남깁니다.

상위 변경 이슈에는 D1~D3을 각각 유지한 채 승인 의도·결정 revision, 실패 관찰, 확정 원인과 수정 위치, 수정 build, 재검증 환경·fixture, 기대값·실제값, QA 담당자·결과·원문 링크를 연결하는 구성을 권합니다. 성공 요약만 남기지 말고 어떤 범위가 종료되었고 무엇이 아직 미확인인지 적어야 합니다. D3처럼 원인을 조사 중인 결함은 수정·재확인 완료로 닫을 수 없습니다. 세 사례는 독립 프로젝트이므로 한 사례의 성공 증거를 다른 사례의 누락에 사용할 수도 없습니다.

다른 프로젝트에서 같은 사고가 반복되었다는 자료는 없습니다. 이번 결함은 우선 해당 프로젝트의 결정·명세·구현·테스트 자료에 반영하고, 이 기록만으로 공통 정책 변경이나 자동화 의무를 확정하지 않는 것이 적절합니다.

요약 판정의 의미는 누락 증거와 사람 결정이 남아 있는 `2`에 해당합니다. 이는 spec-it-check의 모형상 의미이며 실제 검사 프로세스가 반환한 종료 코드는 아닙니다. 프로젝트 파일은 수정하지 않았습니다.
