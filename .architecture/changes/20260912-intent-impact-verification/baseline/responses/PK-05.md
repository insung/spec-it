# 현재 변경 검토 및 다음 세션 조사 기록

이번 결과는 `quick` 범위의 읽기 전용 **shadow assessment**입니다. 애플리케이션에 승인된 manifest와 lock이 없으므로 spec-it 준수·위반을 확정하지 않습니다. 제공된 정책은 `VERSION` 기준 0.4.0이며, 정책 저장소 자체의 manifest를 이 애플리케이션의 선택으로 사용하지 않았습니다. 수동 검토의 종합 상태는 `human-review`입니다. 구현 완료나 수용 가능 여부를 판단할 제품 의도, 승인, 실행 검증이 부족합니다.

기존 `spec-it-check`와 `spec-it-specify`로 현재 사실과 명세에 필요한 내용을 정리하고, `spec-it-clarify`의 결정 패키지 형식으로 다음 의사결정 항목을 준비했습니다. 코드·설정·정책·프로젝트 문서는 수정하지 않았습니다. 요청된 응답 파일만 별도 저장합니다.

## 이어받을 기준과 이전 증거의 유효 범위

현재 기준은 요청에 명시된 `app-c2 + patch-d2`, 디자인 rev3, 확보되어 있다고 전해진 feed 계약 rev2입니다. 이 이름들은 합성 fixture 식별자이며 Git commit이나 배포 식별자가 아닙니다. 제공된 실제 파일은 현재 `app/` 소스뿐입니다. 디자인·feed 계약 원문과 이전 전체 snapshot은 제공되지 않아 요청의 기록과 diff 이상으로 대조하지 못했습니다.

| 이전 기록 | 현재 확인 | 인계 시 취급 |
| --- | --- | --- |
| app-c1, patch-d1 기준 조사 | 현재 app-c2, patch-d2로 교체됨 | 이전 조사 결론 전체를 현재 승인·검증으로 승계하지 않음 |
| 조사 대상 shared.ts, select-a.ts, config.json | B도 같은 helper를 직접 import하고 호출함 | 기존 목록은 소비자 영향 조사로 불완전. 이번에 B까지 확장 |
| filterFlag=false, 기본값 allow | 현재 config.json:1은 true/deny | 이전 설정 결론은 과거 사실로 보존하고 현재 결론에서 제외 |
| A가 helper 호출 | 현재 select-a.ts:1–3에서 재확인 | 호출 관계는 유지되지만 helper 동작이 달라 A의 결과를 재검증해야 함 |
| 디자인 rev2 | 요청에 따르면 rev3에 저장 실패 재시도 버튼 추가 | 코드 diff에 화면 변경이 없다는 이유로 디자인 영향 없음으로 처리할 수 없음 |
| feed 계약 rev2 | 최신 여부 미확인, 원문도 이번 검토 범위에 없음 | 현재 계약 호환성 판단에 충분하지 않음 |
| 사전 기획 승인·실패 테스트 기록 없음 | 승인 자료와 실행 이력 모두 제공되지 않음 | 사후 기록으로 과거 승인이나 TDD 수행을 만들어 채우지 않음 |

## 현재 코드에서 확인한 동작

`src/shared.ts:2`는 `!excluded.includes(assetId)`를 반환합니다. `src/select-a.ts:3`과 `src/select-b.ts:3`은 모두 이를 호출하며, true이면 각각 `['item-a']`, `['item-b']`, false이면 빈 배열을 반환합니다. A와 B 파일이 c1→c2에서 변경되지 않았다는 사실은 helper 변경의 영향이 없다는 뜻이 아닙니다.

정상적인 문자열 배열과 asset ID가 전달된다는 조건에서 다음은 코드 독해로 확정할 수 있습니다. 실행 테스트 결과는 아닙니다.

| 입력 조건 | 이전 helper 기준 | 현재 A | 현재 B |
| --- | --- | --- | --- |
| excluded에 asset.id 포함 | helper가 true이므로 각 item 반환 | 빈 배열 | 빈 배열 |
| excluded에 asset.id 미포함 | 각 item 반환 | item-a 반환 | item-b 반환 |
| excluded가 빈 배열 | 각 item 반환 | item-a 반환 | item-b 반환 |

추가로 `excluded`가 undefined/null이면 현재 helper는 `.includes` 접근에서 예외를 일으킵니다. 이전 helper는 인자를 사용하지 않아 true를 반환했습니다. 반면 settings 자체가 없으면 A/B가 `settings.excluded`를 읽는 단계에서 실패할 수 있었으므로, 이를 모두 이번 변경이 처음 만든 문제라고 분류하면 부정확합니다. asset 자체 누락도 기존 호출부에서 실패할 수 있습니다.

`filterFlag`와 `missingSettings`는 제공된 파일 중 config.json에만 등장합니다. A/B와 helper에는 설정 로딩이나 flag 분기가 없습니다. 따라서 true/deny라는 저장값은 확인되지만, 실제 런타임이 이를 읽는지, flag=false에서 필터가 해제되는지, 설정 누락이 빈 결과·업무 거절·예외 중 무엇이 되는지는 입증되지 않았습니다. 현재 보이는 경로에서 예외 발생을 `missingSettings=deny` 구현 완료로 해석할 수 없습니다.

config 변경은 다른 세션이 작성한 것으로 기록합니다. 승인되지 않았다는 이유로 이를 되돌리거나 다른 기본값으로 대체하지 않습니다.

## 후보 정책과 검토 결과

초기 도입은 프로젝트 기준선 검토가 필요하고, 지금의 helper·설정·화면 동작은 별도 변경 명세로 추적할 실질적 동작 변경입니다. 두 범위를 한 번의 구현 완료 주장으로 합치지 않습니다.

- `capability/shared-domain-library`는 후보입니다. A/B는 현재 확인된 로컬 호출 경로이고, 독립 배포 단위인지 확인되지 않았습니다. 원격 서비스 C의 소비 기록 때문에 독립 소비자 공유 여부를 더 조사할 근거는 있지만, 릴리스·배포 토폴로지는 아직 미확인입니다.
- `risk/standard`는 운영 사용자나 지속되는 업무 상태가 있는 경우의 후보입니다. 현재 자료만으로 위험 축을 확정할 수 없습니다.
- 언어는 TypeScript입니다. 제공된 프로필 목록에는 Python만 있으므로 Python 도구나 구문 규칙을 이 프로젝트에 적용하지 않습니다. backend-service, AWS, 배포, HTTP API, DB 프로필도 제공된 코드만으로 선택하지 않습니다. package.json의 dependencies가 비어 있다는 사실은 외부 서비스가 없다는 증거가 아닙니다.

아래 ID는 lock에 확정된 적용 목록이 아니라 후보 정책과 검토 항목의 연결입니다.

| 상태·후보 규칙 | 발생 계기와 관찰 | 실제 영향 및 다음 증거 |
| --- | --- | --- |
| human-review · HITL-001, HITL-002, GOV-001 | helper의 선택 결과와 missingSettings 기본값이 바뀌지만 제품 의도·승인 없음 | 현재 코드를 정답으로 삼으면 의도와 다른 제외·누락 동작을 승인할 수 있음. 사람 소유 수용 기준과 결정 근거 필요 |
| human-review · COMP-002, 조건부 COMP-001 | 공용 helper의 시그니처가 같아도 A/B 결과가 달라짐. C 사용 기록만 있고 저장소 접근 불가 | A/B의 제외·누락 사례를 검증하고, C의 사용 위치·고정 버전·소유자·실제 배포 버전·계약을 확보해야 함. 공개 계약 해당 여부 및 호환성 계획도 확인 |

| human-review · TOOL-005 | 실행 소스는 있지만 package.json에 scripts·테스트 runner·lint 계약 없음 | 저장소 소유 실행 명령을 수행할 수 없음. TypeScript용 도구·버전·설정·검사 범위·명령·CI 상태를 먼저 정해야 함 |
| human-review · MSG-001, MSG-002, 조건부 COMP-001 | 요청에 따르면 디자인 rev3에 저장 실패 재시도 버튼 추가. 관련 코드·계약 원문 없음 | 클릭 허용 조건, 실패와 결과 미확인 구분, 중복 저장 방지·재시도 안전성을 확인해야 함. 버튼이 보인다는 사실만으로 재시도 정책을 확정하지 않음 |
| warn · CODE-003, CODE-004 검토 후보 | A/B의 settings와 asset에 명명된 입력 타입이 없고, chooseA/B 이름은 역할을 fixture 표기 이상으로 설명하지 않음 | 미변경 legacy 계약 가시성 문제로 분리. 합성 fixture 이름 예외와 실제 소유 경계를 확인한 뒤 작은 별도 개선 범위를 정하며, 이번 검토에서 일괄 개명하지 않음 |

C는 `impact-unknown`입니다. 최신 계약 미확인도 별도 미확인 상태로 유지합니다. A/B는 사용 사실과 소스상 행동 영향이 확인됐지만 실제 릴리스 단위·버전·검증 자료가 없어 업데이트·배포 완료라고 할 수 없습니다. 소비자 평가에는 각 소유자, 위험에 따른 확인 기한, 사용 버전, 검증 결과를 추가해야 합니다.

정책 자동 검사기는 Phase 0에서 제공되지 않습니다. 이번에는 정적 읽기만 수행했고 테스트·lint·타입 검사·빌드·배포 확인을 실행하지 않았습니다. checker 종료 의미에 대응하면 사람 결정 또는 증거 부족에 해당하는 `2`이지만, 실제 검사 프로세스의 종료 코드라는 뜻은 아닙니다.

## 다음 작업에 넘길 결정 기록

제품 결정 확정 0건, 미결 4건입니다. 현재 결정 가능한 선행 묶음은 D1–D3이고 D4는 승인된 동작과 소비자 증거를 확보한 뒤 정합니다. 예상 문답은 2–3회이며, C·최신 feed 계약 조사 결과에 따라 늘 수 있습니다. 이번 요청은 조사 기록 정리이므로 여기서 사용자에게 즉시 답변을 요구하지 않고 다음 세션의 결정 패키지로 남깁니다.

| ID | 결정할 내용·선택지·권고 | 영향·예상 변경·복구 경계 |
| --- | --- | --- |
| D1 | 제외 목록을 A/B 모두에 적용할지, 특정 경로에만 적용할지. 권고는 동일한 제품 정책을 공유하는 것이 확인될 때 공통 적용을 명시하는 것. 현재 호출 구조만으로 제품 범위를 승인하지 않음 | 공통 적용은 일관성을 주지만 B와 C의 기존 결과를 바꿀 수 있음. 경로별 적용은 호출·정책 경계를 나눌 수 있음. 승인된 대상과 포함/미포함/빈 목록 수용 사례를 명세화하고 필요 코드 범위를 정함. 복구는 실제 소비 버전·설정 조합과 기존 허용의 위험을 확인해 설계 |
| D2 | missingSettings의 의미와 allow/deny를 선택. 권고는 settings 전체 누락, excluded 누락, 로딩 실패를 먼저 구분해 각각 명시적 결과를 정하는 것. 자산의 위험 성격이 없으므로 allow/deny 자체를 추천 기본값으로 확정할 수 없음 | allow는 업무를 지속하지만 제외 대상이 노출될 수 있고, deny는 보수적이지만 정상 결과를 차단할 수 있음. 현재 config·로더·경계 검증·오류 또는 빈 결과 계약이 영향 범위. 다른 세션의 config 소유 기록을 유지하고 설정 단독 복구와 helper 복구의 조합을 검증 |
| D3 | 디자인 rev3의 재시도를 이번 변경에 포함할지 별도 변경으로 분리할지. 권고는 이번 범위에 포함한다면 실패/결과 미확인별 허용 동작과 중복 처리 기준까지 승인하는 것. 범위 밖이면 후속 항목과 연결 근거를 남김 | 포함 시 UI·실패 outcome·재시도 업무 흐름·수용 사례가 필요. 분리 시 rev3 충족을 이번 완료 기준으로 주장하지 않음. 복구 경계는 버튼 노출·재시도 경로와 이미 발생한 저장 결과를 구분해야 함 |
| D4 | 채택할 위험 수준과 공유 라이브러리 경계, C 영향 확인 전 릴리스 여부. 권고는 공유 배포가 확인되면 해당 capability를 선택하고 소비자 영향이 미확인인 범위를 공개한 상태로 릴리스 결정을 받는 것 | 프로필·manifest/lock·소비자별 버전·이행/복구 기록에 영향. 확인 전 릴리스는 미확인 소비자 동작 변경 위험이 있으며, 임시 완화·소유자·재검토 조건 없는 완료 처리는 근거 부족. 이 응답에서는 릴리스나 기준선 파일을 만들지 않음 |

다음 세션은 우선 현재 자료의 식별자와 조사 범위를 유지하고, 설정 로더·실제 호출 입력·디자인 rev3 원문·feed 정본/버전·C 담당자와 사용 증거를 보강하면 됩니다. 그 뒤 사람 소유의 목적, 대상 사용자, 성공 기준, 비목표, 수용 사례, 복구 경계를 `clarifying` 상태의 변경 명세로 정리할 수 있습니다. 기존 구현을 과거 사전 기획으로 꾸미지 말고 명세 작성 시점과 이미 구현된 범위를 명시해야 합니다. 중요 결정이 남아 있으므로 지금은 `spec-it:converge` 단계가 아닙니다.
