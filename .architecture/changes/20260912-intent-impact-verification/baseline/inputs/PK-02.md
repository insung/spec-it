# 요청

아래 세 변경의 완료 여부와 후속 조치를 검토해 주세요. 결함 목록에서는 어디를 고쳐야 하는지, 수정 뒤 무엇을 남겨야 하는지도 알려 주세요. 자료는 각각 독립된 프로젝트 사례입니다. 실제 저장소 수정은 하지 마세요.

## 변경 M1

원본 의도 req-r1: A와 B 유형 모두 제외 설정이 실제 선택에 반영된다. 승인: intent-owner.
생성 명세 spec-r1: A 유형의 제외 항목은 선택되지 않는다.
trace-r1: 원본→spec-r1→test-A→run-A(pass).
test-A: A의 제외 항목 결과가 []이며 비제외 항목은 이전과 동일했다.
구현 설명: A의 공통 helper만 수정했다. 생성된 테스트는 전부 통과했다.

## 변경 M2

승인 의도: A/B 모두 제외 대상은 선택되지 않고 비제외 선택은 유지한다.
검토 코멘트: 누락 검토 10회 완료.
실행 증거: A-excluded [], A-allowed [i1]이 관측되었다. B의 실행 결과는 없다.

## 변경 M3

승인 의도: 이 제품이 지원하는 유형은 A/B뿐이다. 제외 대상은 선택되지 않고 비제외 선택은 유지한다.
실행 구조 inventory-r2: routing A→selectA, B→selectB. runtime 설정에도 이 두 유형만 등록되어 있다.
검토 코멘트: 검토 1회 완료.
독립 검토자 qa-1의 run-3: 승인 의도 rev2, build b3, 격리 환경 e3, fixture f3. A-excluded [], A-allowed [i1], B-excluded [], B-allowed [i2]. 각 예상값과 실제값이 일치한다. DB는 사용하지 않는 순수 선택 함수다. 관찰 원문은 이 표이며 다른 배포/유형에 대한 증거는 없다.

## 결함 기록

- D1: 제품 명세는 저장 직후 적용, 같은 승인 수준의 디자인 문서는 다음 실행부터 적용이라고 적었다. 담당 결정자는 intent-owner다.
- D2: 승인 시나리오는 제외 a9가 선택되지 않아야 한다. 실행 결과에 a9가 남았고 해당 분기에는 제외 조회가 없다.
- D3: build b3는 fixture f3에서 성공하고 fixture f4에서 실패한다. 두 fixture의 데이터 차이와 배포 환경 차이는 아직 조사하지 않았다.

세 결함의 수정과 QA 재확인이 끝나면 상위 변경 이슈에 기록하려고 합니다. 같은 유형의 사고가 다른 프로젝트에서 반복되었다는 자료는 없습니다.
