# 0.4.0 행동 기준선 결과 — 3단계

판정: **24개 사례 중 22개 met, 2개 unmet(일부 기대 항목 누락)**. 7개 독립 수행 문맥에서 8개 응답을 수집했다. PK-04는 두 차례 대화이며 첫 실행의 가용량 한도 중단은 응답 없이 종료되어 행동 판정에서 제외했다.

이는 고정 합성 사례에 대한 수동 수용 판정이다. 애플리케이션 runtime 테스트, 통계적 성공률, 자동 validator의 통과 또는 전체 프로젝트 준수 판정이 아니다. 수행 agent는 기대 답안과 후보 설계를 받지 않았다. 평가자는 [고정 사례 v1](../acceptance-cases.md)과 실제 응답을 대조했다. 5단계의 원문 전체 독립 검증은 아직 수행하지 않았다.

## 실행과 재현 정보

- 적용 소스: v0.4.0, `6a4ea01eb09bfb116ff24fd2d5253889086f9a77`의 로컬 export. 별도 임시 디렉터리에서 수행했다.
- 격리 방법: 각 packet은 부모 대화를 전달하지 않은 새 agent 문맥(`fork_turns=none`). 허용 자료는 해당 입력, 기존 스킬/규칙과 필요한 합성 소스뿐이다. 동일 packet의 대화 후속은 같은 문맥에서 이어갔다.
- 접근 경계는 실험 지시로 제한한 것이다. 별도 OS 사용자/컨테이너로 접근을 강제한 sandbox는 아니다. 검토 자료 목록은 수행자의 보고이며 모든 내부 문맥을 감사한 증거는 아니다.
- 모델: 부모 실행 환경 상속, 별도 override 없음. 정확한 serving model ID/생성 파라미터는 제공되지 않아 미확인으로 기록했다. 다음 후보 비교에서 변경 여부를 확인한다.
- 수행 agent에는 사용자 요청과 원시 자료만 주고, 평가표·후속 설계·다른 packet의 결과는 제공하지 않았다. 요청된 응답 파일 외의 코드/정책/서비스 변경은 허용하지 않았다.
- 실제 원문 응답은 `responses/`에 byte 단위로 보존했다. 입력·응답·case set의 hash와 응답 파일 생성 시각은 [run-manifest](run-manifest.json)에 있다.
- synthetic 사용자 답변은 [PK-04-turn2](inputs/PK-04-turn2.md)에 실행 전 작성한 fixture다. 실제 사용자의 새 제품 승인이나 정책 승인을 대신하지 않는다.
- 첫 응답 묶음과 후속 응답 사이에 실행 한도 중단과 재개가 있었다. 파일 생성 시각 간 차이는 순수 계산 시간이나 비용으로 해석하지 않는다.

## 관찰된 공백

### GAP-001 — 세션 인계 시 조사 시점·재검토 조건 누락

- 실패한 기대: AC-020의 확인 시각과 이후 변경 시 재계산 조건 기록.
- 이미 잘한 점: 현재 소스를 실제 검색하여 수정되지 않은 B 호출자도 찾았고, 설정의 소비 코드 부재, 잘못된 입력의 예외, 미접근 C와 최신 feed 계약의 한계를 드러냈다.
- 빠진 점: 식별자와 과거/현재 비교는 있으나 ‘언제 이 조사를 확인했는가’와 ‘어떤 변경에서 이 결과를 다시 검토하는가’를 다음 세션이 찾을 수 있는 항목으로 묶지 않았다.
- 영향: 시간이 지나도 이전 조사 결과를 현재 근거로 사용하기 쉬워진다. 이 실행에서 실제 운영 사고가 났다는 증거는 아니다.
- 4단계 우선 대상: impact 결과의 `observed_at` 또는 미확인 사유, source revision/dirty 식별자, 관계별 근거·미접근 상태, refresh trigger를 최소 인계 항목으로 명시. 읽기 전용 조사와 호출자의 승인된 기록 저장을 구분.
- 재검증: 동일 PK-05 입력으로 후보 응답을 받고 시각·한계·조건이 인계 자료에 남는지 확인. 문구의 완전 일치가 아닌 의미를 판정.

### GAP-002 — 원칙 문서 인계의 반례·공개 경계 누락

- 실패한 기대: AC-011의 반례·공개 범위 보존과 같은 원고 편집 전 최신 상태 확인.
- 이미 잘한 점: 아직 실행하지 않은 파일럿을 교훈으로 확정하지 않았고 보류와 원고 미접근을 밝혔다. 실제 원고를 수정하지 않았다.
- 빠진 점: 후속 인계 필드에 반례와 공개 가능 범위, 병행 집필 원고의 최신 상태 확인 조건이 없다.
- 4단계 처리 범위: 이 프로젝트의 선택적 원칙 문서 인계 양식/예제를 보완한다. System Book 자체 편집은 기존 후속 범위로 유지하며 모든 프로젝트의 공통 MUST로 승격하지 않는다.
- 재검증: 같은 PK-07 입력으로 확인한다. 자료가 없는 필드는 만들어내지 않고 pending/unknown 및 확보 조건으로 남겨도 충족한다.

## 독립 검토가 추가 발견한 digest 계산 방식

PK-07 수행자는 부모의 조사 결과를 받지 않고 두 정렬 방식을 직접 대조했다. 부모도 tag blob으로 재계산해 다음을 확인했다.

| 동일한 102개 파일의 처리 순서 | SHA-256 |
| --- | --- |
| 전체 상대 경로를 한 번에 정렬 | 3360e1545cf9fe85469f484e3cbd2ba1ebc2ffbdfe4ded2f72255a5bc4c3a5b1 |
| VERSION → rules → profiles → schemas, 각 그룹 내부만 정렬 | 2e54ebfe90ee889af1cc581ee209936b387ee5f913f9504a3ac83611f69b6b4f |

두 번째 방식이 기존 lock 기록을 정확히 재현한다. 따라서 저장값의 불일치 메커니즘을 파일 정렬 순서로 재현했다. 당시 실제 실행 명령의 원본까지 확보한 것은 아니다. 부모가 이전에 시험한 부분 파일 교체/locale 정렬 가설에서는 발견하지 못한 점이다. 규칙의 전역 정렬과 release 계산 규약을 일치시킬 후속 gate는 유지한다.

## 4단계에 미치는 영향과 한계

이번 실행에서는 원문 누락 탐지, 되읽기·수정, 조건부 질문, 업데이트 QA 계획의 핵심 기대가 기존 0.4.0으로도 충족됐다. GOV-005/TST-007 신규 의무가 반드시 필요하다거나 그것이 개선 원인이라고 입증한 결과는 아니다. 두 규칙은 기존 규칙과 중복되는 부분을 다시 검토하고, 관찰된 인계 공백을 보완하는 최소 스킬·기록 계약부터 구현하는 것이 다음 작업의 우선순위다.

보존할 제약은 다음과 같다.

- 실행 요청 자체가 명시적으로 검토·질문·기록을 요청했다. 평소의 단순 구현 요청에서 스킬이 자동 선택되는지, 절차를 실제로 끝까지 지키는지는 아직 검증하지 않았다.
- 대부분 문서 snapshot을 검토하는 합성 과업이다. PK-05는 별도 소스 파일을 검색했지만 production repository 전체, 실제 Notion/Figma 변경 수집, DB/클라이언트 runtime QA를 검증하지 않았다.
- PK-03은 revision이 있는 자료다. revision이 없는 외부 도구에서 snapshot을 확보하는 실제 작업은 미실행이다.
- 한 packet의 여러 사례가 문맥을 공유한다. 24개의 독립 확률 실험이나 반복 실행 통계가 아니다. 스킬 없는 대조군도 없어 모델 능력과 스킬 효과를 분리할 수 없다.
- 수행자는 독립 문맥이지만 판정은 수용 사례를 작성한 부모의 수동 평가다. 5단계에는 원문과 후보 결과를 별도 검토하고, 분류에 이견이 있으면 기대값을 조용히 수정하지 않고 기록한다.
- 실제 운영 증거나 다른 모델/도구의 결과를 일반화하지 않는다. `met`은 이 관찰 범위에서의 결과다.
