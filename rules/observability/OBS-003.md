# OBS-003 — Scheduled data outcome health

0.3.0에 도입되었습니다. 운영 상태는 `job succeeded`와 `job failed` 둘로 끝나지 않습니다. expected schedule과 terminal output contract를 기준으로 실제 run과 최종 데이터를 비교합니다. 중간 단계 번호나 특정 log row는 진단 단서일 수 있지만 완료 증거를 대신하지 않습니다.

## 관측 단위

- **freshness**: 승인된 시각까지 필요한 partition 또는 기준일이 준비됐는지 봅니다.
- **completeness**: 필수 stage와 terminal dataset이 모두 생성됐고 기대 범위가 채워졌는지 봅니다.
- **integrity**: unique·foreign-key·check constraint와 별도 invariant가 지켜졌는지 봅니다.
- **reconciliation**: 원천과 결과의 건수·합계·control total 또는 단계 간 관계가 승인된 허용 범위에 있는지 봅니다.

DB constraint로 막을 수 있는 중복과 잘못된 참조는 constraint를 우선 사용하고 monitoring을 유일한 방어 수단으로 삼지 않습니다. 반대로 freshness와 업무상 completeness처럼 constraint가 표현하지 못하는 조건은 metric, query 또는 synthetic read로 검사합니다. threshold와 정상적인 빈 결과의 의미는 공통 규칙이 아니라 프로젝트 계약이 소유합니다.

## 발견과 복구

경보는 증상, target partition, 마지막 정상 run, 영향받는 consumer, 현재 owner와 runbook을 연결합니다. 재실행은 calendar gate와 분리하고, 같은 partition의 competing run을 [ARCH-005](../architecture/ARCH-005.md)에 따라 막거나 안전하게 deduplicate합니다. 일부 stage만 다시 실행해야 하면 전체 dependency와 terminal outputs를 재검증하고 같은 run ledger에 이유와 결과를 남깁니다.

API와 화면은 [MSG-001](../messages/MSG-001.md), [MSG-002](../messages/MSG-002.md)에 따라 정상 0건, 준비 중, stale, 실패를 필요한 범위에서 구분합니다. backup restore는 [REL-001](../reliability/REL-001.md), 코드·routine·schema 변경은 [DATA-009](../data/DATA-009.md)의 release identity를 연결합니다.

자료: [OpenLineage run cycle](https://openlineage.io/docs/spec/run-cycle/), [dbt source freshness](https://docs.getdbt.com/docs/deploy/source-freshness). 제품 선택을 요구하지 않습니다. runtime validator와 alert integration은 미구현이며 Phase 0 판정은 `human-review`입니다.
